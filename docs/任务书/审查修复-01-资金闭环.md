## 3. 必须成立的业务不变量

1. 成功支付的订单最终必须是有效已支付订单，或进入已完成退款的取消结果；外部结果未知时有可恢复的处理状态，不能悄悄结束。
2. 库存释放和支付/取消胜负一致，一笔订单最多回补一次；被取消的订单不能重新获得核销能力。
3. 退款、售后开案、暂扣确认和分账启动具有明确的互斥顺序。不能依靠“调用前再查询一次”代替原子占位。
4. 财务已经成功的支付、退款、分账事实必须落库或进入对账待办；本地更新零行不能被当作成功收尾。
5. 同一操作的重试复用幂等键；迟到回复必须匹配操作 ID/版本，不得覆盖后续操作。
6. 部分退款保留是否核销、剩余本金和后续履约义务。无未决操作的终态满足：原支付额 = 已确认累计退款 + 最终净分账；分账内部三方金额之和等于净分账。
7. held/争议期间停止资金分出，但不会占死整个调度队列。正常可执行记录必须在有限轮次内取得处理机会。

## 4. 实施步骤

### C01-A：先确定操作模型和兼容契约

列出当前所有写入订单状态和资金字段的入口，形成“支付/取消/退款/分账/售后/暂扣”的转换表。区分订单履约状态与资金操作状态，优先复用现有操作、outbox、dispatcher 和对账能力。

建议的资金操作记录至少能表达：订单、操作类型、稳定操作 ID、请求金额、业务版本、在途/成功/失败/待核对状态、provider 引用、重试时间、领取租约。字段名和表拆分属于实现选择；必须具备的能力是持久化、可重试、可查询、可防止旧执行者覆盖新结果。

本地事务只负责占位与写事实，不跨 Finance RPC 持有数据库事务。先争取操作权，再调用远端，最后按操作 ID/版本收尾；进程在任意一步退出后，后台均能找到未完操作。

### C01-B：收口支付与取消竞态

- 将消费者取消和超时关单接入相同的竞争规则。
- 支付开始时未过期，请求在途时关单仍可能发生；不要只加一个请求前的 deadline 判断。
- 若取消胜出而支付已成功，登记稳定幂等的退款补偿，并由持久化恢复驱动完成。
- 支付成功回复丢失时，复用同一支付操作查询/重试，不能再扣一次；取消后的退款也不能重复。
- 明确取消处理中、补偿失败时的 API 状态和可解释原因，同步前端兼容处理。

### C01-C：收口分账与售后/暂扣互斥

在分账发出前原子占位，让售后开案和暂扣确认检查同一操作边界。售后或暂扣先取得权限时不发出分账；分账先取得权限时，其他入口返回约定的处理中/冲突结果，不能谎称已经成功阻断资金。

分账成功后将财务事实可靠落库；不要仅因订单展示状态已变化而丢弃 split_completed_at。补查 Finance 内部退款与分账是否也竞争同一权威状态，保证 Marketplace 的判断不会被另一路调用绕过。

### C01-D：补部分退款后的净额结算

- 保留原支付总额、原冻结费率/分配及已核销事实，不能通过改写原金额让旧分账校验“通过”。
- 未核销部分退款：继续允许合法核销；到期时退剩余可退本金。
- 已核销部分退款：售后结案且满足冷静期/暂扣条件后，继续结算剩余净额。
- 抽出唯一的服务端净额分配函数，沿用既有冻结比例、舍入及尾差规则；若当前代码缺少相应规则，先把拟用算法与例算写入本阶段技术决策，不自行引入新费率。
- 使用累计退款计算最终分配，避免同一总退款拆成多次后因逐次取整产生不同结果；覆盖 1 分、退满和接近金额上限。
- Marketplace/Finance 同步升级契约，明确原支付额、累计退款、净分账额各字段含义；旧零退款及历史 redeeming 行仍兼容。
- 保留 #97 的结算后退款禁令；参考旧分摊算法不等于重新开放旧结算后退款路径。

### C01-E：让调度持续前进

在 LIMIT 前排除当前不可分账的 held/争议行，或按资金操作队列配合 next_attempt_at、租约调度。不能仅在取满批次后返回 empty；也不能通过删除待办“解决”队列拥堵。

考虑多实例领取、租约过期和重试退避。暂扣解除后重新进入可执行集合。到期关单、到期退款的独立扫描语义保持清楚，测试分别验证。
