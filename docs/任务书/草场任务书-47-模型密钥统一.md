# 草场任务书 #47：模型密钥统一（平台通用凭据 + 用户级模型开关）

> 来源：2026-08-25 用户提出「密钥设置散在三处」，逐项对齐后落项。改动面调研 2026-08-25 完成（main `89be273` 快照）。
> 状态：2026-08-25 立项，待实现。

## 目标

把散在四处的密钥/模型配置收敛成两句话可以讲清的模型：

1. **运营在 admin 配一套通用凭据**（provider + baseUrl + 密钥同行），平台模型配置引用它；改密钥不改 env、不重启。
2. **用户按能力用开关选择「用我自己的模型」还是「用系统默认」**；商家侧由组织统一配置，不下到个人。

顺带清偿三处既有缺陷与一处明文凭据存储（见 D22）。

### 现状（动手前必须先认清）

四个入口，背后是**两套互不相通的机制**：

| # | 入口 | 位置 | 存什么 | 加密 | 谁真的在用 |
|---|---|---|---|---|---|
| 1 | 顶部「设置」按钮 | `DefaultLayout.vue:168` → `AnalysisSettingsModal.vue`（1169 行 / 6 页签） | 每用户 × 每 feature 的 baseUrl+apiKey+model（`user_settings` type=analysis） | **明文**（仅读时 mask） | 只有 `video` 被 `VideoRecreationAdaptationService` 消费；`image`/`article`/`imageGeneration`/`videoProduction` **写了没人读** |
| 2 | AI 创作中心「模型密钥」页签 | `AiCreationCenter.vue:301` → `AiProviderKeysPanel.vue` | 个人 BYOK（`/api/ai/keys`），按 capability | 信封加密 | `ByokRoutingService` 第一优先级 |
| 3 | 工作台 → 组织管理 | `GrasslandWorkbench.vue:856` → `AiOrgProviderKeysPanel.vue` | 组织 BYOK + `allow_platform_fallback`（ADR-D17） | 信封加密 | `ByokRoutingService` 第二优先级 |
| 4 | 运营台 admin | `AdminView.vue:247` → `AiPlatformModelsPanel.vue` | 平台模型 `(capability, model_role)` 的 provider/model/baseUrl/并发/健康 | — | 控制面第三优先级 |

两条决定性事实：

- **入口 4 里没有任何密钥字段。** `PlatformModelConfigResponse` 注释写明「不含任何密钥——平台模型凭据在 env/secret，非此表」。平台密钥是单个环境变量 `ai.qwen.api-key`，`PlatformModelConfig.validate()` 启动期 fail-fast。「运营配置通用密钥」今天在 UI 上不存在。
- **用户开关双向都不存在。** `ByokRoutingService:62-68` 写死 `个人 > 组织 > 平台`：有个人密钥就必然用它，想用系统默认只能停用/删除密钥；反向的 `allowFallback` 由后端调用点硬编码（全部产品流恒 `true`）。

## 决策表（已定死，勿重开）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 平台密钥**落库加密**：admin 可写，复用个人 BYOK 的 `EnvelopeEncryption`/KEK；env 降级为「表内无可用凭据时的 bootstrap 兜底」 | 运营改 key 不该要发版；且 admin 已能改 baseUrl 却改不了 key，这个组合本身是坏的 |
| D2 | 密钥载体 = 新表 `platform_provider_credential`（provider + **base_url** + encrypted_key 同行），`platform_model_config` 去掉 `base_url`、改挂 `credential_id` FK | 不按 `provider` 归组：`provider` 是**类别不是实例**（正则仅 `qwen\|openai-compatible`），`openai-compatible` 可以是多家不同 baseUrl 的厂商，按名归组必撞车。key 与 baseUrl 同生死后，「换地址忘换密钥」在结构上不可能发生 |
| D3 | 「一套通用密钥」的落地形态 = 建一行凭据，十几行模型配置全部指向它；换某能力的厂商 = 只改那行的 `credential_id` | capability 全集远大于二（seeder 就种 `text`/`content_safety`/`voice`/`retrieval`/`image_edit`，另有 `image`/`image_generation`/`video_generation`），主备各一行是十几行，不能让运营填十几遍 |
| D4 | 凭据端点鉴权 = `IntelligenceCallerResolver.requireAdmin`，与 `/api/admin/ai/models` 同闸；**不新增** `PLATFORM_AI` 角色 | `role=admin` 已是平台最高权限；角色细化该在统一的一次 admin 角色治理里做，不在此开先例 |
| D5 | 凭据的掩码/轮换/停用**完全复刻** `AiProviderKeyController`：GET 只回 `maskedHint`，改连接信息用 PUT（不含 key），换密钥用独立 `PUT /{id}/key`，停用为软删 | 老 analysis settings 那套「留空=保留、空格=清空」是历史包袱且不直观，不复制到新表 |
| D6 | 凭据被引用时**拒绝删除**，报「仍被 N 个模型配置引用」，要求先改指向 | 软删+运行时 503 是「配置看起来正常、运行时才炸」的陷阱，且 503 现场离原因跨两张表；级联停用又太暴力 |
| D7 | `ai_run` 增记 `credential_version`，与 `platform_model_version` 并列 | 排障需要：厂商 key 额度耗尽/被封时，第一个问题就是「这批 Run 用的哪把 key、是不是轮换那刻起」。一个 int 列 |
| D8 | fail 语义：启动期只校验「env 兜底或库内至少一行可用凭据」；运行时某 capability 凭据缺失/KEK 未配 → **该请求 503**，其它能力照常 | 严格启动期 fail-fast 与 ADR-D16「`content_safety` 缺省不种、深检降级为仅 L1」直接打架。503 保住「不静默换 key、不静默扣错额度」的底线 |
| D9 | 路由分叉按**活动身份**：merchant 活动身份 → `组织 > 平台`（跳过个人）；recommender → `个人 > 平台`（跳过组织）。个人密钥数据保留，仅不参与 merchant 视角路由 | `SessionIdentityResolver:75-80` 已保证「`organizationId` 非空 ⟺ merchant 活动身份」（注释：破坏它就破坏 HLD 7.4「活动身份 ↔ 组织上下文」不变量），且 `ByokRoutingService:65-68` 已按 `organizationId == null` 分支——**recommender 的 `个人 > 平台` 今天就是现状**，改动只剩「merchant 时跳过个人查询」一处 |
| D10 | **不做**「固定一个账号只能是商家或推荐官」 | PRD 五处写死双身份（§50/§51/§230/§961/§969-970），落地面 21 个 Java 文件 + 前端 4 处，`useActiveIdentity.ts` 还专门有解决双身份激活竞态的注释。更要紧的是它对本任务毫无帮助：D9 下一个 session 的活动身份是确定的，运行时本就是单链条，不存在歧义。记为独立 epic |
| D11 | 用户开关粒度 = **每 capability 一个**（text / image / image_generation / video_generation），非全局单开关 | 「只想自己出文本的钱、图片用平台」是最常见的部分配置，全局开关表达不了；要求配齐四项才能开又太糙 |
| D12 | 开关 off **保留密钥密文**，只是不参与路由 | 开关的价值在可逆——「今天省自己的额度」不该让用户明天重贴一遍 key。不解密即不触碰，安全面不变 |
| D13 | 开关存储 = 新表 `ai_provider_preference(account_id, capability)`，PK 复合，`version` 乐观锁（对齐 V41 的 `ai_org_byok_policy` 形状）；**不塞 `user_settings`** | `user_settings` 正被本任务清空（D17/D18），不该往里加新东西 |
| D14 | 开关默认值 = **无行即 on**（有 key 就用 key） | 与今天语义逐字节一致，存量 BYOK 用户零感知，**迁移脚本一行不用写**。若默认 off，存量用户会在上线瞬间静默切平台模型并**开始扣积分**（D-11：BYOK 恒 0 cents） |
| D15 | 商家侧**没有开关**：组织配了该 capability 的 key 就用，没配就平台（「配置即启用」，删 key 才是关闭） | org admin 本来就是唯一能增删组织 key 的人，「配了但不用」只是多一个能配错的地方。个人侧需要开关是因为用户要在自己付费/平台付费间来回切，组织没有这个诉求 |
| D16 | `ai_org_byok_policy.allow_platform_fallback` **默认翻为 `true`**（列默认 + 无行默认），**已有行不动**；ADR-D17 追加修订记录 | D15「没配就走平台」与 D17 原默认 `false`（DENIED）在「组织配了 text key、没配 image key」时直接冲突。保留原默认会让 org admin 配完 text 后、图片能力对全组织突然不可用，且他完全不会预期。废表则要推翻三天前采纳的 ADR-D17 第 3 条（D-11 落地口径），须重开 ADR。已显式设 `false` 的组织保持严格模式——那是他们的明示选择 |

| D18 | 三个真有消费者的孤儿就近安置：①首页热点数据源 → **升为 admin 平台配置**，`HomepageHotService` 改读平台配置，存量每用户行删除；②飞书导出凭据 → 内联到图片评价视图，并接 `EnvelopeEncryption`；③`features.video` 的 BYOK → 迁进 `/api/ai/keys` 的 `text` capability | 热点是匿名可访问的**平台数据**，每用户配置在缓存层面本就说不通——与任务书 #35「同一缓存窗口标签稳定」的运营资产定位冲突。飞书凭据放在用它的地方，用户不必为配导出翻全局设置 |

## 边界

- **不做**：固定单身份账号（D10）；六视图裸访问收紧为必须带 handoff（D20）；新增 `PLATFORM_AI` 角色（D4）；同组织同能力多把 active 密钥（沿用 ADR-D17「不做」）；成员端组织密钥只读列表（同上）。
- **不动**：`allowFallback` 调用点（D22）；`/api/ai/keys` 与 `/api/ai/organizations/{orgId}/keys` 的既有 wire 契约；ADR-D16 的 L1/L2 两层语义与降级路径；ADR-D11 的计费边界（BYOK 恒 0 cents、组织密钥不 consume/refund）。
- **通知**：D17/D19 是用户可感知变化（顶部设置按钮消失 + BYOK 迁移），上线前经 identity `mail_outbox` 发一条站内通知，重点覆盖有存量 `features.video` BYOK 的用户。

## 验收标准（整体）

1. **运营闭环**：admin 建一行凭据 → 十几行模型配置指向它 → 改 key 后**不重启**下一个 Run 即用新 key；页面只见 `sk-****abcd` 掩码。
2. **凭据护栏**：引用中的凭据删除被拒并报引用数；`sandbox` provider 的三行可 PUT（S0 前 400）；未配 KEK → 凭据写入 503 且**不退化存明文**。
3. **凭据按目的地隔离**：停用某 capability 的凭据 → 该能力**退回 env 密钥**（不是立刻不可用），其它 capability 完全不受影响。

   ⚠️ **原文写的「停用 → 503」在 V52 之前不成立**，实测修正：`base_url` 走 `COALESCE(credential.base_url, config.base_url)`，停用凭据后地址仍可解析，只是密钥不再来自凭据、执行层回落 env bootstrap。等 V52 `DROP COLUMN` 让 COALESCE 无处可落，baseUrl 才变 null 并触发按 capability 503。锁定在 `PlatformProviderCredentialControllerIT` 的验收 3 用例。

   这也意味着 **V52 之前「停用凭据」不是可靠的熔断手段**——要让某能力真正停下来，得停用它的 `platform_model_config` 行（`DELETE /api/admin/ai/models/{capability}/{modelRole}`）。
4. **路由分叉**：merchant 活动身份下个人密钥不参与（三例锁定测试全绿）；recommender 行为与今天逐字节一致。
5. **开关语义**：无偏好行 = 用自己的 key（存量零感知）；关掉 text → 走平台且扣积分、image 不变；关闭前有二次确认；页签常驻显示计费主体。

## 代码库陷阱清单（必读）

- **Java 构建**：JDK 25，必须**显式给路径**（`JAVA_HOME=/opt/homebrew/opt/openjdk@25`）——`java_home -v 25` 会静默回落 JDK 8；入口 `platform-java/` 下 `./gradlew`
- **Docker 重建**：镜像拷贝预构建 jar，改完 Java 先 `bootJar` 再 `docker compose build`，漏跑会静默打进旧代码
- **迁移号冲突**：动手前 `ls db/migration` 取实际最新号顺延，别按本文写作时点的 V45 推
- **Reactor**：`switchIfEmpty` 参数在**装配期**求值，副作用必须包 `Mono.defer`（`ByokRoutingService` 现有代码就是这个写法，改动时别拆掉）；事务 `Mono` 的 `onNext` 早于 commit
- **KEK fail-closed**：`CRYPTO_KEK_BASE64` 未配时相关请求 **503**，绝不退化存明文（D-10 口径）；解密后的明文只活在进程内，不入日志/响应/outbox
- **intelligence 无全局 ObjectMapper bean**——JSON 处理持服务本地实例；jsonb 用 `DatabaseClient` 手写 SQL
- **intelligence 无全局 SecurityWebFilterChain**：授权是逐 controller 约定，新增端点漏掉 `requireAdmin` 就是完全无鉴权（`/api/admin/kyb-requests` 曾如此）
- **admin 端点**用 `IntelligenceCallerResolver.requireAdmin`，别自造角色判断
- **edge fail-closed**：新前缀 `/api/admin/ai/credentials` 与 `/api/ai/preferences` 不注册进 RouteManifest 即 404；`/api/ai/preferences` 要挂在既有 `EDGE_ROUTE_AI_INTELLIGENCE` 精确前缀下，注意别抢 legacy `/api/admin/users`
- **`platform_model_config` 部分唯一索引**（V7）：同 `(capability, model_role)` 只允许一个 `enabled=true`；加 FK 时别破坏它
- **积分与退款**：`refund:<consumeId>` 幂等键由 intelligence 侧派生，partial unique index 保证一次扣减至多一次退款；开关切换**不涉及**退款路径，但改错路由会让计费主体错位——S5 的验证必须真看积分流水
- **`user_settings` 是 database-bootstrap 管的共享表**（JBE-02），S7 的 V51 动它前确认迁移归属服务正确
- 提交按语义拆分（建议：S0 正则修复 / S1 凭据表+端点 / S2 执行侧切换 / V47 收口 / S3 审计 / S4 路由+策略 / S5 开关后端 / S6 开关前端 / S7 清理+迁移 / S8 视图清理 / docs 回写，各一个 commit），message 中文，`feat(scope):` / `fix(scope):` / `test(scope):` / `docs:` 风格

## V50 发布安排（破坏性收口）

### 为什么不能只跑迁移

`PlatformModelConfigRepository` 有 **9 处** SQL 引用 `base_url`（`SELECT_COLS`、`findCurrentWithCredentialByCapability` 的 JOIN、`create`/`revise` 的 INSERT、两个 mapper），实体 `PlatformModelConfig` record 也仍有 `baseUrl` 字段。**这些代码改动必须先于迁移上线**，否则 DROP 之后所有读路径立刻 500。

### 四步发布（原计划的三步是错的，实测修正）

原计划让第 1 步「代码去掉全部 `base_url` 引用」，实测两条都不成立：

- **写路径不能先停写**：`platform_model_config.base_url` 是 `NOT NULL`（V7:19），停写后每次 INSERT 违约 → `DataIntegrityViolationException` → admin 建配置直接 409。
- **读路径不能硬切凭据**：存量行与 8 个测试夹具都可能没有配套凭据行（V46 之后、写入侧上线之前的窗口就会产生这种行），硬切让 baseUrl 变 null，运行时 502。

**第 1 步（代码，已完成）** —— 让凭据成为真相源，但保留兜底：
- 读路径改 `COALESCE(credential.base_url, config.base_url)`：凭据优先（D2），配置列兜底
- `PlatformModelWithCredential.effectiveBaseUrl()` 保留回落分支，注释写明它是过渡期必需
- 写路径 **不变**（仍写 `base_url`，仍 find-or-create 凭据）
- `PlatformModelConfigResponse` 与 `{Create,Update}PlatformModelRequest` 的 wire 形状完全不变

此步单独上线是安全的：凭据在生产中立即生效，无凭据的存量行照旧工作。

**第 2 步（校验，滚动部署完成后执行）** —— 见下方 SQL。

**第 3 步（V50 迁移）**

```sql
ALTER TABLE platform_model_config ALTER COLUMN credential_id SET NOT NULL;
ALTER TABLE platform_model_config ALTER COLUMN base_url DROP NOT NULL;
```

两条都可回滚（`DROP NOT NULL` / `SET NOT NULL`）。`base_url` 转可空是第 4 步停写的前提。

**第 4 步（代码 + V52）** —— 只有这一步才能真正去掉引用：
- 读路径去掉 COALESCE 的兜底分支；`effectiveBaseUrl()` 去掉回落
- 写路径停写 `base_url`；`insertHistory` 的 baseUrl 改由凭据提供（history 表自己的列保持 NOT NULL 不变）
- 实体 record 去掉 `baseUrl` 字段（构造点：`PlatformModelConfigController` ×2、`Seeder` ×3、mapper ×2、测试 ×3）
- 8 个直接插 `platform_model_config` 的测试夹具要改成同时插凭据行
- 之后 V52 `DROP COLUMN base_url`

**第 2 步（前置校验，必须在滚动部署完成之后执行）**

```sql
-- 必须为 0；非 0 说明有行未挂凭据，跑收口会失败
SELECT COUNT(*) FROM platform_model_config WHERE credential_id IS NULL;
-- 必须为 0；非 0 说明有人绕过写入侧改过 base_url，需先对齐
SELECT COUNT(*) FROM platform_model_config c
  JOIN platform_provider_credential r ON r.id = c.credential_id
 WHERE c.base_url IS DISTINCT FROM r.base_url;
```

迁移拆成 V50（可回滚的两条 ALTER）与 V52（不可逆的 DROP COLUMN），中间隔一次代码部署与观察窗口——合成一个会让可回滚的部分被不可回滚的部分绑死。

### 滚动部署的真实风险

V46 之后、第 1 步代码上线之前的窗口里，**旧实例仍在跑没有 find-or-create 的代码**，它新建的模型配置行 `credential_id` 会是 NULL，这些行会让 V50 失败。所以第 2 步的校验必须在滚动部署**完成后**执行，不能部署前跑完就直接发迁移。查出 NULL 行时按写入侧同样规则补挂：

```sql
UPDATE platform_model_config c SET credential_id = r.id
  FROM platform_provider_credential r
 WHERE r.provider = c.provider AND r.base_url = c.base_url AND c.credential_id IS NULL;
```

### 回滚

V52 的 DROP COLUMN **不可回滚**，发布前必须有可用备份，且第 1 步代码已在预发跑满一轮（原约定）。

## S7 发布安排（明文清偿 + 老 modal 下线）

### Flyway 做不了这件事

`user_settings` 的 `features.video.apiKey` 要迁成信封加密的 `ai_provider_key` 行，**加密需要 KEK 与 Java**，纯 SQL 迁移无法完成。飞书 `appSecret` 同理。

先例：`PlatformModelConfigSeeder` 是 `ApplicationRunner`（best-effort、不阻断启动）。S7 照此实现了 `LegacySecretMigrationRunner`（**已完成**），三条硬约束：

- **幂等**：video 按「该 account 已有 enabled 的 text `ai_provider_key` 行」跳过；飞书按「已有 `appSecretEncrypted`」跳过。Runner 每次启动都跑，可安全重跑
- **KEK fail-closed**：KEK 未配时**不迁移也不改动任何数据**，只记日志退出——绝不能在无法加密时推进（那会让 V51 清空时数据丢失）
- **可观测**：逐条记 accountId（**不记密钥值，连掩码也不记**）与结果计数，运维据此确认完整性

### 飞书 appSecret 用独立键，不原地替换

`appSecretEncrypted` 是新增键，`appSecret` 明文原样保留到 V51。理由：原地加密后读路径**无法区分「已加密」与「还是明文」**，试解密再回落是启发式的、不可靠。独立键让 `FeishuCredentialsRepository.resolveAppSecret` 的优先级明确——有密文就解密用，没有才回落明文；KEK 不可用或解密失败也回落明文并告警，不让导出功能整体不可用。V51 清空明文后回落分支自然失效。

### 两类不可迁的 video 形态

Runner 会跳过并留日志，**不产生不可用的密钥**：

- `provider=coze`：走独立协议、非 OpenAI 兼容，迁过去也调不通（`AnalysisByokResolver` 注释已说明）
- 缺 `baseUrl`：无法构造有效密钥行

这两类在第 2 步的校验 SQL ② 里列出，需人工确认这些用户是否还在用，再决定是否单独沟通。它们不阻塞 V51，但必须先看过。

### 发布顺序（四次动作，不能合并）

1. **迁移 Runner 上线**，不删任何东西：`features.video` 密钥 → `ai_provider_key` 行；飞书 `appSecret` → 信封加密。此时明文仍在，新旧双读。
2. **确认迁移完整**：

列名是 **`user_id`**（uuid），不是 `account_id`——`user_settings` 的定义见 database-bootstrap 的 `V1__java_backend_base_tables.sql:26-37`。

```sql
-- ① 仍有明文 video 密钥、却没有对应 text 密钥的账号数
--    必须为 0（或全部属于下面 ② 的不可迁形态）
SELECT COUNT(*) FROM user_settings s
 WHERE s.settings_type = 'analysis'
   AND s.settings_json->'features'->'video'->>'apiKey' IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM ai_provider_key k
                    WHERE k.owner_account_id = s.user_id::text
                      AND k.organization_id IS NULL
                      AND k.capability = 'text' AND k.enabled = true);

-- ② 不可迁形态（provider=coze 或缺 baseUrl）：Runner 会跳过并留日志，需人工确认这些用户
--    是否还在用。它们不该阻塞 V51，但必须先看过。
SELECT s.user_id::text,
       s.settings_json->'features'->'video'->>'provider' AS provider,
       s.settings_json->'features'->'video'->>'baseUrl'  AS base_url
  FROM user_settings s
 WHERE s.settings_type = 'analysis'
   AND s.settings_json->'features'->'video'->>'apiKey' IS NOT NULL
   AND (s.settings_json->'features'->'video'->>'provider' = 'coze'
     OR s.settings_json->'features'->'video'->>'baseUrl' IS NULL);

-- ③ 飞书：有明文但没有密文的行数，必须为 0
SELECT COUNT(*) FROM user_settings s
 WHERE s.settings_type = 'analysis'
   AND s.settings_json->'integrations'->'feishu'->>'appSecret' IS NOT NULL
   AND s.settings_json->'integrations'->'feishu'->>'appSecretEncrypted' IS NULL;
```

3. **站内通知**（经 identity `mail_outbox`），重点覆盖上一步查出的存量 BYOK 用户。文案要点：顶部设置按钮移除、模型密钥改在 AI 创作中心「模型密钥」页签维护、**已有密钥已自动迁移，无需重填**。通知先发，再进第 4 步——给用户发现问题的窗口。
4. **V51 + 老 modal 下线**：清空 `user_settings` 全部 secret 字段、`SettingsSchemaGuard` 拒键、删 `AnalysisSettingsModal.vue` 与顶部设置按钮、三孤儿就近安置（D18）。

### 不可逆点

第 4 步清空明文之后，若第 1 步有遗漏，那些用户的密钥**无法恢复**。故第 2 步校验必须返回 0 才能进第 4 步，且第 4 步发布前要有 `user_settings` 的独立备份。

### 已拍板（2026-08-25）

1. **通知与 V51 间隔 = 3 个工作日**。第 3 步发出通知后满 3 个工作日才执行第 4 步，给用户发现「我的密钥还在吗」的窗口。工作日不含周末与法定节假日——若通知落在周四，第 4 步最早为次周周二。
