## 4. 目标行为
### 4.1 用户流程
A加载配置/余额/工作台 → 退出成功 → 同步清A状态 → B登录 → 仅B初始化结果可显示；A旧响应即使最后返回也不弹toast、不改loading、不改URL。当前会话请求失败显示本域已有错误并允许显式重试，不自动重放写操作。
### 4.2 行为变化表
| 场景 | 目标 |
| --- | --- |
| 加载 | 当前账号显示加载态，私有旧值为空；无余额不能显示成上一账号数值 |
| 未登录 | 配置和余额清空、工作台登录引导；不发私有初始化请求；公开协议仍可读 |
| 无权限 | 保留真实401/403/409，前端不补开未获准身份，不改权限 |
| 空数据 | settings默认空feishu、积分null表示未加载/失败而成功0仍显示0；组织任务空列表用原空态 |
| 失败 | 当前ticket才更新错误；旧失败静默丢弃；不清新账号loading |
| 重复请求 | 同账号同epoch身份bootstrap合并；不同账号绝不共享promise |
| 刷新/离开 | 刷新重新认证和加载，不从storage恢复私有数据；卸载本地请求失效，其他活跃消费者的全局bootstrap不被误杀 |
### 4.3 状态定义
session为匿名(accountId=null)/账号就绪(accountId非空)，epoch非负整数；数据为未加载、loading、loaded-empty、loaded-data、error。旧请求stale是内部终态，不是UI错误码。字段清空必须包含error、saveError、saving、loading、loaded、分页、表单和选中资源。
### 4.4 状态迁移
任意账号变化→epoch+1→reset→新账号loading；loading→当前success或error；旧ticket完成→无副作用终止。相同id普通资料更新不增epoch；A→null→A产生两个epoch。当前组织/查询变化再增加本地revision；只有双重匹配可提交。首次mount不允许因默认状态重写深链。

## 5. 业务规则
### 5.1 输入规则
accountId只来自AuthUser.id，string或null，不从URL/表单接受；空串视无账号，缺字段/空白/非string认证响应不得作为有效新账号。epoch不从网络输入、不持久化。组织/门店/任务ID原样传递既有UUID契约，不改变枚举大小写。
飞书PUT只传integrations.feishu：缺省保持，密钥掩码保持，空串/纯空白按当前服务归一清除；UI空密钥框省略字段。appId/folderToken当前空框仍省略，不趁机改为清除按钮。积分为整数积分，钱包为整数分，null与0不同；金额格式化复用money.ts。
### 5.2 校验规则
发请求前核对ticket仍有效和必需账号；表单owner不匹配则清空并停止，不复制旧字段到新账号；只在当前owner加载成功后可保存。旧401不能退出新账号；当前保存失败保留非密钥输入，明文密钥提交取出后立即清空。不得新增自动重试写请求。
### 5.3 稳定业务规则
R79-01至R79-07逐一对应§1.3同行目标；所有卡还必须R79-08“每次续发请求前也验ticket”、R79-09“catch/finally不能覆盖新状态”、R79-10“取消不等于退款/回滚”。R79-08/09由TC79-01B/02B/04B/05B覆盖；R79-10由TC79-05B覆盖。
