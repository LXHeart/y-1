# 草场任务书 #49：商家主体成员账号单一模型收敛

> 来源：2026-08-27 用户在 #48 验收后提出「成员应是商家主体附属账号，而非收编已注册平台账号」的产品口径修订，两轮对话逐项拍板定稿。改动面调研 2026-08-27 完成（main 快照，含 #48 四 commit）。
> 状态：**2026-08-27 已实现并自验**（S1–S7 同日落地）。PRD §2.1 已回写为单一模型口径。
> 前置：#48（主体直建子账号）已落地——本任务在其之上收敛，且推翻 #48 两处当时刻意保留的决策（通路 1/2 原样保留、D5 邮箱冲突确认关联）。

## 目标

成员体系从「三条加人通路并存」收敛为**单一附属账号模型**：

1. **成员 = 商家主体的资产**：账号由主体直接创建（#48 已有），登录名带主体前缀（本任务新增），生命周期（建/停/删）全部由主体管理，不存在任何「把已注册平台账号收编为成员」的通路。
2. **登录标识从邮箱改为「账号名或邮箱」双标识**：子账号建号时**不填邮箱**，账号名 = `主体前缀-登录名`（如 `caoyuan-zhangsan`）；成员登录后可自行绑定邮箱（强制验证码），绑完可用邮箱登录。存量邮箱登录行为逐字节不变。
3. **删除动作补齐**：删除成员 = 解除全部成员关系 + 账号逻辑删除留痕（不可恢复，区别于可恢复的停用），前端强确认。

## 边界

- **不做**：纯门店经理子账号（D12）；物理删除任何行（邀请表/成员表/账号全留痕）；手机号通道；解绑邮箱；改 `StoreAuthorization` 隐式继承规则；#48 已交付的创建/停用/恢复/审核/重置密码行为变更。
- **不动**：`app_users` 共享表 DDL（占位邮箱方案正是为了绕开它，见 #48 D14 雷区）；edge 前缀路由（`/api/organizations`、`/api/me` 已是前缀级覆盖，新端点无需登记路由——但 identity 新 Controller 仍必须登记 `IdentityAuthorizationManifest`）。
- **留痕不删表**：`organization_invitation` 表与历史行保留（pending 迁移标 cancelled），便于审计追溯。

## 验收标准（整体）

1. **单一通路**：全代码库不存在任何「以已注册账号为入参挂成员」的端点或 UI；邀请流端点 404、前端无痕迹（仅迁移表留痕）。
2. **账号名闭环**：org admin 填登录名建出 `前缀-登录名` 子账号 → 拿到一次性密码 → 用账号名登录 → 强制改密 → 工作台绑定邮箱（验证码）→ 此后账号名/邮箱均可登录。
3. **存量零回归**：改动前存在的邮箱账号，登录、me、成员管理、AI 中心、任务流行为逐字节一致（对照 IT 锁定）。
4. **删除语义**：强确认删除后成员关系清零、账号 `deleted` 留痕、任何端点不可再登录、restore 409；停用/恢复行为与 #48 一致。
5. **存量清理**：非 owner 挂靠关系清零、owner 与纯门店经理不受影响、被清账号各收到一条站内信、pending 邀请全 cancelled。
6. **门禁全绿**：identity 全量 + edge + 前端 test/typecheck/build + CI。
