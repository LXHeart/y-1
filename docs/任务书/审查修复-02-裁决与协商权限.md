## 3. 业务规则

### R04：资格合法之外，必须与本案无利益冲突

- 原告 openedByAccountId 与被告 respondentAccountId 都不得担任本案审判官。
- 初审、自动开庭、手动自愈、补席、重开与重审共用同一冲突判定。
- 保留现有组织冲突、显式利益冲突、运营准入、等级/考试、暂停、垂类与见习配额规则。
- 排除双方后人数不足，应保留可重试的待处理状态，不能放回冲突候选，也不能提交半个面板。
- 服务层筛选和数据库面板插入都要执行关键回避约束。

### R05：确认者必须是相反业务方

| 发起业务方 | 确认/拒绝的合法主体 | 必须拒绝 |
| --- | --- | --- |
| merchant | 该报名的推荐官本人 | 发起商家账号、同商家其他管理者、其他推荐官 |
| recommender | 对该任务/门店具有当前管理权限的商家方 | 推荐官本人、其他推荐官、无该资源管理权限的人 |

业务方由服务端资源归属和 Identity 权威授权解析，不能相信请求体中的 role。confirmed 后的续传也要走相同授权，不得在幂等分支绕过。撤回仍沿用现有发起账号权限，不借本修复扩大权限。

### R06：开庭条件由一条规则决定

仅 court 案件可进入面板；满足以下任一条件才可把待质证案件变为 voting：

1. 质证截止时间已到；或
2. claimant_done_at 与 respondent_done_at 均已落定。

手动“重试/自愈”只保证工作流被启动/唤醒，不赋予提前跳过质证的权限。已 voting 的自愈保持幂等，已 final 不能重开；cs_direct 及 merchant_rejection 继续走既有专用流程。

## 4. 实施步骤

### C02-A：统一案件冲突上下文

读取案件权威双方账号，构造一个共享冲突上下文，在所有 draw/assign/repair/retrial 入口传递，不在不同入口各拼一份 exclusions。

存量 respondent_account_id 为空时，按既有履约授权接口补解析；解析失败保持可解释的待处理状态，不能把 null 当作“没有被告冲突”放行。不能用商家组织中的任意账号猜被告。

候选经远端资格回查后，在提交面板时再校验双方回避。新增迁移扩展现有数据库约束，不能覆盖旧迁移或移除原有资格限制。测试必须构造完整准入元数据，区分夹具失败与业务拒绝。

### C02-B：按业务方修复协商退出

使 resolveEngagementParty 的可信结果进入领域服务，或由共享服务在领域层重新解析。以 request.initiatedRole 与 responderParty 比较，账号比较只作身份和原发起账号约束。

同一套检查覆盖 confirm、reject 和 confirmed 后重入。错误保持已有错误信封及 403 语义；不得为了兼容 UI 把同侧操作当作成功。

### C02-C：让手动入口与工作流共用开庭转换

移除 fresh HTTP 分支未经条件校验直接分配面板的路径。手动入口可返回“质证中/工作流已启动”的当前快照，不应为了保留旧响应中的 voting 而提前翻状态。

将最终 evidence→voting 更新和面板/outbox 提交纳入一致的条件检查。双方 done、定时到期和手动重试同时发生时，最多提交一个完整面板和一次对应事件。

使用已冻结的 evidence_deadline/计时锚点，重试不能重新给 48 小时；时间判断采用统一的服务端口径。存量 open/空 deadline 必须有显式兼容分支，不能默认立即开庭，也不能影响已在 voting 的合法案件。

### C02-D：兼容与历史诊断

核对旧 AdjudicationControllerIT 中“手动调用立即 voting”的假设。应将测试前置改成已到期/双方完成，另保留未来期限的拒绝提前开庭测试；不能直接删旧测试来获得绿灯。

输出只读诊断：已有面板含双方账号、未来质证截止却提前 voting、同侧账号完成协商退出。未经事实核验，不自动删票、重判或回滚历史资金；本阶段保证新操作安全并提供可审阅的历史处置清单。
