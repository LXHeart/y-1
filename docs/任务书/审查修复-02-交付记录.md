## 1. 实际修改

### C02-A：统一案件冲突上下文（R04）

| 文件 | 变更 |
|---|---|
| `trust/judge/DisputeConflictContext.java`（新） | 案件冲突上下文 record：权威双方账号 + 涉案组织；`exclusionsWith()` 合并既有面板成员等额外回避。 |
| `trust/judge/DisputeConflictContextResolver.java`（新） | 读取案件构造上下文。存量空被告分三路：推荐官开案 → 被诉方=商家组织（组织级冲突，不视为「无冲突」）；商家开案 → 按**既有履约授权接口**（`MarketplaceEngagementAuthorizationClient.authorize`，以原告身份调用）补解析并经 `backfillRespondentAccount` 回填落库（仅 NULL 时写入）；解析失败（授权空/上游异常）→ 可解释 503「被诉方账号未能解析」，案件保持可重试待处理，绝不用商家组织任意账号猜被告。 |
| `AdjudicationActivityImpl` | `assignPanel` 抽签前经 resolver 取统一上下文，与既有面板成员合并进 `drawVerifiedPanel` 排除集。 |
| `AdjudicationController.retrial` | 发回重审重抽面板排除集 = 历轮全部成员 + 本案双方（共用同一冲突判定）。 |
| `JudgeRepository.insertPanelMember` | INSERT..SELECT 追加 `j.account_id <> d.opened_by_account_id AND (d.respondent_account_id IS NULL OR j.account_id <> d.respondent_account_id)`（服务层写库侧回避）。 |
| `V17__panel_party_recusal.sql`（新迁移） | `CREATE OR REPLACE enforce_panel_assignment_eligibility()` 追加当事人回避两条件；保留 V14 全部资格/组织/显式冲突限制，幂等可重放。 |

触发器生效的直接证据：隔离演练库播种历史数据时，直插原告席位被拒（`judge is not eligible for panel assignment`），须禁用触发器才能模拟修复前数据——见 diagnostics-output.txt 头注。

### C02-C：唯一开庭转换（R06）

| 文件 | 变更 |
|---|---|
| `HearingConditions.java`（新，adjudication 包） | 开庭条件唯一口径：双方 done 或冻结 deadline 已到；空 deadline 存量行锚点 = `created_at + 质证窗`（不默认立即开庭）。提供 `met` / `anchor` / `remainingSeconds`。 |
| `DisputeCaseRepository.startAdjudication(id, round, legacyWindowSeconds)` | guarded-UPDATE 追加开庭条件（与 HearingConditions 同口径，SQL `now()` 为统一服务端时钟）。这是 evidence/open→voting 的**唯一**转换：手动、工作流、到期、done 信号并发共用，至多一方胜出。 |
| `AdjudicationActivityImpl.assignPanelReactive`（新公开方法） | 从阻塞 activity 抽出反应式面板分配核心（抽签→组织复验→`Mono.defer` 事务：锁下复查+条件转换+面板+outbox）；activity `assignPanel` 委托 `.block()`，HTTP 手动入口直接订阅——**手动入口与工作流共用同一实现**。并发输家在 `transitionForAssignment` 重读为已 voting（round≥1）时幂等继续，不 503。 |
| `AdjudicationController.adjudicate` | 删除 fresh 分支的 `startFreshAdjudication`/`ensurePanelAndEvent`/`completePanelUnderLock` 重复实现。新行为：质证未到期且未双 done → 只唤醒工作流并返回当前快照（202，status 仍 evidence/open，含 workflowId）；已满足条件或已开庭（自愈）→ 走共用 `assignPanelReactive`。cs_direct/merchant_rejection 409、final 409、已 voting 幂等不变。 |
| `AdjudicationWorkflowStarter` | 质证计时锚定冻结 `evidence_deadline`（空 → created_at+窗口）：手动重试/工作流重启只等锚点剩余时间，**不重新给 48 小时**；已满足开庭条件 → 0 秒直进开庭。 |
| `MerchantRejectionFinalizer.promote` | deferred 晋升的继任 standard 案改走 `createCase` 落 court 通道 + `now+质证窗` deadline（原走 `createWithId` 落空 deadline，是唯一的活跃空 deadline 生产路径，已消除）。 |

## 5. 向 03 的交接（ApplicationLifecycleService 授权边界）

- `respondNegotiatedExit` 新增 `String responderParty` 入参（"recommender"/"merchant"），由 `TaskController.resolveEngagementParty` 服务端解析传入：报名推荐官本人 → recommender；`TaskResourceAuthorization.requireScope(caller, org, store, "manager")` 通过 → merchant。**03 调整事务编排时不得回退为只比较账号**——同侧判定 = `initiatedRole.equals(responderParty)`，且该检查必须保持在 confirmed 幂等续传分支**之前**（否则同侧可借续传绕过）。
- `requestNegotiatedExit(task, app, initiator, initiatedRole, reason)` 的 initiatedRole 同源；撤回 `cancelNegotiatedExit` 刻意维持发起账号口径（不借本修复扩权）。
- Trust 侧新增公共件：`HearingConditions`（开庭条件唯一口径）、`DisputeConflictContext(Resolver)`（回避集唯一来源）、`AdjudicationActivityImpl.assignPanelReactive`（面板分配唯一实现）。03 若触碰 `DisputeCaseRepository.startAdjudication`，注意其三参签名含 legacyWindowSeconds 且 guarded 条件即开庭规则本体。
