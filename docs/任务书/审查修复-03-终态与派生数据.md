## 3. 实施步骤

### C03-A：修无责退出的本地事务

当前 transactions.transactional 的括号只覆盖报名更新。将以下操作纳入同一本地事务：guarded 报名终态、名额回收、残留协商申请取消、对应 outbox。

只有本次终态转换的胜者能释放名额和发出终态事件。零行更新/名额回收失败必须明确处理，不能通过吞异常获得 200；重复调用也不能多次减少名额或重复发事件。

Finance RPC 保持在本地事务外。核对“资金已释放、本地终态未完成”的失败窗口，为本次退出保留可恢复的操作关联，复用现有 Saga/操作意图机制；不得为了原子性跨 HTTP 持有数据库事务，也不得只在内存里记补偿。

与交付确认、超时终结、商家取消并发时，仍然只有一个终结结果。保留原来的无提交、无已确认里程碑、体验未兑现和交付政策前置条件。

### C03-B：让售后退款只有一条完成路径

在发起退款时持久化裁定意图：关联售后单、退款操作 ID、裁定金额、原因、操作者及必要审计字段。以实际落库的裁定为准，不能在重试时用一个空 reason 或新随机操作 ID 重建。

在 01 的统一退款完成事务中接入售后收尾：

1. 验证成功结果匹配当前退款操作 ID/版本。
2. 更新订单已确认退款事实、必要的库存回补。
3. 若操作来源为售后裁定，关闭匹配售后记录并保存实际裁定/退款结果。
4. 写完成 outbox；任何本地一步失败均可整体重试。

即时 HTTP 成功、dispatcher 成功、对账恢复成功都调用此路径。普通消费者退款、过期退款或支付取消补偿不能误关闭不相关的售后单。

保留全额与部分退款差异：部分退款可以关闭本次售后，但不把订单误设为全额退款；后续剩余资金依照 01 继续处理。单订单售后记录的既有唯一性规则保持不变。

### C03-C：按责任原因修复声誉统计

不要继续将 status=refunded 等同于商家取消。用现有 exit_kind、确认事实和任务类型明确分类，所有读取入口采用一致口径。

| 记录类别 | 内容完成数 | 责任完成率分母 | 说明 |
| --- | --- | --- | --- |
| 正常内容履约已确认 | +1 | +1 | 分子和分母来自同一内容任务集合 |
| accepted 且未确认、仍进行中 | 0 | 0 | 接新单不应拉低完成率 |
| refunded + exit_kind=timeout | 0 | +1 | 推荐官有责未交付 |
| refunded + exit_kind=merchant_cancel | 0 | 0 | 商家责任取消，继续按既有规则豁免 |
| withdrawn + no_fault | 0 | 0 | 无责退出 |
| withdrawn + negotiated | 0 | 0 | 沿用 #97 撤销口径，不借本次修复修改政策 |
| 套餐推广任务 | 0 | 0 | 不属于内容完成率，保持单列统计 |

存量 exit_kind 为空的退款记录沿用已确认的旧兼容规则；如有证据表明是其他责任，进入可核验分类方案，不能把全部历史退款改成推荐官失败。

如需新增 timeoutCount 等字段，同步 DTO、前端类型和使用方，旧字段含义要清楚。保证无样本沿用现有返回口径，完成率在 0–1 之间；不要靠 clamp 掩盖错误的分子/分母集合。

检查等级评估、匹配排序和 Trust 资格回查实际使用的派生值，确保它们读取修正后的统计；不自动授予运营准入或更改等级阈值。

## 4. 历史异常的诊断与修复方案

输出只读、可重复运行的诊断，至少包含：

- 已 withdrawn/no_fault，但名额或 pending 协商申请尚未收口。
- 退款已确认成功，相关售后仍 open。
- exit_kind=timeout 被旧 merchantCancelledCount 统计豁免。

名额修复不能简单“每条异常减 1”，应按同一任务有效 reserving/accepted 占位事实和既有计数规则核对，避免与新接受的报名冲突。

售后修复须关联原裁定意图、退款操作/权威退款事实和已有 outbox。能唯一确定的才列出拟修复动作；无法确定原因、金额或操作者时保留待核验，不伪造历史裁定。

声誉主要是读时派生：先改查询；仅对实际存在的缓存/派生记录作必要重建，不改写源资金事实，不重发奖励事件。

若新增迁移，使用当前未占用版本。交付 dry-run 默认的诊断/修复脚本、幂等条件、执行前后不变量和隔离库演练证据；生产执行不在本阶段范围内。
