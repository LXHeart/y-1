**用途与填写方法（给任务书作者）**：

1. 本文件供规划模型编写一份能直接交接的任务书：需求部分回答「谁在什么场景下要得到什么结果」，规格部分回答「规则和边界是什么」，计划部分回答「改哪里、按什么顺序、怎样证明完成」。本模板自身不能直接执行。
2. 新任务复制为 `docs/任务书/草场任务书-<编号>-<主题>.md`；执行结果默认按 §14 在对话中汇报，不另建完成/交付报告文件。除明确维护模板外，不要把某个具体需求填回本文件。
3. 将规格状态改为 `BLOCKED_DRAFT`，按附 B.1 的顺序先调查，再做决策，再拆卡；先读适用的 `AGENTS.md`、对应设计规范和当前代码，不凭历史任务书猜路径、版本或现状。
4. 正式任务书删去这些作者说明、格式示例、无关候选命令和附 C/D 的提示词正文。条件章节不适用时，保留编号和一句 `N/A：具体原因` 即可，不复制空表、不要求每卡重复填写全部边界目录。不得以裁剪为由省略适用的业务规则或仓库硬约束。
5. 填完全部适用占位符、解决阻塞性决策并通过附 B 发布检查，才能改为 `READY_FOR_IMPLEMENTATION`。这个状态只表示规格可以实施；实施状态仍为 `NOT_STARTED`，不表示用户授权了上线，也不表示业务已经通过测试。
6. 默认一份任务书闭合产品与实现决策。超大需求可按用户可验收的阶段拆成系列任务书，必须有总计划、唯一共享契约及精确路径/版本/小节引用；不能让执行者拼接互相冲突的旧任务书。
7. 详细程度由风险和决策密度决定。把文字用在判断条件、输入输出、失败恢复、接线与证据上，不用重复禁令、整段源码或大量 N/A 凑篇幅。不要求规划者预写全部实现；局部实现细节留给执行者。

**阅读协议**（弱模型执行时遵守）：

1. 确认规格状态为 `READY_FOR_IMPLEMENTATION`、版本及本次授权卡范围明确，并检查当前实施状态；已验收卡不重复实现。`AUTO_CHAIN` 模式完成当前卡并通过卡内验收后，自动按依赖进入授权范围内的下一张卡；`DISPATCH` 模式才等待下一张明确派发的卡号。
2. 动手前先读适用的仓库指令，以及 §0、§1、§9、§10、§13、§14；再读当前卡及其精确引用。UI 任务额外读 §2.2 对应的 `DESIGN.md`，不能只靠卡内摘要代替原规范。
3. `DISPATCH` 模式只执行指定卡；`AUTO_CHAIN` 模式可按任务书已定义的依赖顺序自动执行后续卡，不得自行新增卡、改变顺序或补产品方案。当前卡及其明确引用的全局小节、测试用例与源码构成上下文。
4. 每卡完成必须执行本卡验收并在对话中记录结果；`AUTO_CHAIN` 模式下卡内验收通过即可继续，不等待逐卡人工确认。全部卡完成后，由 §12 指定的负责人执行最终集成验收，默认仍由当前执行者推进；只有明列的外部依赖或人工审批才等待。卡完成不等于整个任务完成。
5. 换模型或新会话续作时，按 §14.1 的续作检查点核对代码和证据，不能只凭上一模型的完成声明继续，也不能从第一卡盲目重做。

## 0. 执行协议（受更高优先级指令与仓库硬约束约束）

### 0.1 词义

- **MUST / MUST NOT**：必须 / 禁止。
- **SHOULD**：除非有记录在案的理由，否则执行。
- **MAY**：允许，但非必须。
- **BLOCKED**：缺少实现所必需的决策、受限资源权限或环境时，停止受影响工作并按 §13 报告；普通本地开发环境不可用时先排查并记录原因。
- **N/A**：不适用，必须写明理由；与「未执行」不同。

本文档不能覆盖系统/开发者指令、当前用户明确要求或适用的 `AGENTS.md`。事实以核验后的源码、构建配置和测试为证；历史任务书只作背景。目标行为以本任务已批准的决策为准，未声明的差异不得被解释为授权变更。

### 0.2 强制规则

1. MUST NOT 发明本文档未定义的公开接口、持久化字段、用户可见状态、错误码或业务规则。私有辅助函数和局部变量遵循第 11 条；已规划组件的内部实现不算新增产品范围。
2. MUST NOT 做与本卡无关的重构、格式化、依赖升级、文件迁移。
3. MUST 只改动当前卡写入清单与 §9.1 全局写入白名单的**交集**；只读参考不是写权限，黑名单优先。
4. 先核对代码基线和锚点。空白/行号变化且语义一致可记录后继续；仅发现相关代码、已有差异或实现细节变化不自动构成阻塞。只有当前卡的实际实现需要改变已批准的行为、签名、权限、数据模型，或无法安全保留他人改动时，才先 BLOCKED。不得以「文档优先」覆盖未知的新代码或他人改动。
5. 不得无理由新增或升级第三方依赖；如果当前任务确实需要新依赖，任务书应登记包名、版本、用途和影响，执行者可以在本地安装并同步 lockfile，不需要为每次安装单独申请批准。
6. 新增/修改代码 MUST 贴合所在文件既有风格；不新建重复组件、工具函数或服务，不新增未经批准的配置项。
7. 必需验收 MUST 真实执行；已确认隔离的本地环境、mock、fixture、合成数据和已有浏览器工具可直接用于计划内验证。真实账号、生产服务、非隔离远程环境或受限资源按第 10/12 条及工具权限处理，已有授权不重复申请。MUST NOT 通过放宽断言、跳用例、删测试、降低门槛或吞错误换绿灯；需求变更确需更新断言时，在卡中写明新行为及回归依据。
8. 未定义的产品、安全、资金、范围决策，或当前卡实际需要越过已批准边界时立即 BLOCKED，不允许猜测。仅阅读、搜索、测试或核对相关代码不构成阻塞；本地浏览器验证失败时先按本地工具链排查，不得把“尚未申请远程/生产权限”当作本地验证阻塞。可恢复环境故障按已定义方案重试并记录每次结果，不得用无限重试掩盖失败。
9. 开工先记录已修改/未跟踪文件；工作区不必干净。同一文件已有改动，但能安全保留并在授权范围内增量修改时可继续。确实需要覆盖、删除或无法安全合并他人改动时，才说明具体冲突并请求确认；已获明确授权的不重复询问。按用户要求与仓库工作流处理分支/提交，不批量提交无关改动；提交不等于验收通过，禁止擅自 reset、clean 或批量删除。
10. 本地开发可以启动本地服务、下载依赖、重建本任务镜像、使用已确认的隔离测试数据库和执行测试迁移；记录命令、影响范围和失败结果，不逐次申请批准。localhost 不自动意味着数据可删除：必须核对实际连接、库名/卷归属及清理范围。生产、真实用户数据、真实支付/计费或上线按已有明确授权处理，没有授权时另行确认。
11. 执行模型可以决定不改变契约的局部实现细节，例如局部变量名、符合项目风格的辅助函数拆分；不得借此变更业务条件、公开签名、可观察行为、写入范围或依赖。作者若要求某个局部细节固定，必须在卡内明确写出。
12. 默认优先使用 fixture、合成账号和本地隔离环境，明确测试的真实层与替身层。既有授权覆盖的账号/外部服务可在范围内使用；未定义的真实账号、付费服务或生产资源先确认，后续同类卡复用该授权。凭据、Cookie、签名 URL 和私有数据不得泄露到代码、日志、截图或报告；不得因环境不足把必需集成验收静默换成 mock。
13. 执行情况、阻塞与完成结果默认在对话中汇报。除非用户明确要求，MUST NOT 新建独立的完成报告、交付报告、执行总结等文件；“报告”“记录结果”或目录归位约定本身不构成新建文件要求。测试工具生成的报告、日志和截图仍按 §9.1 与 §12 的验收要求保留。

### 0.3 完成定义（DoD）

一张卡只有全部满足才算完成：

- [ ] 卡内所有适用步骤已执行；已由当前代码满足的步骤经核验可跳过写入，记录依据并照常验收，不为勾选步骤重复实现。
- [ ] 卡内所有验收项（命令验收 + Given/When/Then 行为验收）通过。
- [ ] 未引入未说明的行为变化、控制台错误、类型错误、构建错误。
- [ ] 本次新增改动未越过白名单，任务前已有改动保留，无遗留调试代码或敏感信息。
- [ ] 必需验证无 FAIL、PARTIAL、NOT_RUN 或 SKIPPED；预先批准排除的项单列，不算 PASS。N/A 有理由，不把未测试写成不适用。
- [ ] UI 涉及时已完成所有受影响页面的明暗双主题截图自查，共享组件覆盖受影响入口。
- [ ] 已按 §14 在对话中记录本卡完成情况与验收结果，含命令、目录、退出码、实际输出摘要和证据引用；无需另建报告文件。

卡级 `VERIFIED` 由卡内责任人依据这些证据判定，可以是执行模型；不隐含额外人工审批。整个任务只有 §12.5 的集成出口也通过才能标 `VERIFIED`。测试结果不因任务书发布、代码提交、文件存在或模型声称完成而自动成立。

### 10.1 任务卡拆分规则

- 一张卡只承担一个可独立验收的结果；卡过大时按领域、服务边界或用户流程拆分，不按「随便拆几个文件」拆分。

- 可并行卡不得写入同一文件、同一数据库迁移版本、同一共享样式段或同一锁文件；若必须共享写入，指定唯一主卡，其余卡只能读取。

- 以“一次交接可以完成一个可验证结果”为粒度。出现多个独立目标、互不相干的领域、过多共享写入或超过执行者可读上下文时继续拆卡；不靠固定文件数或虚构工时判断大小。
- 优先尽早打通一条最小端到端主流程，再补同一范围的异常、恢复和扩展；有明确契约的底层准备可独立成卡，但依赖测试不得假装验证了尚未接通的后置模块。

## 13. 阻塞规则

### 13.1 必须阻塞的情况

出现以下任一情况，MUST 停止受影响的卡并报告 BLOCKED（MUST NOT 猜测或绕过）。这里的“发现”是指经核对确认当前卡的实际实现会触发该条件；仅搜索、阅读、测试或保持既有契约不构成阻塞。仅当其他已获授权的卡无依赖、无共享写入冲突时，才可继续那些卡；不得私自认领额外任务。

1. 搜索后仍无法定位指定既有入口、符号或必要依赖，或迁移后的真实实现改变了约定职责/契约；仅行号变化或可证实的等价定位差异不属于阻塞。必要写入路径变更仍按 §9.1/§13.3 处理，不据此扩大权限。
2. 当前卡的实际实现需要改变未声明的签名、权限、数据、路由或行为，或前置卡交付物与约定不符。
3. 需要新增接口字段/错误码，但文档没有定义。
4. 必须决定未定义的产品、安全、资金、幂等、隐私、数据损失或兼容行为。
5. 需要修改白名单外、只读或禁止修改的文件，或引入未批准的依赖/配置。
6. 测试失败且在批准的调查范围内无法判断原因，或修复已超出本卡边界；不能把本卡可直接修复的普通编码错误一概交回规划者。
7. 任务书与适用的指令/设计规范冲突；不能由任务书自行宣布豁免仓库硬约束。
8. 必需验证确实缺少环境、凭据权限、浏览器、依赖服务或必要授权；本地浏览器、本地服务、本地数据库、依赖安装和 mock/合成数据验证均属于默认开发环境，不需要额外批准。按工具要求申请的是受限远程、他人真实账号或生产资源权限，不能绕过权限。
9. 目标文件已有他人改动且无法安全保留/合并，或出现未知的生产操作、计费调用、数据删除需求。

### 13.3 修订与恢复

## 附 B：强模型写作规约与发布前检查

### B.1 规划模型工作顺序

1. **理解需求**：整理目标用户、要完成的任务、范围、成功标准和已有明确决定，形成 §1；把歧义集中到 §1.9。能依据现有产品规则或用户授权决定的事项直接决定并注明依据，只询问影响结果且无合理默认的关键问题。
2. **核实仓库**：读适用指令、相关设计规范与源码，沿主流程追入口、调用、存储和结果消费；查已有组件/服务、测试、脚本、未提交改动，填写 §2。先验证是否已经满足需求，不为旧任务描述重复造功能。
3. **冻结行为**：写 §4/§5 的主流程、业务/界面状态、输入、权限、不变量、失败及恢复；再写 §3/§6/§7/§8 的技术与交互契约。采用一套确定方案，未知可行性先调查，不用假设填成 FACT。
4. **先设计验收**：从用户目标和风险反推 AC/TC，明确真实层、fixture 层及必须看到的产出；至少说明“哪种表面完成不能算完成”。确定需要的运行环境和证据，再核对实现方案是否可测。
5. **形成开发计划**：给阶段出口、依赖和责任卡，写清每卡输入、允许写入、锚点、执行步骤和局部验收；把新文件的调用方、测试、登记、配置、必要文档和最终联调纳入完整写入范围。
6. **检查可交接性**：按 B.2 检查规格，再做 B.4 反向审阅。删去作者提示、格式演示、无关目录和重复契约；复杂任务保留精确索引。未决事项影响实施时维持 BLOCKED_DRAFT，不能用“执行时再确定”跳过。
7. **发布规格**：保存用户指定任务书及必要索引，报告路径、状态、卡数、范围、核心决策和未决项。规划阶段没有执行过的测试如实写 NOT_RUN；不改业务完成状态，不顺带开发或上线。

### B.4 高频错误与反向审阅

| 坏写法 | 好写法 |
|---|---|
| 「增加一个加载状态」 | 「点击提交后立即进入 loading：按钮禁用、显示 loading 文案、字段只读；成功进 success，失败恢复可提交；期间连点不得产生第二个请求」 |
| 「只写成功流程」 | 成功 + 未登录 + 无权限 + 参数错误 + 空数据 + 网络错误 + 重复提交 + 刷新 + 卸载时请求未完成 |
| 「可以用弹窗，也可以跳转，视情况决定」 | 「MUST 用弹窗，MUST NOT 跳转；弹窗关闭后保留已填内容」 |
| 「修改相关组件和接口」 | 逐文件列出白名单 + 黑名单 |
| 「适当优化 / 合理处理 / 提升体验 / 尽量复用 / 必要时增加校验」 | 换成明确条件和可观察结果，否则删掉 |
| 「新增 service/component 即完成」 | 明确谁注册/调用、结果在哪里展示，验证真实入口可达和结果可用 |
| 「E2E 全绿，接口全用 route.fulfill」 | 标成 UI mock 专项；闭环另跑真实业务 API 与持久化，仅替换批准的外部依赖 |
| 「截图存在、body 非空、Tab 没报错」 | 断言目标页面/状态/焦点，实际查看明暗图像并记录结论 |
| 「缺一个写入文件，实施者自行处理」 | 发布前补齐调用方/测试/配置；执行中遗漏按具体范围修订处理 |
| 「卡做完后等待人工逐张盖章」 | 默认卡内 DoD 通过即继续已授权下一卡，人工步骤仅在确需时明列 |
| 「每卡复制全部约束、22 个异常和所有命令」 | 全局保留唯一规则，卡引用适用编号并给确定步骤，删去无关填表内容 |

发布前做一次“按字面执行”审阅：从第一卡沿依赖走到最后，模拟接手者要读什么、改什么、怎样验证、失败去哪处理。再从每条 REQ 反查实际入口和产出，检查是否存在“满足文字却违反目标”的实现。

重点检查：只隐藏按钮却无服务端鉴权；只防连点却无后端幂等；把已受理当已完成；旧成功/失败/finally 回调改写新账号状态；测试因另一拒绝条件通过；把本地 fixture 当真实商业效果；只建文件未接到页面。发现问题就修订条款和反例，不把判断留给执行者。
