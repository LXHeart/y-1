**用途与填写方法（给任务书作者）**：

1. 本文件供规划模型编写一份能直接交接的任务书：需求部分回答「谁在什么场景下要得到什么结果」，规格部分回答「规则和边界是什么」，计划部分回答「改哪里、按什么顺序、怎样证明完成」。本模板自身不能直接执行。
2. 新任务复制为 `docs/任务书/草场任务书-<编号>-<主题>.md`；不要把具体需求填回本模板。用户通常只需提供路径与需求，附 D 已给出默认决策授权和交付边界。
3. 将规格状态改为 `BLOCKED_DRAFT`，按附 B.1 的顺序先调查，再做决策，再拆卡；先读适用的 `AGENTS.md`、对应设计规范和当前代码，不凭历史任务书猜路径、版本或现状。
4. 正式任务书删去这些作者说明、格式示例、§12.4 的候选命令正文和附 D；自动生成并保留填实后的附 C，填写规则见该附录。条件章节不适用时，保留编号和一句 `N/A：具体原因`，同类不适用项可合并说明；不复制空表。不得省略适用规则或留下指向已裁剪内容的执行引用。
5. 填完全部适用占位符、解决阻塞性决策并通过附 B 发布检查，才能改为 `READY_FOR_IMPLEMENTATION`。这个状态只表示规格可以实施；实施状态仍为 `NOT_STARTED`，不表示用户授权了上线，也不表示业务已经通过测试。
6. 默认一份任务书闭合产品与实现决策。超大需求可按用户可验收的阶段拆成系列任务书，必须有总计划、唯一共享契约及精确路径/版本/小节引用；不能让执行者拼接互相冲突的旧任务书。
7. 详细程度由风险和决策密度决定。把文字用在判断条件、输入输出、失败恢复、接线与证据上，不用重复禁令、整段源码或大量 N/A 凑篇幅。不要求规划者预写全部实现；局部实现细节留给执行者。

## 0. 执行协议（受更高优先级指令与仓库硬约束约束）

### 0.1 词义

- **MUST / MUST NOT**：必须 / 禁止。
- **SHOULD**：除非有记录在案的理由，否则执行。
- **MAY**：允许，但非必须。
- **BLOCKED**：缺少实现所必需的决策、受限资源权限或环境时，停止受影响工作并按 §13 报告；普通本地开发环境不可用时先排查并记录原因。
- **N/A**：不适用，必须写明理由；与「未执行」不同。

本文档不能覆盖系统/开发者指令、当前用户明确要求或适用的 `AGENTS.md`。事实以核验后的源码、构建配置和测试为证；历史任务书只作背景。目标行为以用户明确要求或授权规划者作出的决策为准，未声明的差异不得被解释为授权变更。

### 0.2 强制规则

1. **契约与裁量**：MUST NOT 发明未定义的公开接口、持久化字段、用户可见状态、错误码或业务规则。可以决定不改变契约的局部变量、私有辅助函数等内部细节；不得改变业务条件、公开签名、可观察行为、写入范围或依赖。需固定的局部做法由卡明确。
2. **范围与复用**：只写入当前卡与 §9.1 白名单的**交集**，黑名单优先；只读参考不是写权限。不做无关重构、格式化、升级或迁移。沿用所在文件风格和已有组件/服务，不新造重复工具或未经批准的配置。
3. **基线与已有改动**：按 §0.4 核对后增量修改，能安全保留已有改动时直接继续；不能覆盖未知新代码或他人工作。分支/提交按用户及仓库要求处理，不批量提交无关内容，不擅自 reset、clean、删除或清理无关仓库、卷、容器与分支。
4. **本地开发权限**：可直接安装已登记用途/版本/影响的依赖并同步获准修改的 lockfile、下载工具、启动本地服务/浏览器、重建本任务镜像、使用已确认隔离的测试数据库及执行测试迁移，记录影响与结果。必须遵守根 `AGENTS.md`「本机资源约束」：单一应用栈、按需最小服务、重型任务串行；启动权限不等于允许全量起栈或与旧栈并行，具体计划填入 §9.3。localhost 不等于可删数据，须核对连接、库名、卷归属和清理范围。
5. **真实资源与隐私**：生产、真实用户数据、真实支付/计费、非隔离远程或受限资源按明确授权及工具权限处理；未获授权先确认，已有授权不重复申请。默认使用合成账号/fixture；凭据、Cookie、签名 URL 和私有数据必须脱敏，不进入代码、截图、日志或报告。
6. **验证诚信**：真实执行必需验收，证据边界见 §12.2。不得通过放宽断言、跳/删测试、降低阈值、关闭安全检查或吞错误换绿灯；批准的行为变更须同步断言和回归依据。不能因环境不足把必需集成验收静默换成 mock。
7. **失败与阻塞**：范围内普通编码错误和本地环境问题先自行排查；恢复重试须有边界并记录结果。只有 §13.1 的实质条件成立才停止受影响链路，不以只读调查、等价定位变化或尚未申请生产权限为本地开发阻塞理由。
8. **汇报与推进**：按阅读协议推进，执行结果和证据按 §14 汇报；独立报告文件的创建条件也统一见 §14。

### 0.3 完成定义（DoD）

一张卡只有全部满足才算完成：

- [ ] 卡内所有适用步骤已执行；已由当前代码满足的步骤经核验可跳过写入，记录依据并照常验收，不为勾选步骤重复实现。
- [ ] 卡内所有验收项（命令验收 + Given/When/Then 行为验收）通过。
- [ ] 未引入未说明的行为变化、控制台错误、类型错误、构建错误。
- [ ] 本次新增改动未越过白名单，任务前已有改动保留，无遗留调试代码或敏感信息。
- [ ] 必需验证无 FAIL、PARTIAL、NOT_RUN 或 SKIPPED；预先批准排除的项单列，不算 PASS。N/A 有理由，不把未测试写成不适用。
- [ ] UI 涉及时已完成所有受影响页面的明暗双主题截图自查，共享组件覆盖受影响入口。
- [ ] 已按 §14 记录本卡结果、实际命令与证据。

卡级 `VERIFIED` 由卡内责任人依据这些证据判定，可以是执行模型；不隐含额外人工审批。整个任务只有 §12.5 的集成出口也通过才能标 `VERIFIED`。测试结果不因任务书发布、代码提交、文件存在或模型声称完成而自动成立。

### 0.4 每卡开始前检查

1. 核对版本、授权、依赖卡与前置交付物；记录当前代码基线及相关已修改/未跟踪文件，不要求工作区干净。
2. 以 §2.7 为依据核对入口、稳定符号、调用签名和配置；前置卡的预期变化以其交付物为准。行号/空白或可证实的等价变化记录后继续，实质漂移按 §13 处理。
3. 运行本卡指定的针对性基线 V，记录已知失败；未执行写 `NOT_RUN`。已满足步骤记录依据，不重复写入。
4. 核对 §9.1 写入边界、§9.3 环境/隔离数据及必要权限；按 §0.2 准备环境，无法解除的实质缺口按 §13 报告。卡只补充自身特有的前置检查。

- 内容安全遵守 ADR-D16：L1 `ContentSafetyChecker` 是底线；L2 经 `capability=content_safety` 进入 `AiExecutionService`，当前不开放 BYOK，使用既有平台资助零积分分支但仍记录运行/预算/并发。流尾深检失败按现有 `deepCheck:false` 降级，不覆盖已经成功的生成结果。
- 公开分析请求不得携带浏览器指定的 provider 地址/凭据；受控 BYOK 设置与公开分析端点不同，复用当前受权配置、加密及服务端路由，不能把受控设置通道一并删除。
- URL/媒体代理/BYOK/第三方调用保留 trusted-host、协议/地址校验、挑战检测、session fallback、全量 DNS 检查、固定解析地址与原 hostname/SNI 等既有防护；不得放宽 SSRF/DNS rebinding 检查让联调通过。
- 生成/上传内容不视为可信 HTML；沿用当前 Markdown/sanitizer（如已有 DOMPurify 路径），不能直接将不可信字符串交给 `v-html`。不新增绕过服务端控制的浏览器直连提供者路径，既有受控预签名对象存储上传除外。

### 10.1 任务卡拆分规则

- 一张卡只承担一个可独立验收的结果；卡过大时按领域、服务边界或用户流程拆分，不按「随便拆几个文件」拆分。
- 卡依赖必须是有理由的：写明依赖的输出文件、接口、数据库结构或测试基线；仅因为「方便」不能声明串行。
- 可并行卡不得写入同一文件、同一数据库迁移版本、同一共享样式段或同一锁文件；若必须共享写入，指定唯一主卡，其余卡只能读取。
- 后置卡不能隐式修改前置卡的契约；契约变化必须新增返工卡或修订任务书版本，并重新通过附 B 发布检查。
- 每张卡按 §11 提供结果、依赖、读写边界、定位、执行步骤与验收；已定义内容用精确引用，特有约束就地补齐，不复制通用开工和汇报规则。
- 卡片划分支持多人或多模型交接。`AUTO_CHAIN` 只表示同一执行者可自动推进；「可并行」不等于必须启动子代理。没有独立执行单元时，按任务书列出的顺序串行执行，不得共享写入。
- 以“一次交接可以完成一个可验证结果”为粒度。出现多个独立目标、互不相干的领域、过多共享写入或超过执行者可读上下文时继续拆卡；不靠固定文件数或虚构工时判断大小。
- 优先尽早打通一条最小端到端主流程，再补同一范围的异常、恢复和扩展；有明确契约的底层准备可独立成卡，但依赖测试不得假装验证了尚未接通的后置模块。

出现以下任一情况，MUST 停止受影响的卡并报告 BLOCKED（MUST NOT 猜测或绕过）。这里的“发现”是指经核对确认当前卡的实际实现会触发该条件；仅搜索、阅读、测试或保持既有契约不构成阻塞。仅当其他已获授权的卡无依赖、无共享写入冲突时，才可继续那些卡；不得私自认领额外任务。

1. 搜索后仍无法定位指定既有入口、符号或必要依赖，或迁移后的真实实现改变了约定职责/契约；仅行号变化或可证实的等价定位差异不属于阻塞。必要写入路径变更仍按 §9.1/§13.3 处理，不据此扩大权限。
2. 当前卡的实际实现需要改变未声明的签名、权限、数据、路由或行为，或前置卡交付物与约定不符。
3. 需要新增接口字段/错误码，但文档没有定义。
4. 必须决定未定义的产品、安全、资金、幂等、隐私、数据损失或兼容行为。
5. 需要修改白名单外、只读或禁止修改的文件，或引入未批准的依赖/配置。
6. 测试失败且在批准的调查范围内无法判断原因，或修复已超出本卡边界；不能把本卡可直接修复的普通编码错误一概交回规划者。
7. 任务书与适用的指令/设计规范冲突；不能由任务书自行宣布豁免仓库硬约束。
8. 按 §0.2/§9.3 排查准备后，必需验证仍缺环境、凭据、浏览器、依赖服务或必要授权；说明已尝试与具体缺口，不能把正常本地准备一概转为审批，也不能绕过工具权限。
9. 目标文件已有他人改动且无法安全保留/合并，或出现未知的生产操作、计费调用、数据删除需求。

### 13.3 修订与恢复

- 规划者/负责人提供决策并更新受影响契约、文件清单、测试与任务卡，记录版本、依据和影响。用户已在会话中明确补充的决定有效，不要求重复确认；能在授权文档范围内同步时直接同步，不能写回时在交接记录保留原决定与待同步项。不得用笼统的“按你理解做”冒充具体产品决策。
- 执行者核对新版本、当前基线、前置交付物与新授权后恢复；旧版本验收记录与已有证据仍保留，不能把旧命令结果当成新版本验收。
- 仅环境恢复且行为/范围不变时，可记录恢复证据后继续，不强制修改产品决策；已改变的代码仍须重跑相关验证。
- 独立发现的无关缺陷列入报告，不扩大当前任务；需要修复时由负责人另开卡。

## 附 B：强模型写作规约与发布前检查

### B.1 规划模型工作顺序

1. **理解需求**：整理目标用户、要完成的任务、范围、成功标准和已有明确决定，形成 §1；把歧义集中到 §1.9。能依据现有产品规则或用户授权决定的事项直接决定并注明依据，只询问影响结果且无合理默认的关键问题。
2. **核实仓库**：读适用指令、相关设计规范与源码，沿主流程追入口、调用、存储和结果消费；查已有组件/服务、测试、脚本、未提交改动，填写 §2。先验证是否已经满足需求，不为旧任务描述重复造功能。
3. **冻结行为**：写 §4/§5 的主流程、业务/界面状态、输入、权限、不变量、失败及恢复；再写 §3/§6/§7/§8 的技术与交互契约。采用一套确定方案，未知可行性先调查，不用假设填成 FACT。
4. **先设计验收**：从用户目标和风险反推 AC/TC，明确真实层、fixture 层及必须看到的产出；至少说明“哪种表面完成不能算完成”。确定需要的运行环境和证据，再核对实现方案是否可测。
5. **形成开发计划**：给阶段出口、依赖和责任卡，写清每卡输入、允许写入、锚点、执行步骤和局部验收；把新文件的调用方、测试、登记、配置、必要文档和最终联调纳入完整写入范围。
6. **检查可交接性**：按 B.2 检查规格，再做 B.4 反向审阅。删去作者提示、格式演示、无关目录和重复契约；复杂任务保留精确索引。未决事项影响实施时维持 BLOCKED_DRAFT，不能用“执行时再确定”跳过。
7. **发布规格**：检查编号占用，按附 C 填写规则生成可复制的派发提示词并随任务书保存，安全增量更新 `docs/任务书/README.md` 等必要索引，保留已有改动。报告路径、状态、卡数、范围、核心决策和未决项。未执行测试写 NOT_RUN；不改业务完成状态，不顺带开发或上线。
