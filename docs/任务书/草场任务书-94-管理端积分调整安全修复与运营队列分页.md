## 4. 目标行为

### 4.1 调整积分（改后）

输入 → 前端校验（非零整数、边界）→ POST 带 operationId → identity `requireAdmin` + 参数校验 + 补键 → `adminAdjust` → finance 校验（D94-02/03/04）→ 落 `admin_adjust` 流水（含 operator）→ 逐级返回 → 弹窗关闭、列表刷新、余额可见变化。

### 4.2 行为变化表（要点）

| 场景 | 当前 | 目标 |
|---|---|---|
| amount=-5，余额 100 | 余额变 105、totalSpent−5 | 余额 95，earned/spent 不变，流水 type=admin_adjust、amount=−5 |
| amount=0 / 非整数 / abs>1e6 / NaN | 0 被后端 award(0) 吸收；NaN→解码 400 | 前端拦截不发请求；后端 400 |
| 超时重试（上游已提交） | 可能重复入账 | 同键 dedup，余额/流水只变一次 |
| 同键不同金额/账号 | 不可能发生（无键） | 409 幂等键冲突 |
| 扣减超过余额 | 退款语义静默加钱 | 402「积分余额不足」+ 前端明确文案 |
| 运营列表第 51+ 条 | 不可见 | 分页可达；高危/来源筛选服务端生效 |

## 5. 业务不变量

- 每笔调整恰落一行 `credits_transaction(type='admin_adjust')`，`balance_after` 与 `credits_account` 一致；`balance ≥ 0` 恒成立。
- `total_earned` 只被正向调整/奖励增加；`total_spent` 只被 consume/refund 改变；`admin_adjust` 负向不触碰两者。
- 同一 operationId 全局至多一行（既有部分唯一索引）；重复请求返回原 balance/transactionId。
- 未经 `requireAdmin`（identity）/ `requireService(IDENTITY_SERVICE)`（finance）的请求 401/403，且零副作用。
- 运营三列表 `total` 与同参数下全量行数一致（不含 limit/offset 影响）。
