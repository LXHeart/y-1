## 目标

PRD §六 筛选功能两项：

1. **批量通过/拒绝**：商家在报名列表多选后一次处理多条
2. **自动通过条件**：任务级设置「Lv4+ 自动通过」等等级门槛，满足门槛的报名自动接受

## 设计决策（已定死，勿另起方案）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **自动通过走 dispatcher（定时扫描），不改 apply 契约** | 镜像既有 `TaskReviewSlaDispatcher` 模式；完整复用单条 accept 守卫链（名额 claim、资金 Saga、权益冻结、contest 门闩 V17），apply 端点零改动 |
| D2 | **批量=逐项独立、允许部分成功**，响应回逐条 outcome | 名额/资金/状态在批内天然不齐；all-or-nothing 会在 saga 场景下无法实现 |
| D3 | **批量按传入顺序占名额**，靠前者优先 | UI 列表本就是声誉权重排序，商家所见顺序即接受顺序 |
| D4 | **资金型批量接受 = 派发预留 Saga 后返回 `reserving`**，前端用既有 `pollReservation` 轮询 | 与单条 202 语义一致 |
| D5 | `auto_accept_min_level smallint NULL`（1–5，null=关闭）；**开启后对存量 pending 也生效**（UI 提示） | 免做申请时间戳切割；商家开规则即处理存量，列表可预览 |
| D6 | **复用单条 accept 内部逻辑（重构提取），禁止复制第二套** | `ApplicationController.claimAcceptance` 链路必须单点维护 |
| D7 | 自动接受的通知**零新增**——`ApplicationAccepted` 已进通知中心（#28，2026-08-16 落地） | 复用即可 |

## Stage 1 — 任务字段：auto_accept_min_level

**Migration**（`ls` marketplace db/migration 取下一版）：`task` 加 `auto_accept_min_level smallint NULL` + `CHECK (auto_accept_min_level BETWEEN 1 AND 5)`。已发布任务修订可改（对后续扫描生效）。

**契约**：`CreateTaskRequest` / `UpdateTaskRequest` / revise 请求体加可空 `Integer autoAcceptMinLevel`（包装类型——Jackson 3 primitive 陷阱）；校验 1–5。`TaskController.toBody` 回显。draft/publish/revise 三条路径都要带上。

**测试**：字段往返、非法值 400、默认 null。

## Stage 2 — 批量端点（最大一块）

**重构先行（D6）**：把单条 accept 的「claim 名额 → 权益快照 → beginAcceptance/accept + outbox」提取为内部方法（返回结构化 outcome 而非 ResponseEntity），单条端点与批量端点共用；单条端点行为与响应**字节级不变**（既有 IT 是回归网）。

**端点**（挂 ApplicationController，同前缀 `/api/tasks/{id}/applications/...`，鉴权同单条：`requireUser` + `loadManageableTask`）：

```
POST /api/tasks/{id}/applications/batch-accept   { "applicationIds": ["..."] }   // 1–50 条，超限 400
POST /api/tasks/{id}/applications/batch-reject   { "applicationIds": ["..."] }   // 同上
```

**响应（逐项，D2/D3/D4）**：

```json
{ "success": true, "data": { "results": [
  { "applicationId": "a1", "outcome": "reserving" },
  { "applicationId": "a2", "outcome": "accepted" },
  { "applicationId": "a3", "outcome": "rejected" },
  { "applicationId": "a4", "outcome": "failed", "reason": "名额已满" } ] } }
```

**语义细则**：

- 逐项调用共享内核，单项失败（`该报名已处理`/`名额已满`/任务越界 404→该项 failed）**不中断**后续项
- 项与项之间**不共事务**（各自事务 + 各自 Saga 派发，镜像单条 `transactions.transactional(write).flatMap(dispatch...)` 结构；副作用派发必须在事务外——Reactor 陷阱见清单）
- 幂等：沿用请求头 `Idempotency-Key`，批内派生 `key:appId` 逐项传入；客户端重试同批走既有 replay 路径
- 名额在批内按顺序 claim（D3）；名额满后剩余项 failed「名额已满」
- batch-reject 复用单条 reject 内核（pending→rejected + outbox），同样逐项独立
- 前置状态守卫：仅 pending 可处理；非本任务/不存在的 appId → 该项 failed「报名不存在」

**Edge**：确认 RouteManifest 对 `/api/tasks/{id}/applications/**` 是前缀匹配还是精确路径；精确则补注册两条新路径（fail-closed，漏了就是 404）。

**测试**：batch-accept IT（混合：非资金 accepted + 资金 reserving + 已处理 failed + 名额耗尽后续 failed；顺序语义）、batch-reject IT、上限 50 校验、非 owner 404、单条端点回归（行为不变）、幂等重放。

## Stage 3 — 自动通过 dispatcher

新 `ApplicationAutoAcceptDispatcher`（taskcatalog，镜像 `TaskReviewSlaDispatcher` 结构）：

- `@Scheduled(fixedDelayString = "${marketplace.applications.auto-accept-poll-ms:5000}")`，配置开关 `marketplace.applications.auto-accept-enabled`（默认 true）
- 每轮：查 `status='published' AND auto_accept_min_level IS NOT NULL AND (application_deadline IS NULL OR > now())` 的任务 → 其 pending 报名 → 按声誉权重排序（复用商家排名列表的既有排序，不新造）→ 逐条判定 `effectiveLevel >= auto_accept_min_level` → 满足则调共享 accept 内核（D6）
- **等级来源必须复用 apply 门槛同一权威计算**（`reputationService.snapshot` / effectiveLevel），不得自算
- 守卫透传：名额满 → 停止该任务本轮（不是 failed，下轮再看）；资金不足 → Saga 补偿回 pending（既有语义），不再重试同一报名（记录日志即可，防死循环：补偿回 pending 后下轮又会试——**必须加冷却**：同一 application 补偿后跳过 N 轮或按 `updated_at` 冷却窗口，避免资金不足时每 5s 空转派发 Saga）
- 系统操作者：`reviewed_by_account_id` 置 null（先确认列可空；AcceptanceCommand 的 actor 若是 uuid 类型同样置 null 或系统标记，按 schema 实际类型定）；outbox 事件照常发（#28 通知自动达）
- 竞态安全：pending→accepted 本就是 guarded UPDATE，双副本重复扫描无害（第二写者 0 行）；dispatcher 本身无状态
- 关闭任务/cancelled/截止过期不扫（SQL 谓词已含）

**测试**：dispatcher 单测（达标→accepted、不达标→留 pending、名额满停、截止/关闭不处理、冷却生效）、与权益冻结（V21 快照）集成、资金型→reserving→补偿回 pending 不死循环。

## 验收标准

1. 商家多选 3 条报名批量接受：非资金任务 2 条 `accepted`、1 条已处理 `failed`，列表刷新正确，被接受推荐官收到站内通知（#28 链路）
2. 资金任务批量接受返回 `reserving`，前端轮询到最终状态；名额不足时靠前项成功、后续 `failed:名额已满`
3. 任务设 Lv4 自动通过 → Lv4+ pending 报名在数秒内被系统接受（reviewed_by 为空、权益快照冻结正确、通知送达）；Lv2 报名留 pending
4. 资金不足场景：Saga 补偿回 pending，dispatcher 冷却不空转
5. 既有单条 accept/reject IT 与 #28 通知测试零回归
