# 草场任务书 #74：争议小法庭重构（参照闲鱼）

- 编号: #74
- 日期: 2026-09-04
- 状态: 已出，待实现
- 性质: 2026-09-04 闲鱼小法庭调研（17 票 9 胜抢先达票 / 72h 举证对质 / 垂类专业评审 / 准入考试+见习 / 小二复核改判 / 无判例库=最大投诉点）对照 PRD §七的结构性重构。PRD §七已同日修订定稿，本任务书是其在 trust-service（及 marketplace/identity/前端连坐）的落地方案。
- 一句话目标: 把「单方举证 → 干等 48h 开庭等待窗 → 满窗计票」的争议流，改造成「通道自选 → 双方质证 → 垂类面板 → 抢先达票 → 客服终审三选 → 判例入库」的小法庭结构；客服直裁通道 5 天 SLA。

## 一、决策表（2026-09-04 六拍板，已定死）

| # | 拍板 | 内容 |
|---|---|---|
| D1 | 质证期 | **48 小时**；被诉方超时未答辩 = 放弃抗辩**仅标注不判负**，由面板综合裁量 |
| D2 | 投票规则 | **抢先 4/7 达票即终局**；投票理由**必填 ≥20 字**，终局后随判例脱敏展示 |
| D3 | 垂类匹配 | **硬配额**：涉案任务平台完成 ≥3 任务的审判官占面板 **≥4/7 席** |
| D4 | 审判官资格 | Lv5 直入；**或 Lv4+完成 ≥20 任务+准入考试及格**=见习审判官（≤2 席/面板，累计 10 轮投票无异常自动转正） |
| D5 | 判例库 | **登录可见+脱敏+不显示具体金额** |
| D6 | 通道选择 | 提异议方**自主选择**小法庭（质证 48h）或**客服直裁（5 天内处理完成）**；提交后不可改 |

派生决策（设计定死，随拍板连带，非新拍板）：

1. 质证期**复用原「开庭等待窗」48h 时隙**（现 `adjudication-window`），总资金 hold 时长不变（D-06 时序门控不受冲击）。
2. 质证期结束**自动开庭**；双方各点「质证完毕」可提前开庭（两标志齐 → 立即开庭，任一未点 → 窗口到点自动开庭）。
3. 垂类熟手池不足 4 人时**按可得数降级**并在案件记录 `matched_platform_count`，**不 503 卡死争议**（503 只保留给总池凑不齐 7 人的现状语义）。
4. 激励维持 D15/D18 平坦口径（积分每票 20 + 现金佣金默认关），**不与裁决方向挂钩**；自动考核只考弃权率/参与率，**不考投票方向**。
5. 客服终审三选：`maintain`（维持原判）/ `overturn`（改判）/ `retrial`（发回重审=重抽面板再投，复用既有重开轮次机制）。
6. 判例内容 = **结构化字段拼接**（任务类型+平台+争议焦点+双方主张摘要+裁决+投票理由摘要），v1 **不接 AI 生成**（AI 不参与争议终审是 PRD 红线，摘要拼接保持零 AI 介入）。
7. `merchant_rejection`（D-03 商家履约异议）**零改动**：仍直送客服终审+SLA 超时自动终局，不吃通道字段。
8. 通道在**开争议请求体**携带（`channel: court | cs_direct`，缺省 `court` 存量语义）；`cs_direct` 不进入面板/投票/质证。

## 三、卡片

> 依赖序：B → C → D 是小法庭主链（B 改时隙结构，C 改计票触发，D 改抽签分池）；A 独立可先行（客服直裁不碰主链）；E/F/G 相对独立。建议实现顺序 A → B → C → D → E → F → G。

### 卡 A：通道选择 + 客服直裁（5 天 SLA）

**背景**: PRD §7.1 拍板 D6。现状 standard 争议只有陪审一条路；merchant_rejection 已有「open 态直送客服终审 + SLA 超时自动终局」完整先例可照抄。

**改动点**:

1. **DDL（V13）**: `dispute_case` ADD `channel varchar(16) NOT NULL DEFAULT 'court'`（court/cs_direct）、`cs_due_at timestamptz`（cs_direct 受理时刻+SLA，court 空）。存量行默认 court 语义不变。
2. **开争议**: `OpenDisputeRequest` ADD `channel`（缺省 court，白名单校验）；`DisputeController.openOrDefer` 创建时落 channel 与 cs_due_at（`AdjudicationProperties` 新组件 `csDirectSlaHours` 默认 120，compact 构造守卫 `<1 → 120`；照 `disputeCooldownHours` 惯例 `0` 保留为禁用哨兵，秒级覆盖 `csDirectSlaSeconds` 照 `voteWindowSecondsEffective` 惯例）。服务断言路径（merchant_rejection）不吃 channel，强制 court 缺省。
3. **cs_direct 门禁**: `adjudicate` 端点对 channel=cs_direct 409（文案「客服直裁争议不进入审判面板」）；`castVote` 天然被 status≠voting 挡住，无需改。
4. **客服终审入口扩展**: `final-decision` 受理范围加 `("open".equals(d.status()) && "cs_direct".equals(d.channel()))`，走 forceFinalize 分支（与 appealed 同路，MFA 门禁同享）。
5. **SLA 超时自动终局**: 照 auto-finalize 先例**不新增内部端点滥用**——新增 marketplace 无关的到期扫描不可取（无调度基建），改为**终局兜底挂在查询侧不可行**。定死方案：cs_direct 开争议即启动一个轻量 workflow（复用 DisputeAdjudicationWorkflow 的 csAwait 轮询段：新 input 或独立 `CsDirectSlaWorkflow`，sleep(slaSeconds) 后检查未终局 → 调用 activity 自动终局，**默认裁决=维持系统核实结果 for_recommender**，照 merchant_rejection auto-finalize 语义，事件 DisputeFinalized 附 `auto: true`）。治理台列表把 cs_due_at 即将/已超时案件排前（查询排序字段）。
6. **通知**: 开争议事件载荷带 channel；identity `EngagementDisputed` 模板按 channel 分文案（cs_direct:「对方对履约结果发起争议并选择客服直裁，平台客服将在 5 天内裁决」）。
7. **前端**: 开争议入口（GrasslandWorkbench `#gl-disputes` 区块）加通道选择 radio（小法庭/客服直裁）+ 时效说明文案（小法庭:质证 48 小时+投票 24 小时；客服直裁:5 天内终局）；争议列表区分通道 badge。文案不改任何既有 48h 异议窗提示。

**测试**: IT——cs_direct 开争议 201 落 channel/cs_due_at；adjudicate 409；final-decision 在 open+cs_direct 可裁（MFA 过期 403 不变）；SLA workflow 到期自动终局 for_recommender 且幂等（已终局再触发不动）；court 缺省兼容存量。

### 卡 B：举证质证期（48h，复用开庭等待窗）

**背景**: 拍板 D1。现状 open 后干等 48h（adjudication-window）才可手动开庭，被诉方无结构化答辩位。本卡把死时隙变成活质证。

**改动点**:

1. **状态**: `DisputeCaseStatus` 新增 `EVIDENCE("evidence")`，位置 open→**evidence**→voting→decided→appealed→final。存量 open 案件兼容：开工/读取时把 open 视同 evidence（`fresh` 判定从 `"open".equals` 扩为 open|evidence）。
2. **DDL（V13 同卡 A 合并）**: `dispute_evidence` ADD `phase varchar(16) NOT NULL DEFAULT 'claim'`（claim=原告首轮/answer=被告答辩/rebuttal=原告补充）；`dispute_case` ADD `claimant_done_at timestamptz`、`respondent_done_at timestamptz`、`respondent_answered boolean NOT NULL DEFAULT false`、`evidence_deadline timestamptz`（=受理时刻+质证窗）。
3. **轮次规则（服务端强校验，409 人话文案）**: answer 仅被诉方角色可提交且每案至多一次；rebuttal 仅原告可提交且须已存在 answer、每案至多一次；claim 沿用开争议时提交。证据端点复用 `DisputeEvidenceService.submit`（加 phase 参数）+ `DisputeEvidenceController` 鉴权扩展到被诉方（现状仅当事方与面板/客服读，写侧加对方角色判定——被诉方身份经 authorizer 复验，同开争议口径）。
4. **质证完毕**: `POST /api/trust/disputes/{id}/evidence-done`（当事方各自调用，落各自 done_at，幂等）；双方齐 → 立即开庭；窗口到点 → 自动开庭。
5. **开庭驱动改造**: `adjudication-window` 语义更名为质证窗（配置键保留兼容名，新键 `trust.adjudication.evidence-window-hours` 同值默认 48，`adjudicationWindowSecondsEffective` 照抄改名）。开庭触发从「手动 adjudicate+窗口校验」改为 **workflow 前置质证段**：court 通道开争议即 `workflowStarter.start`，workflow run 首段 `sleep(evidenceWindowSeconds)`（或收到 both-ready signal 提前醒）→ 既有 runVotingLoop。保留手动 `adjudicate` 作自愈/重试入口（ensurePanelAndEvent 分支已有幂等），删除其 48h 等待校验（窗口改由 workflow 持有）。Temporal 确定性铁律不变：evidenceWindowSeconds 进 AdjudicationInput。
6. **缺席标注（拍板 D1:不判负）**: 被告未提交 answer 时，`assignPanel` 阶段把「被诉方未在质证期答辩」写入审判官可见快照（adjudication 端点 snapshot 附 `respondentAbsent: true`）；**不自动裁决**。
7. **通知**: `EngagementDisputed` 文案补质证截止时间（payload 带 evidenceDeadline）；新增 `DisputeVotingStarted`（=原 DisputeAssigned 语义，面板组建时双方收）已有模板可复用，勿重复建。
8. **前端**: `#gl-disputes` 区块扩争议详情时间线（质证中[含截止倒计时文案]→评审中→已裁决→上诉期）；被告答辩表单（文本+证据上传复用既有上传组件）；双方「质证完毕」按钮；缺席态不渲染惩罚性文案（「对方未答辩，等待审判官综合裁量」）。

**测试**: IT——evidence 态占活跃槽阻塞结算（DisputeChecker 连坐）；answer/rebuttal 轮次与角色 409 矩阵；双方 done 提前开庭（workflow signal）；窗口到点自动开庭；respondentAbsent 标注进快照；存量 open 案件 adjudicate 自愈路径不回归。

### 卡 C：抢先达票 + 理由必填

**背景**: 拍板 D2。现状满窗计票（sleep 完才 tally），rationale 可空。castVote 已每次投票即时 tally——只差「达多数即终局」的触发线。

**改动点**:

1. **抢先达票**: `castVote` 在 `tallyVotes` 返回 `tally.hasMajority()` 时，同事务后置：翻 `decided`（复用 `disputes` 既有 decide/recordDecision 路径）+ outbox DisputeDecided + **signal workflow**（新组件 `AdjudicationSignaler`：`workflowClient.newWorkflowStub(DisputeAdjudicationWorkflow.class, "adjudicate-"+id)` 发 `concludeEarly()`；Reactor 侧 boundedElastic 包裹，失败仅 WARN 不阻断——满窗 tally 是兜底双保险）。`DisputeAdjudicationWorkflow` 接口加 `@SignalMethod void concludeEarly()`，workflow 用 `Workflow.await(() -> concluded || 窗口到点)` 替代裸 sleep（信号到已完成 workflow 的投递异常一律吞掉）。
2. **平票重开不受影响**: hasMajority 为 false 时维持现流程（窗口到点 tally→下轮）。
3. **理由必填**: `CastVoteRequest` compact 构造校验 `rationale == null || rationale.trim().length() < 20` → IllegalArgumentException→400（文案「投票理由必填且不少于 20 字」）。**无 DDL 改动**（rationale 列已存在、存量可空行保留）。abstain 同样必填理由（弃权也是「实际投出」，判例要展示）。
4. **理由呈现口径**: 当事方/公开判例侧只见**脱敏聚合**（票数分布+每票理由摘要），不见审判官身份——沿用 D-10 redactor 与 `AdjudicationController` 快照脱敏注释的既有红线，个票 rationale 不进当事方快照（终局后经判例库卡 G 落地聚合呈现）。
5. **前端**: 审判投票面板（现状入口待查：judge 面板经治理台或工作台——实现时以 `JudgeController` 消费端为准）加理由 textarea 必填校验+字数提示。

**测试**: IT——第 4 票落库即翻 decided 且 DisputeDecided 事件同事务；signal 失败不影响满窗兜底终局；rationale<20 字 400；abstain 缺理由 400；3 票+窗口到点走原 tally 路径无回归。

### 卡 D：垂类硬配额抽签（涉案平台熟手 ≥4/7）

**背景**: 拍板 D3+派生 3。闲鱼按品类抽行家；草场对应物=涉案任务的目标平台。

**改动点**:

1. **marketplace 新内部端点（跨服务连坐）**: `GET /internal/marketplace/reputation/{accountId}/platform-completions` → `{ "xiaohongshu": 12, "douyin": 3, ... }`（口径=该账号 completed 履约按任务 platform 聚合）。鉴权同 reputation/level 端点（服务 principal）。
2. **争议侧拿平台**: 开争议时 authorizer 响应若不含任务 platform，扩 `MarketplaceEngagementAuthorizationClient` 响应体带 platform，DisputeCase ADD `task_platform varchar(32)`（V13）落库——抽签、判例库（卡 G）都吃它，避免事后跨服务回查。
3. **抽签分池**: `JudgeEligibilityService` 新方法 `drawVerifiedPanel(int size, String organizationId, String taskPlatform, int hardQuota, Set<String> excluded)`：先从「该平台完成 ≥3 的合格候选」抽 quota 人，再从通用池补齐（两池都过既有实时复验+组织冲突排除）；熟手池不足 quota → 有多少取多少并记录（派生 3，不 503）；总池不足 size → 维持现状 503。
4. **面板审计**: `dispute_panel_assignment` ADD `matched_platform boolean NOT NULL DEFAULT false`（V13）；assignPanel 落熟手标记；adjudication 快照附 `matchedPlatformCount`（治理台可核硬配额达成率）。
5. **抽签入口换新方法**: AdjudicationActivityImpl.assignPanel 改调 drawVerifiedPanel（panelSize=7、quota=4 均入 AdjudicationProperties：`panel-size` 已有则复用，`platform-quota` 默认 4，`platform-completions-min` 默认 3——三值可配，测试可缩）。

**测试**: IT——熟手池充足时 ≥4 席 matched；熟手池 2 人时 2 席+5 席通用不 503+快照计数正确；总池不足 503 不回归；V8 触发器（org 冲突/tier 门禁）对两池均生效。marketplace 侧端点聚合口径单测（含 0 平台账号）。

### 卡 E：准入考试 + 见习 + 自动考核

**背景**: 拍板 D4+派生 4。Lv5 池子撑不起随机抽 7 人（现状 503 风险）；闲鱼同款解法=考试+见习。**注意 V8 触发器连坐**。

**改动点**:

1. **DDL（V14）**: `judge` ADD `exam_passed_at timestamptz`、`admission_level varchar(16) NOT NULL DEFAULT 'full'`（full/probation）、`probation_since timestamptz`、`suspended_until timestamptz`、`suspension_reason varchar(500)`；新表 `judge_exam_question`（id, category, question, options jsonb, answer_index int, active bool, version bigint, created_at；治理台维护，UPDATE 即 version+1）；`judge_exam_attempt`（id, account_id, score int, passed bool, answers jsonb, created_at）；`judge_admission_audit` 的 action CHECK 扩值（'suspended','reinstated'——`ALTER TABLE ... DROP CONSTRAINT + ADD CONSTRAINT`，幂等写法照仓库惯例）。
2. **V8 触发器改造（同一 V14 内重建两函数）**: 资格条件从 `eligibility_tier >= 5` 改为 `(eligibility_tier >= 5 OR (eligibility_tier >= 4 AND exam_passed_at IS NOT NULL))`，并追加 `AND (suspended_until IS NULL OR suspended_until < now())`。**两处函数都要改**（panel_assignment + vote_eligibility），`idx_judge_drawable` 部分索引同步重建含 exam 通道。⚠️ 触发器重建期间在途案件不受影响（函数 CREATE OR REPLACE 原子）。
3. **报名与考试流**: JudgeController 报名门槛放宽为 Lv4（报名表单校验 `完成 ≥20 任务`经 reputation 端点——level 端点若不携带完成数，扩一个字段，比新端点省）；`POST /api/trust/judges/exam`（出题：active 题库随机 N=10；交卷：≥80 分及格 → 落 exam_passed_at+admission_level=probation+audit 事件；不及格冷却 24h 再考，attempt 留痕）。Lv5 报名照旧直入 full（ops_admitted 审批流不变）。
4. **见习席位 ≤2**: 抽签（卡 D drawVerifiedPanel）输出后补一条约束：面板内 admission_level=probation 者超过 2 时，超出的 probation 换通用池 full 候选重抽（循环至满足或池尽——池尽容忍 >2 并在快照记 `probationCount`，不 503）。
5. **转正**: recordVote 成功路径后轻量检查（同事务）：该 judge 去重 (dispute_id, round) 投票数 ≥10 且无低质标记（v1 无低质标记概念=只数轮次）→ admission_level=full + audit 事件。10 为配置 `probation-promote-rounds` 默认 10。
6. **自动考核**: 新增滚动考核 job——**不引入新调度基建**，挂既有 outbox 消费/启动扫?不行：定死用**数据库侧物化+按需计算**：治理台「审判官考核」页签打开时实时聚合 90 天窗口（分配面板数、实投数、弃权数、弃权率=abstain/已分配），对弃权率 >40% 且分配 ≥5 次的 judge 展示「建议暂停」按钮，运营点击 → 挂起 30 天（suspended_until/reason+audit 'suspended'；恢复 'reinstated'）。**v1 不做自动挂起的定时器**（运营确认制，避免误伤见习期波动），派生 4 的「自动暂停」降格为「一键建议+人工确认」——治理台可见即达标。
7. **通知**: identity 新增 `JudgeExamPassed`（DISPUTE 类，深链 /me/disputes 或审判台）、`JudgeSuspended`/`JudgeReinstated`（收件人=judge）。
8. **前端**: 审判官报名流加考试页（答题卡 UI，N 题单选+交卷评分+冷却提示）；治理台「审判官管理」页签扩：题库 CRUD、考试记录查询、考核看板（弃权率列表+建议暂停/恢复按钮+audit 时间线）。用户端审判台显示见习/正式标识。

**测试**: IT——Lv4+考试及格可报名可被抽签（触发器新分支）；Lv4 未考试被触发器拒（INSERT panel assignment 抛 23514）；见习 >2 换重抽；10 轮转正+audit；挂起后触发器拒票、恢复后可投；题库 version 递增幂等迁移重放。

### 卡 F：客服终审三选（维持/改判/发回重审）

**背景**: 拍板 5。现状 final-decision 的 decision 只收胜负值，客服无结构化「发回重审」出口。

**改动点**:

1. `FinalDecisionRequest` 扩为 `(action: maintain|overturn|retrial, decision?)`——maintain/overturn 需 decision（for_merchant/for_recommender），retrial 不需要。缺省兼容：老调用只传 decision 时视 action=overturn（治理台旧表单不破）。
2. `final-decision` 端点：retrial 分支——校验当前 appealed（retrial 只对上诉案件开放，escalated 兜底案件不允许重审，文案说明）；落 `dispute_appeal.status='decided', final_decision='retrial'`；案件回 `voting`、round+1、appeal_state 重置 none；**重抽面板排除上一轮全部成员**（excluded 集合传 drawVerifiedPool——派生自 dispute_panel_assignment 既有 round 行）；发 `AdjudicationReopened` 事件（模板已有）；重新 `workflowStarter.start`（固定 workflowId 幂等语义 ALLOW_DUPLICATE_FAILED_ONLY——**注意**：上一 run 已结束才会允许重启，确认上 run 已随 forceFinalize 分支前终止；若 workflow 仍在跑，先 signal 取消或用 `withStart` 新 run，实现时以 Temporal 实测为准并锚定在实现说明）。
3. 判决→终局链路（releaseHoldAndApplyDecision）不因 retrial 提前触发——回 voting 即回到「非 final 占槽」语义，资金继续 hold（D-06 语义自然延续）。
4. 治理台终审表单改三选一 radio（维持/改判[选胜负方]/发回重审），MFA 门禁不变。
5. **前端用户侧**: 争议详情时间线加「客服发回重审」节点。

**测试**: IT——retrial 翻 voting+round+1+新面板无旧成员+AdjudicationReopened 事件；资金仍 hold（DisputeChecker）；escalated 案件 retrial 409；老载荷（仅 decision）兼容为 overturn；MFA 过期 403 不回归。

### 卡 G：脱敏判例库

**背景**: 拍板 D5+派生 6。闲鱼最大投诉点=无判例库；草场做成差异化亮点。

**改动点**:

1. **DDL（V15）**: `precedent_case`（id uuid PK, dispute_id uuid UNIQUE, task_type varchar(32), task_platform varchar(32), dispute_kind varchar(32), focus varchar(200), claims_summary text, decision varchar(32), final_via varchar(16)——panel/cs/retrial, vote_summary jsonb, rationale_digest jsonb, created_at timestamptz）。**表内无 org/account/金额列**（脱敏由构造保证，不靠查询过滤——审阅时一眼可证）。
2. **生成时机与口径**: `publishFinalStatus`/终局事务内直接 INSERT（trust 本地表，不走 outbox）：focus=kind+platform+reason 前 80 字截断；claims_summary=原告 claim 与被告 answer 的 caption 拼接（各截 200 字，取自脱敏证据元信息，不取 raw）；vote_summary=各轮 `{forMerchant, forRecommender, abstain, matchedPlatformCount}`；rationale_digest=终局轮每票 rationale 截 100 字数组（**不含 judge 账号**）；cs_direct 案件 decision=客服终值、vote_summary 为空对象。

4. **前端**: 新页 `/precedents`（判例库）：卡片列表（平台+任务类型 badge、争议焦点、裁决结果色点、投票分布 mini 条）+筛选器+详情抽屉（双方主张摘要+投票理由列表）。入口挂主导航（**路径与入口位置见 §四 IA 待确认**）。DESIGN.md：用户端 Stripe 系，复用 `.glass-card`/`.badge` 全局层，禁硬编码新 token。
5. **不留原文**: 判例只存摘要与计数，不复制证据本体（V7 证据访问审计的口径外不扩散）。

**测试**: IT——终局即生成且 UNIQUE 幂等（retrial 多轮终局只一行，final_via=retrial）；cs_direct 案件生成口径；未登录 401、登录无 org 限定可读；filter/分页矩阵；构造性脱敏（表无身份列，快照断言字段集）。
