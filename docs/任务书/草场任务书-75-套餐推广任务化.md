# 草场任务书 #75：套餐推广任务化

- 编号: #75
- 日期: 2026-09-04
- 状态: 已出，待实现
- 性质: 把已建成的 commerce 线（ADR-D07：套餐/专属链接/核销/分账）接进任务流——发布任务新增第三类型「套餐推广」，推荐官接任务后生成专属链接，用户购买→线下核销→核销+48h 冷静期后自动分账提成。PRD §2.2/§8.3/§8.4/§九 已同日修订，本任务书是其落地方案。
- 一句话目标: 商家在任务表单关联一个已上架套餐发布「套餐推广」任务 → 推荐官接单（无资金预留）后生成专属归因链接 → 消费者经链接购买、到店核销 → 48 小时冷静期后自动三方分账，推荐官佣金入钱包可提现。

## 一、决策表（2026-09-04 五拍板，已定死）

| # | 拍板 | 内容 |
|---|---|---|
| D1 | 方向 | **套餐管理归经营、推广分发归任务**：套餐创建/定价/分成/上下架/核销留在「资金与经营 → 到店套餐与核销」；任务表单新增模式三「套餐推广」，发布时从已上架套餐中**关联一个**（任务表单不重复设定分成）。演化 2026-09-03「模式三独立形态不入任务表单」旧拍板 |
| D2 | 佣金形态 | **比例与每单固定额都支持**，套餐版本内二选一（`recommender_share_bps > 0` XOR `recommender_fixed_cents IS NOT NULL`）；存量版本一律视为比例形态 |
| D3 | 结算时序 | **核销 + 48 小时冷静期后分账**：核销即置 redeemed（商家立即见核销成功），资金继续托管；`split_eligible_at = 核销时刻 + 48h`，期满由 dispatcher 触发既有 split；冷静期内退款直接从托管全额退（零追扣），期满后退款走既有比例冲销 |
| D4 | 接单门槛 | **纯任务化**：只有对该套餐关联的进行中推广任务持有 accepted application 的推荐官才是有效归因人；推荐官侧手输套餐 ID 的自由分销入口下线 |
| D5 | 归因语义 | **重定义为末次点击单归因**：下单时链接所带 `recommender` 参数为唯一归因依据；未接任务/参数无效 = 自然流量（推荐官份额 0）；停写多推荐官 allocations（V37 表冻结增量、存量行保留供冲销读取）；治理台/商家侧人工改绑端点保留为纠错通道 |

派生决策（设计定死，随拍板连带，非新拍板）：

1. **资金模型不动 escrow**：套餐推广任务 `bounty_cents = 0` 且 `freebie_deposit_cents = 0`，`TaskFunds.isMonetary` 天然为 false → 接单走既有非资金路径（无预留 Saga、直接 accept）。**不改 ApplicationAcceptanceService**。
2. **每套餐同时至多一个进行中推广任务**：部分唯一索引强制；商家下架套餐时若存在进行中关联任务，**联动将任务转手动截止语义态**（不 409 打断商家）；任务结束不反向动套餐。
3. **归因与任务生命周期解耦**：订单金额在下单时快照进 `consumer_order`（既有机制），核销分账只看快照——任务结束/套餐下架**不影响已下单未核销订单的分账**；但结束后新下单的归因校验失败 → 自然流量（=推广资格随任务终止）。
4. **自购不计佣**：下单人账号 = 归因推荐官账号时，`recommender_account_id` 照落（审计可见）、`recommender_amount_cents = 0`（该份额归商家，平台费照常）；V26 金额和=价格 CHECK 仍成立。
5. **application 无新状态**：accepted 即长周期态（套餐推广任务无提交凭证/商家确认/refunded 环节——核销即真实消费，无申报造假空间）；任务终态后 application 保持 accepted 不迁移。
6. **佣金是套餐属性不是任务属性**：发布任务时不设定佣金，展示只读（来自套餐版本快照）。
7. **content_form / 平台等任务字段照用**：套餐推广任务仍是「做推广内容 + 挂专属链接」的形态（对齐抖音团购带货），任务大厅卡片自然融合。
8. 冷静期 48h 为配置 `commerce-split-cooldown-hours` 默认 48（照 `payment-timeout-seconds` 惯例，秒级 override 照 `voteWindowSecondsEffective` 惯例供 IT 用；**0 = 立即分账哨兵**，兼作回滚开关）。治理台可视化配置本批不做。
9. 契约层三选一沿用 `TaskCatalogFundingRules` 模式（DB 层 V45 已无 XOR 约束，不恢复）；新增分支：`commerce_package_id` 非空 ⇔ bounty=0 且 freebie=0 且无阶梯佣金。

## 三、卡片

> 依赖序：**A → B → C → D** 主链（A 建任务-套餐关联，B 的归因资格校验依赖它，C 的冷静期依赖 B 的单归因金额快照，D 收视图）。C 的 marketplace 侧改造其实不依赖 B，可与之并行，但集成验收按 A→B→C→D。

### 卡 A：任务模型——套餐推广类型与发布（marketplace + 商家/大厅前端）

**背景**: 拍板 D1。任务表单只有模式一/二，commerce_package.task_id 列闲置；要把「选一个已上架套餐发推广任务」接进任务 CRUD 与发布表单。

**改动点**:

1. **DDL（V52）**: `task` ADD `commerce_package_id bigint NULL`（IF NOT EXISTS）；部分唯一索引 `CREATE UNIQUE INDEX IF NOT EXISTS uniq_active_promotion_per_package ON task(commerce_package_id) WHERE commerce_package_id IS NOT NULL AND status IN (<进行中状态集合——按 `TaskStatus` 实际枚举列全，含 published 及其后未截止态>)`。同文件 ADD `commerce_package_version.recommender_fixed_cents int NULL` + `CHECK (recommender_fixed_cents IS NULL OR recommender_fixed_cents >= 0)`（二选一语义在服务层判，见卡 B；DDL 只挡负数）。
2. **契约三分支**: `TaskCatalogFundingRules` 加：`commercePackageId != null ⇔ bounty==0 && freebie==0 && 无阶梯佣金`（与既有两分支互斥，violation 文案「付费方式只能三选一：套餐推广任务不能设置赏金/押金/阶梯佣金」）；四个 Request record 各加 `commercePackageId` 字段并在紧凑构造器走规则；`TaskController.enforceFundingSingleMode` 合并终判扩展同语义。
3. **发布校验**: 创建/修订时 `commercePackageId` 非空 → 校验套餐存在、属同主体（organization）、`status='published'`（上架）；唯一索引冲突 → 409 文案「该套餐已有进行中的推广任务」。修订边界：任务已有 accepted application 后禁改 `commercePackageId`（与既有修订冻结同位实现）。
4. **回填关联**: 套餐推广任务创建成功时回填 `commerce_package.task_id`（列已存在）；任务终态（截止/关闭）时清空该回填（列可空，保持「进行中任务才占用」）。
5. **publishGate 核实**: bounty=0/freebie=0 时 `TaskPublishGate.enforce` 行为——若放行则零改动，若拦截则加 0/0 豁免分支（在锚点处注明实际行为）。
6. **审核流零改动核实**: 套餐推广任务照走 TaskReviewPolicy（IT 里验一单走通 published）。
7. **前端发布表单**: `MerchantTaskForm.vue` paymentMode 扩为三选（'commission'|'freebie'|'commerce'，文案「套餐推广」）；选 commerce 时：隐藏赏金/押金/阶梯区块，出套餐选择器（拉本主体 published 套餐列表：标题+价格+佣金形态展示「xx%」或「¥xx/单」+已关联标记；本主体无上架套餐时空态+引导跳「资金与经营 → 到店套餐与核销」）；提交体带 `commercePackageId`、bounty/freebie 恒 0。
8. **任务大厅卡片**: `RecommenderTaskHall.vue` 对套餐推广任务渲染类型 badge「套餐推广」+ 套餐摘要行（价格 formatYuan + 佣金「xx% / 单」或「¥xx / 单」）；接单动作复用既有报名/接受流（零改动，非资金路径自动生效）。

**边界**: 不动接单/预留代码（isMonetary false 路径现成）；不改套餐管理 UI；佣金计算归卡 B。

**测试**: IT——创建套餐推广任务 201（bounty/freebie 均 0、task_id 回填）；设赏金同时设 packageId → 400；同套餐第二个进行中任务 → 409；包不属本主体/未上架 → 400；有人 accepted 后改 packageId → 409；接单后无 funds_reservation 行、application 直接 accepted；任务发布过审走通 published；迁移重放幂等。

### 卡 B：归因重定义 + 佣金形态 + 推荐官推广入口（marketplace + 推荐官前端）

**背景**: 拍板 D4/D5 + 派生 4。现状归因=URL 参数直写无资格校验、allocations 多人分润、自由分销手输套餐 ID；要改为末次点击单归因 + 接单资格闸 + 自购不计佣 + 固定佣形态，并把推荐官入口换成「我的推广任务」。

**改动点**:

1. **佣金形态**: `commerce_package_version` 契约加 `recommenderFixedCents`（创建/改版可设）；服务层校验二选一（`fixedCents != null` ⇔ `recommenderShareBps == 0`），fixed 模式时 version 三 bps 仍满足和=10000 CHECK（推荐官 bps=0 为形式值）；商家套餐创建/改版 UI（MerchantCommerceCard）佣金输入从单一比例改为形态切换（比例 % 或固定 ¥/单）。
2. **下单金额快照**: `createOrder` 按形态算推荐官份额——比例：`price×bps`（现状）；固定：`recommenderFixedCents`（超价校验：fixed > price-平台费 → 创建套餐时 400）；平台费照 bps、商家=price−推荐官−平台。金额双 CHECK 不变。
3. **归因资格闸（末次点击 + 纯任务化）**: `createOrder` 取到 `recommenderAccountId` 后单查一次：`task_application(application.status='accepted') JOIN task(commerce_package_id=:pkgId AND task.status IN 进行中集合 AND task_application.account_id=:recommender)` → 命中才落归因；不命中 → `recommender_account_id` 置 null（自然流量语义，份额 0、商家+平台费照快照——先完成锚点 2.2 的自然流量核实）。
4. **自购不计佣**: buyer accountId == recommenderAccountId → 归因照落、`recommender_amount_cents = 0`（份额归商家，bps 快照照存，金额和 CHECK 仍成立）。
5. **停写 allocations**: `createOrder` 不再调 `replaceAttributionAllocations`（V37 表冻结增量；finance split 统一走单推荐官重载——多推荐官重载仅存量冲销路径读 V17 行继续可用）；`rebindAttribution` 改绑后也只写 V34 审计行、不写 V37 行（改绑语义=单归因纠错）。V34/V37 表与存量数据不删不改。
6. **推荐官推广端点**: 新增 `GET /api/v2/recommender/promotions`——返回当前用户 accepted 的套餐推广任务列表：`{taskId, taskTitle, taskStatus, packageId, packageTitle, priceCents, commissionDisplay（形态+数值）, stats: {orderCount, redeemedCount, pendingSettleCents（已核销未满冷静期）, settledCents（已分账入账）}}`（stats 聚合 marketplace consumer_order，权限=本人）。链接仍由前端拼 URL（模式不变，资格由下单侧服务端校验兜底）。
7. **推荐官前端**: `RecommenderShareCard.vue` 原位改造为「我的推广」列表卡（数据来自新端点）：每条任务出「生成推广链接」→ URL+QR（复用现有拼 URL/QRCode 逻辑）；**删除手输套餐 ID 输入框**；无接单时空态引导去任务大厅。位置保持在 PersonalSettingsModal「主页与分享」区，标题改「我的推广链接」。
8. **消费者下单页**: `ConsumerCommerceView.vue` 归因参数读取不变；无效归因静默降级为自然流量（不报错、不提示，页面照常可购）。

**边界**: 不动 split/退款/冷静期（卡 C）；不改 rebindAttribution 的权限模型与状态守卫；V34/V37 存量不动。

**测试**: IT——未接任务推荐官参数下单 → consumer_order.recommender_account_id 为 null、推荐官份额 0；接任务后下单 → 归因落列、金额快照正确；自购 → 归因落列、份额 0；固定佣套餐下单 → 份额=fixedCents、超额创建被 400 拒；任务截止后再下单（带原链接）→ 自然流量；promotions 端点只返回本人数据且 stats 聚合正确；createOrder 后 V37 无新行。

### 卡 C：核销 48h 冷静期分账（marketplace + finance 代码）

**背景**: 拍板 D3。现状核销即 attemptSplit、成功才 markRedeemed——商家核销反馈被分账 RPC 绑架，且核销后退款要追扣。改为核销即 redeemed、分账延迟 48h 由 dispatcher 触发；冷静期内退款从托管直退。

**改动点**:

1. **DDL（V52 同文件）**: `consumer_order` ADD `split_eligible_at timestamptz NULL`（IF NOT EXISTS）。
2. **核销解耦**: `redeem()` 流程改为 markRedeging → 直接 `markRedeemed`（核销码校验/过期守卫不变）+ 写 `split_eligible_at = now() + cooldown`；**不再内联 attemptSplit**。事件 ConsumerOrderRedeemed 语义不变（核销即发）。
3. **attemptSplit 条件改**: 仅 `status='redeemed' AND split_eligible_at <= now()` 可 split；兼容历史在途单：`status='redeeming' AND split_eligible_at IS NULL` 视为立即可 split（升级时刻卡在 redeeming 的旧单由 dispatcher 收尾）。split 成功后的完成标记沿用现状（split_operation_id + finance completeSplit），幂等键 `"commerce-split:"+orderId` 不变。
4. **dispatcher 扩展**: `pendingDispatch` 扫描状态集加 `redeemed`（SQL 里对 redeemed 附加 `split_eligible_at <= now()` 条件；redeeming 保持原样兼容）；分派分支 redeemed→attemptSplit。注意排序键 updated_at 会把未到期的 redeemed 单反复扫出——SQL 里过滤掉未到期行，避免空转。
5. **冷却配置**: `CommerceProperties`（或现有配置类惯例位）加 `splitCooldownHours` 默认 48，compact 构造守卫 `<0 → 48`，`0 = 立即分账哨兵`（IT 与回滚用）；秒级 override `splitCooldownSecondsEffective` 照 `voteWindowSecondsEffective` 惯例。redeem 时取配置写入 split_eligible_at（**快照进行，后续改配置不影响已核销单**——与 payment_deadline 同款语义）。
6. **冷静期内退款**: 核销后消费者自助退款守卫先核实（锚点 2.3）——本卡定死语义：**普通自助退款仅限未核销订单（现状若允许核销后退则收紧为 409 引导售后争议）；核销后退款只走 V36 售后争议成立 → attemptRefund**。冷静期内（未 split）退款命中 `refundFresh` 无 split 分支 → 从托管直退，推荐官零佣金、零追扣；冷静期满后退款命中 `refundAfterSplit` 比例冲销（既有）。两路径零新代码，IT 锁行为。
7. **CLAWBACK 流水补齐（顺手修）**: finance `refundAfterSplit` 对每个被冲销推荐官补 `appendEntry(CLAWBACK, -amount, engagement_ref=orderId)`（照 `EscrowLifecycleService.java:199` 写法），商家侧 accounts 冲销有无对应流水按同口径核实补齐。
8. **通知**: 冷静期满分账完成时推荐官收「佣金已入账」通知（identity 新模板 `SplitCommissionSettled`，深链个人设置弹窗/钱包；事件从 finance outbox 既有 split 完成事件挂——若 split 完成无事件则在 completeSplit 处补 outbox 事件，事件契约照 finance 既有 outbox 惯例）。

**边界**: 不改 finance split 入参/幂等/入账投影（除 CLAWBACK 流水与事件）；不动 wallet 表（不冻结余额——延迟 split 本身就是冻结）；不动 redeem 权限（store staff 核销不变）。

**测试**: IT——核销后立即：status=redeemed、split_eligible_at=+48h、无 split 行、商家界面语义（redeemed 即成功）；cooldown=0 哨兵：核销后下一轮 dispatcher split 完成、推荐官 wallet +COMMERCE_COMMISSION；期满 split：SQL 推进时间或直接把 split_eligible_at 改过去后 dispatcher 触发；冷静期内售后退款：全额退消费者、推荐官余额不变、无 CLAWBACK；期满后退款：refundAfterSplit 比例冲销 + CLAWBACK 流水行存在；历史兼容：手工造 status='redeeming' 旧行 → dispatcher 仍收尾；迁移重放幂等。

### 卡 D：商家视图与联动（marketplace + 商家前端）

**背景**: 拍板 D1 派生 2/3。商家要在套餐管理里看到推广任务与漏斗，下架套餐要联动截止任务。

**改动点**:

1. **下架联动**: `CommerceService` 套餐下架（published→draft/offline 路径）时，若存在进行中关联推广任务 → 将任务转手动截止态（复用既有截止端点逻辑/状态迁移，等价商家手动截止）+ 清空 `commerce_package.task_id` 回填；任务结束（截止/关闭/审核拒绝终态）同样清空回填。已下单未核销订单不受影响（金额快照在单上，IT 锁定）。
2. **商家推广统计端点**: 新增 `GET /api/v2/merchant/promotions`（本主体维度）：`{packageId, packageTitle, taskId, taskStatus, stats: {orderCount, redeemedCount, pendingSettleCents, settledCents, refundedCount}}`，权限照既有 merchant commerce 端点（requireScope org 级）。
3. **MerchantCommerceCard**: 套餐列表每条加「推广任务」区：有关联任务 → 状态 badge + 漏斗统计（下单/已核销/待结算佣/已付佣，formatYuan）+ 跳任务管理；无 → 「发推广任务」快捷入口（预填该套餐跳发布表单 commerce 模式）；已被其他任务占用时置灰提示。
4. **治理台**: 任务列表对套餐推广任务展示类型标识（照既有任务列表列扩展惯例，`src/ops` DESIGN.md 体系）；人工改绑入口保持现状（锚点：ConsumerCommerceView 改绑 UI 与 POST attribution 端点），列表注记「末次点击单归因，改绑为人工纠错」。

**边界**: 不动分账/退款；治理台不做冷静期配置界面（派生 8）。

**测试**: IT——下架套餐 → 关联任务转截止态、task_id 回填清空、409 不出现；任务结束后原链接下单 → 自然流量（与卡 B 测试互补：结束前已 paid 的单核销照分账）；商家 promotions 端点权限与聚合正确；已核销待冷静期订单在任务结束后照常 split。

## 四、集成验收

1. 全量门禁照仓库惯例（`./gradlew build` 或按服务 `:marketplace-service:test :finance-service:test`，含迁移重放测试）全绿。
2. 冒烟脚本（浏览器实测，照 #71/#72 惯例）：商家建套餐（固定佣 ¥5/单）→ 发布套餐推广任务（三选一表单）→ 治理台过审 → 推荐官大厅接单（无预留）→ 个人设置「我的推广链接」生成链接 → 消费者经链接下单支付 → 商家核销（立即成功）→（cooldown 调 0）推荐官钱包入账 → 余额提现走通。
3. 反向冒烟：未接任务推荐官手拼链接下单 → 自然流量；推荐官自购 → 零佣；冷静期内售后退款 → 全额退用户；下架套餐 → 任务联动截止。
4. 回归：既有 commerce IT（V26-V39 全链）与任务 IT（接单/预留/结算）零回归——非资金路径为纯增量。
