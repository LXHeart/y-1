## 2. C01-A：状态转换表与操作模型

### 2.1 订单履约状态（consumer_order.status）

| 来源（守卫） | 迁移 | 说明 |
| --- | --- | --- |
| createOrder | → `pending_payment` | 同事务快照 payment_deadline/payment_operation_id |
| markPaid（`status='pending_payment'`） | → `paid` | 支付成功；0 行=取消/他路先赢 |
| claimPaymentExpired / claimConsumerCancelled（`pending_payment`） | → `cancelled` | 终态；同事务释放库存一次；若财务已捕获由补偿收尾（§2.2） |
| requestRefund / requestDisputeRefund（`paid`/`partially_refunded`/`after_sales_disputed`） | → `refund_pending` | 预写 refund_operation_id + refund_requested_amount_cents |
| claimExpired（`paid` 或 `partially_refunded` 且未核销，到期） | → `refund_pending` | 全额退剩余（COALESCE） |
| markRefunded（`refund_pending`） | → `refunded` / `partially_refunded` | 累计退款落账；未核销全额退补库存 |
| markRedeemedWithCooldown（`paid` 或未核销 `partially_refunded`） | → `redeemed` | 快照 split_eligible_at/split_operation_id |
| **claimSplit（新增；`redeemed`/已核销 `partially_refunded`/`redeeming`，未结算，无 held）** | **→ `splitting`** | 分账原子占位；失败 abandonSplitClaim 归还 resting 态 |
| **markSplitCompleted（改；`splitting`/`redeeming`）** | **→ `redeemed`（有退款史回 `partially_refunded`）** | 落 split_completed_at（结算事实） |
| openAfterSalesDispute（`redeemed`/`partially_refunded`） | → `after_sales_disputed` | splitting 期间 409「结算处理中」 |
| rejectAfterSalesDispute（`after_sales_disputed`） | → `redeemed`/`partially_refunded` | 按退款史归还 |
| markCancelCompensated（新增；`cancelled`） | cancelled 不变 | 落 refunded_amount=price、refunded_at、`last_error='compensated_after_capture'` |

### 2.2 资金操作持久化（V62 `commerce_fund_operation`）

订单状态机承载 resting 态互斥；两类窗口无状态可承载，落操作行：

| 操作类型 | 幂等键 | 生命周期 |
| --- | --- | --- |
| `payment` | `commerce-payment:<orderId>`（订单行预写，不变） | 发出前 ensure（in_flight）→ 成功收尾（markPaid 同事务 succeeded）；取消胜出 → succeeded + 登记 compensation；失败 → 退避重试 / 4xx·8 次耗尽 → `needs_review`（对账待办） |
| `cancel_compensation` | `commerce-cancel-compensation:<orderId>` | 登记时订单行预写补偿键与全额；退款成功 → markCancelCompensated 同事务 succeeded + outbox `ConsumerOrderPaymentCompensated` |

恢复扫描（`CommerceDispatcher.dispatch` 末步 → `recoverFundOperations`）：租约认领（`FOR UPDATE SKIP LOCKED` + 60s 过期接管）到期未终态操作——payment 只捞订单已取消的行（未取消的由 pendingDispatch 驱动，无双路重发）；迟到执行者按 operation_id + `status IN ('in_flight','failed')` 守卫收尾，不覆盖后续结果。

### 2.3 分账互斥矩阵（C01-C）

| 先手 \ 后手 | 分账 claim | 售后开案 | 退款请求 | 暂扣确认 |
| --- | --- | --- | --- | --- |
| 分账 claim（splitting） | 第二执行者 0 行跳过 | **409 结算处理中** | **409 结算处理中** | **409 资金在途**（不虚报阻断） |
| 售后/退款先胜 | claim 0 行跳过，下轮按新状态处置 | — | — | — |
| 暂扣确认先胜 | claim 的 `NOT EXISTS held` 排除 | — | — | — |

Finance 侧同查证：refund 遇 split `processing` → 409 在途互斥、遇 `completed` → 冲销路径（`refundAfterSplit`）；split 遇 `refunded` 终态拒绝——两域各自在权威行上单边胜出，Marketplace 的判断不会被另一路调用绕过。

## 3. 净额分配（C01-D）

唯一服务端函数 `NetSplitAllocation.allocate(price, R0, M0, P0, cumulativeRefund)`：

- 退款按各方冻结占比整数分摊（向下取整）：`r=min(R0, C·R0/S)`、`m=min(M0, C·M0/S)`；尾差 `p=C−r−m` 由平台吸收；`p>P0` 时溢出转嫁商家（封顶冻结额）——与 finance `refundAfterSplit` 既有冲销算法同构，不引入新费率。
- 净分账 = 冻结额 − 各方退款分摊；**累计口径**保证同一总退款一次退成与分多次退成结果一致（比例分摊的规模不变性）。
- 原支付额、冻结金额不改写（不改原金额让旧校验「通过」）；退满净额为 0（防御性不进零额账本）。

例算（价格 10000，冻结 推荐 1000/商家 8500/平台 500）：

| 累计退款 | 推荐官 | 商家 | 平台 | 净合计 |
| --- | --- | --- | --- | --- |
| 0 | 1000 | 8500 | 500 | 10000 |
| 3000 | 700 | 5950 | 350 | 7000 |
| 5000（一次） | 500 | 4250 | 250 | 5000（=3000+2000 分两次） |
| 1 | 1000 | 8500 | 499 | 9999 |
| 9999 | 1 | 0 | 0（含平台溢出转嫁） | 1 |
| 10000 | 0 | 0 | 0 | 0 |

Finance 契约（`SplitCommand` 新增装箱可选 `refundedAmountCents`，缺省兼容旧调用方）：`totalAmountCents` 恒为原支付额；净额 = finance 权威 `refunded_amount_cents` 计算；三方合计必须等于净额；marketplace 申报累计退款与财务事实不一致 → 409 进对账；`partially_refunded` 支付态可分账、`refunded` 拒绝。零退款行为与旧契约逐字节一致（`validateSplit` 移除原额合计校验，净额校验在加载支付事实后执行）。

#97 结算后退款禁令保持：`requireNotSettled`（split_completed_at 闸门）三路径共用不变；结算后售后裁定退款 409 `settled_no_refund`（TC01-04a 尾段回归）。
