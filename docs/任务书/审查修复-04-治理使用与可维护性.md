## 3. 实施步骤

### C04-A：统一认证角色契约

登录和 /auth/me 通过共享构造逻辑返回一致的 user 对象，roles 来自 backend_role 权威集合，始终为数组；无角色返回 []。保留 id、email、username、hasEmail、displayName、legacy role、mustChangePassword 及现有 cookie/token 信封。

财务、风控、商家审核、内容审核、客服、平台管理员及多角色均测试。其它认证入口若复用相同 userInfo，应同步核对；普通用户不能获得后台角色。

前端登录成功后应直接具备角色判断所需数据。若确需额外加载权限，必须有明确装载/失败态，而不是先展示“无权限”；不能把“登录后强制刷新页面”当作修复。保留 authVersion、账号 epoch 和陈旧响应丢弃规则。

测试使用真实服务返回契约；不能仅把前端 mock 改成含 roles 来掩盖后端缺字段。角色撤销后 me 刷新也要正确反映，不改变现有路由对各角色的可访问范围。

### C04-B：隔离密码验证的重计算

将实际 passwordVerifier.verify 包在延迟执行的 Mono.fromCallable 内，在受控执行器上订阅；不能先同步调用 verify，再把结果 Mono.just 包起来。

执行器的并发和排队有边界，能复用现有配置则复用；专用线程资源应有生命周期管理。保留当前 Argon2 参数、bcrypt 升级、错误密码/未知账号的响应、账号停用判断、限流和成功会话签发顺序。

验证密码计算确实离开 Reactor 非阻塞线程。通过可控的慢验证场景确认普通接口仍可响应；负载结果记录实际测量，不编造吞吐目标，也不通过降低密码强度获得提速。

### C04-C：统一经营指标定义和权威来源

以下是本次修复采用的目标口径；沿用现有字段键以降低兼容成本，名称/说明应准确表达含义。如前序阶段已有明确、等价的版本化契约，复用并在交付中逐字段对应。

| 字段 | 目标含义 | 时间/金额规则 |
| --- | --- | --- |
| attributedSalesCents | 归因实付成交总额，属于毛成交口径 | 按成功支付事实及 paid_at 入窗口；待支付/未支付取消不计，后来退款不抹掉原成交事实 |
| refundedNetCents | 窗口内已确认退款金额 | 累加每笔真实退款的金额与发生时间；显示名改为清楚的“退款金额”，不能暗示它是净核销额 |
| pendingSettleCents | 当前仍应结、尚未结的已核销净佣金 | 使用 01 的净额分配；已确认退款减少义务；held/争议冻结不等于义务消失 |
| settledCents | 截至当前的实际已结佣金 | 读取分账/账本事实；合法历史冲正按事实处理，不按“订单有退款”整笔扣减 |
| netCommissionCents | 当前已结净佣金 + 当前待结净佣金 | 两项已包含有效退款/冲正影响，不再减一遍原订单佣金；注明包含待结部分 |

窗口内成交/退款是期间流量；待结/已结/净佣金是截至某时点的快照，分别清楚标注。统一 asOf、from、to 和 Asia/Shanghai 的展示口径，区间边界明确，不混用浏览器本地日期与数据库时区。

必须读取 01/03 提供的退款明细/完成时间或等价投影。consumer_order.refunded_amount_cents 是累计值，不能承担任意时间窗口的退款发生额；仅全额退款才写入的 refunded_at 也不能覆盖部分退款历史。

没有可靠历史发生时间时，提供数据覆盖范围或待核对标记，不伪造时间。需要 Finance 数据时用批量内部接口或幂等本地投影，不能跨库直读或每个订单一次 RPC。聚合使用一次一致快照/同一事实版本，避免并发分账时前后两次查询重复或漏算。

如新增投影，明确主键/操作 ID、重复事件处理、重建水位和追平过程；原始资金事实不改变。推广归因政策继续采用原冻结归因，不把该指标描述为增量收益。

不要加大超时、任意提高 limit、删 older 断言、标记 skip 或为测试新增专用生产 API。验证单跑、同类组合和模块全量均稳定。
