## 模型与关键技术真相

**现状（要改掉的）**：`OrgSubAccountService.grantMembership`——manager/staff 只写 `store_membership`、**不写** `organization_membership`；「主体成员」与「门店成员」是两个不相交的人群。工作台按「有无组织身份」分流（店长无组织身份→StoreStaffCard）。

**新模型**：建号一律 `organization_membership(role=member)` 入池；门店身份是池上的分配层（`store_membership`，manager/staff 按店）。挂靠端点以新形态回归：仅可操作**本主体池内账号**、ADMIN+ 门禁——与 #49 下线的外部挂靠（任意 accountId 挂入）不同。

**一店一店长闸**：`store_membership` 存在 `role='manager' AND account_id != :self` 的行 → 409。三处同闸：建号挂店、PUT 分配/调度、（同店改角色时排除自身）。**存量的多店长行不受影响**（闸只查新操作的目标店）。

### S3 · 实测（2026-08-28）

本地栈重建 identity（V48 自动执行）+ frontend，Playwright 走查验收清单十项 26/26：
单店三态/开分店/入池/分配联动/建号直配+调度/三路店长闸 409（冲突调度原子不动原挂靠）/移除回池/停用唯一店长（行保留标已停用）/店长登录门店工作台（无建号无审核）/纯池 member 主体台。截图在 bt-shots-52/。

实测踩坑（脚本层，均已消化）：①孤儿 store_membership（清理 SQL 漏删门店挂靠行）会挡唯一闸——清理必须连 store_membership 一起清；②首登改密路由闸只消费登录动作的内存态，整页 goto 会绕过（须 SPA 内导航触发）；③「从池中分配」开着的下拉 option 文本会污染 innerText 断言（要按表格行断言）；④停用≠解除挂靠，代管提示只在无人挂店长时出现。

- **建号入池**：`grantMembership` 改为「先插 org member 行，storeId+门店角色提供时再插 store 行」。请求体兼容现有 `{role, loginName, displayName, storeId?}`（member=不挂店；manager/staff=挂店）。
- **新端点**（StoreMembershipController，均 ADMIN+ + 主体内校验，outbox 留痕 `StoreMembershipAssigned/Removed`）：
  - `PUT /api/organizations/{orgId}/stores/{storeId}/memberships/{accountId}` body `{role: manager|staff}` —— 分配或调度（assign-or-move：已挂他店先删旧行再插，同事务；同店=改角色）。守卫：账号须为本 org 池内成员（有 org membership）、店属本 org、唯一店长闸。
  - `DELETE .../memberships/{accountId}` —— 移除回池。守卫：该行存在；无最后店长保护（决策 E）。
- **守卫调整**：删 D8①（最后店长不可停）。
- **审核流退役**：GET/PATCH `/member-review-required` 端点删除；建号 status 恒 active（`member_review_required` 列保留不删，回滚友好）。
- **列表增强**：GET `/memberships`（组织成员列表）增列 `storeId/storeRole/storeName`（LEFT JOIN store_membership+store）——主体成员表呈现「所属门店/未分配」。
- **V5x 迁移**（幂等）：
  1. `INSERT INTO organization_membership ... SELECT` 为仅有 store_membership 无 org 行的账号补 member 行（WHERE NOT EXISTS 防重放）。
  2. `UPDATE app_users SET status='active' WHERE status='pending_review'`（仅子账号占位邮箱域）。
- Manifest/edge：新端点在已登记 controller 下，无变更。

**测试**：新 IT 覆盖 PUT/DELETE 全守卫矩阵（403 非管理员含店长本人、404 店不在主体、409 店长冲突含同店改角色排自身、400/409 非 池内账号、assign-or-move 原子性、移除回池后可再分配）；建号挂店唯一闸；D8①废除回归（停唯一店长成功）；审核端点 404/410；迁移重放幂等（OutboxRepositoryIT 全量重放）；存量 IT 造数改 SQL 直插处同步补齐。

## 验收清单

1. 多店主体：建「暂不分配」成员 → 出现在池（所属门店=未分配）。
2. 门店区从池分配其为店员 → 行入表；主体成员表所属门店联动。
3. 调度到另一店当店长 → 原店消失新店出现，角色=店长。
4. 目标店已有店长 → 409 错误条，无静默变更。
5. 移除 → 回池（所属门店=未分配），门店区行消失；可再分配。
6. 一店两店长在任何路径（建号挂店/分配/调度）均被拒。
7. 店长登录：门店工作台无任何建号/审核入口，可停用/恢复本店成员。
8. 纯池内 member 登录：主体工作台受限视图，不炸。
9. 单店模式与 #51 口径一致（无建号/分配 UI）。
10. 停用某店唯一店长成功（D8①废除），店进入代管提示态。

## 已知边界（本轮不做）

- 成员同时挂多店（如需再议，D 决策推翻成本已知）。
- 自动降职/批量调度工具。
- 审核流的任何替代（店长建号已整体下线）。
