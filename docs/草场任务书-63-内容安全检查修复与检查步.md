## 1. 目标与背景

**一句话目标**:内容安全检查从「只读报告」升级为「可看、可修」——每条 finding 加查看/修复按钮、面板头部加一键修复(全部经 **diff 预览**后应用、应用后自动复查闭环);文章创作流在正文与配图之间插入**独立「检查」步骤**(软确认放行);同时按方案 C 把原创度两类 finding 的判定信息做实(不存任何原文)。

**用户拍板记录(2026-09-01,执行期不得更改)**:

| # | 拍板点 | 结论 |
|---|---|---|
| P1 | duplicate_content 的查看 | **方案 C:不存原文,从源头把信息做实**——复查落库带 platform(修「未知平台」缺陷)、同源降噪(命中本篇/同任务早期版本时明示)、跨任务撞文只显示元信息。原文展示留二期 |
| P2 | 修复是否收积分 | **不收积分**。走执行环 feature=null 免费分支(平台资助 0 积分),ai_run 照常留痕,预算闸/并发槽照常生效 |
| P3 | 修复应用方式 | **先预览 diff 再应用**(段级 diff,应用前原文不动) |
| P4 | 检查步形态 | **独立步骤 + 软确认**(「仍有 N 项提醒」confirm 后允许继续配图,advisory 姿态不变硬闸) |

**修复免费分支的模型配置**:新增 capability `content_fix`(治理台可单独配模型),**不进 BYOK 白名单**——恒用平台模型(与 content_safety 深检同款形态,「平台资助」语义自洽)。未配置时修复按钮点击返回明确错误,不静默。

### 4.2 同源降噪文案(`OriginalityChecker.duplicateFinding` 四分支)

判定顺序(取首个命中):

| 条件 | match 文案 | advice |
|---|---|---|
| matched.applicationId 非空且 == context.applicationId | `与本文早期版本相似(相似度 {X}%)` | 本文迭代产生的相似属正常;若需进一步差异化,补充新的素材与细节后再生成 |
| matched.taskId 非空且 == context.taskId | `与同任务早期版本相似(相似度 {X}%)` | 同上 |
| matched.createdAt 距今 ≤2 小时 | `疑似本文早期检查版本(相似度 {X}%)` | 同上 |
| 其余(跨任务撞文) | `与 {yyyy-MM-dd HH:mm} 的{平台显示名或"未知平台"}创作相似(相似度 {X}%)` | 与既有创作高度相似,建议重写结构并补充原创信息 |

- 平台显示名:前端 `OVERLAY_LABEL` 不覆盖全部,后端原样回 platform 原值,前端展示时未知/null 显示「未知平台」(现状逻辑不变)。
- X 计算不变:`(64 - distance) / 64` 四舍五入。

### 4.3 `low_originality` 重复片段算法

`fingerprint()` 内已有的 `frequency: LinkedHashMap<String,Integer>`(shingle→次数,**LinkedHashMap 保序**)基础上:
1. 取 `count ≥ 2` 的 shingle,按**首次出现顺序**遍历原文下标;
2. 相邻下标连续(i、i+1)且都入选 → 合并为连续片段;
3. 片段最短 4 字,不足丢弃;
4. 按 `(count-1) × 片段长度` 降序取 **top 5**;
5. 写入新字段 `Finding.fragments`(默认 `List.of()`);`match` 保持 `{N}% 文内重复` 摘要不变,advice 不变。
