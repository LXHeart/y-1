## 关键技术真相（改前缀不是改一列）

`account_username.username` 存的是**完整账号名**（`前缀-登录名`），未绑真实邮箱的成员在
`app_users.email` 还有一份派生占位值 `{账号名}@sub.grassland.invalid`（V44：email 是共享表
NOT NULL UNIQUE 列，identity 迁移不可 ALTER，故以占位值满足约束）。

**只改 `organization.account_prefix` 会让存量成员的登录名永远停在旧前缀上** —— 那是登录直接
坏掉的形态。故三处同事务重写：

1. `organization.account_prefix`
2. `account_username.username`（`旧前缀-x` → `新前缀-x`）
3. `app_users.email` 的**占位行**（`LIKE '%@sub.grassland.invalid'`）；已绑真实邮箱的成员邮箱**不动**

SQL 要点：`substring(username from length(:oldPrefix) + 1)` 只换开头前缀段，**不用 `replace()`**
—— 前缀 `milk` + 登录名 `milkman` 会把中间那段一起换掉。`LIKE '旧前缀-%'` 是第二道闸。

成员范围 = 该 org 的 `organization_membership` ∪ 门店属于该 org 的 `store_membership`（UNION 去重）。
owner 是注册用户、无 `account_username` 行，天然不受影响。

- 删商家侧 `PATCH /api/organizations/{id}/account-prefix`（GET 保留：多店建号表单仍需预览前缀）

## 偏离字面之处（已裁决）

**第 5 条**：初版实现为「单店且只有 owner」时才隐藏操作列，理由是多店期建的 `role=member`
成员不挂门店、删分店回落单店后若无条件隐藏将失去停用/删除入口。

**2026-08-28 用户拍板严格字面执行**：`showMemberActions` 恒为 `!singleStore`。代价由运营台
兜底——回落单店后这批成员的停用/删除由平台运营在治理台处置。「主体所有者」标记位于操作列
单元格内，随整列一起消失（单店无需自证身份）。

## 已知缺口（本轮不做）

改前缀后成员旧登录名立即失效，但系统**不会自动告知新登录名**（拍板 C 不动会话）。运营台有强
确认与影响面回显，线下通知由运营负责。如需站内通知/邮件，`OrganizationAccountPrefixChanged`
事件已在 outbox 里，接上 `MailTemplates`/`NotificationTemplates` 即可 —— 属独立一条。
