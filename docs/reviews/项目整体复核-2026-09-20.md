## 已确认问题

### R01 · P1：个人注销会删除组织草稿的关联来源

位置：[PersonalDataErasureRepository.java](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/compliance/PersonalDataErasureRepository.java#L143)。

`creation_draft` 和版本清理明确限定 `organization_id IS NULL`，但 `source_document`、`text_proposal`、`visual_plan` 等清理只按作者账号过滤。组织草稿因此可以保留下来，关联来源和制作上下文却被个人注销删掉。来源创建路径允许符合图文条件的组织草稿，未限制为个人草稿；创作主体所属组织不能从作者账号推定。

**隔离复现：** 在临时 PostgreSQL 18 容器加载实际相关建表迁移和当前 V86 触发器，创建带组织的草稿及其来源。执行从生产仓储直接提取的两条清理 SQL，来源 `DELETE 1`，草稿 `DELETE 0`，最终计数 `drafts=1 / sources=0`。未连接或修改本地业务库。

**建议：** 沿 `draft_id`/`plan_id`/`storyboard_id` 解析归属，统一清理、残留核对和派生对象登记的范围。组织父对象存在时保留其内容；真正孤儿行按可证明归属处理。检查同文件中其他仅按作者筛选的子资源，不能只补来源表。

**验收：** 同一账号拥有个人项目、组织项目和孤儿数据；到期注销后个人资源清除，组织项目及来源、计划、版本和关联对象可继续读取；其他账号不受影响。图文工作台默认关闭只能限制当前暴露面，不能代替存量数据保护。

证据：[数据库探针结果](../../test-artifacts/project-review-2026-09-20/database-probes.json)。

### R02 · P1：密钥创建者注销后，其他管理员无法维护组织密钥

位置：[V86 屏障函数](../../platform-java/services/intelligence-service/src/main/resources/db/migration/V86__serialize_personal_lifecycle_writes.sql#L16)、[组织密钥轮换与停用](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/ai/byok/AiProviderKeyRepository.java#L170)。

`ai_provider_key.owner_account_id` 表示创建者，组织密钥的权限归组织管理员。当前屏障对该表所有 UPDATE 按创建者生命周期判断，未区分 `organization_id`。创建者进入 frozen/erasing/erased 后，其他合法管理员的配置更新、轮换、停用也会被拒绝；而组织密钥本身按现有策略保留且仍可被组织使用。

组织成员或转让组织后的原 owner 可以进入注销，不能以“当前 owner 不能注销”的检查消除此路径。

**隔离复现：** 建立组织密钥、冻结创建者，再执行组织维度的 `enabled=false` 和密钥轮换 UPDATE，两次均收到 `account_closure_barrier`。触发器判断不受当前管理员身份影响。

**建议：** 区分资源所有权与历史创建者；组织凭据维护遵守当前组织权限，个人注销屏障只限制相应个人资源和被注销账号的新任务。新增纠正迁移，保留历史迁移校验约束。

**验收：** A 创建组织密钥并退出/注销，B 作为组织管理员仍可轮换、停用；A 的个人 BYOK 和新任务继续被拒绝；跨组织访问仍被拒绝。

证据：[数据库探针结果](../../test-artifacts/project-review-2026-09-20/database-probes.json)。

### R03 · P2：私有缓存跨标签页清理和登记上限均有遗漏

位置：[account-private-cache.ts](../../src/lib/account-private-cache.ts#L24)、[登记截断](../../src/lib/account-private-cache.ts#L70)、[清理及广播](../../src/lib/account-private-cache.ts#L75)。

两个独立问题：

1. `registerAccountKey` 不建立 BroadcastChannel 监听。即使接收页已经监听，发送页仍先从共享 localStorage 删除登记表，再广播账号 ID；接收页随后读到空登记表，无法清除自己独立的 sessionStorage。
2. 超过 500 个键时只截断登记数组，没有删除被移出的实际缓存；之后注销再也找不到这些键。

**真实浏览器复现：** Chromium 同一 context 的两张同源页面，分别验证“新标签页”和“预先已订阅”两种情况，清理后另一页仍保留私有 sessionStorage，登记表已为 `{}`。写入 501 个私有键后执行清理，只清掉 500 个，最早的私有值仍保留。这证明本地清理契约不完整，不据此推断服务端越权。

**建议：** 写入/会话初始化时注册监听；广播应携带可清理的键快照或使用各标签页的独立登记，避免依赖已被删除的共享记录。登记淘汰应同时清理实际值，或采用不丢所有权信息的存储设计。

**验收：** 双页面真实 sessionStorage、预订阅/未订阅、多个账号、501 个键、重复清理；主题和其他账号数据均保留。

证据：[浏览器探针结果](../../test-artifacts/project-review-2026-09-20/frontend-probes.json)。

### R04 · P2：页面卸载后，迟到响应会重建资金轮询

位置：[useEngagementExitFunds.ts](../../src/composables/useEngagementExitFunds.ts#L39)。

销毁时仅 `stopPolling()`，没有失效在途请求或清空目标。`refresh()` 的请求返回 pending/retry_wait 后，仍可调用 `schedulePollIfNeeded()` 创建新的定时器。离开页面后会继续发送资金状态请求；KeepAlive 失活和页面不可见也没有对应暂停接线。

**隔离复现：** 在真实 Vue effectScope 中发起 deferred 请求，先 `scope.stop()`，再返回 pending。记录到卸载后新增 1 个定时器，触发其回调又发起 1 次查询。该探针直接执行现有 composable，未访问后端。

**建议：** 生命周期销毁时标记 disposed、递增请求代次并取消只读请求；回包和调度前都检查有效性；按组件使用方式补失活/可见性暂停，并避免慢请求下轮询重叠。

**验收：** 请求中卸载、隐藏、KeepAlive 切页、切换目标、慢于轮询周期的响应，均不得产生游离定时器和旧状态写回。

证据：[轮询探针结果](../../test-artifacts/project-review-2026-09-20/polling-probe.json)。

### R05 · P2：生命周期门禁不能发现整条漏登记

位置：[check-lifecycle-contracts.ts](../../scripts/quality/check-lifecycle-contracts.ts#L149)、[现有契约测试](../../tests/contracts/lifecycle-registration.contract.test.ts)。

检查器只遍历登记簿里的条目，检查必填字段、重复、测试路径和 producer 类名；没有从实际迁移或事件生产代码提取清单作差集。完全遗漏的新表/新事件不会进入检查。`ignoredReason` 和声明的部分派生引用规则也未真正验证。CI 注释“新增持久资源/事件漏登记在此失败”高于实现保证。

**隔离复现：** 复制登记簿到本地证据目录，移除实际存在的 `ai_run` 和 `DeliveryDeadlineExpiring` 整条记录，再调用原检查器；仍返回 `violations=[]`，资源 17、事件 30，甚至仍满足现有数量下限测试。

**建议：** 建立迁移表/事件清单与登记簿的双向核对，允许显式、有说明的历史豁免；测试新增真实资源却未登记、删除整条登记、生产者与消费者不匹配等反例。逐步覆盖全表时明确基线和增量规则。

证据：[登记删除探针](../../test-artifacts/project-review-2026-09-20/registry-probe.json)。

### R07 · P3：共享 HTTP 错误解析丢失纯文本消息

位置：[grassland-http.ts](../../src/composables/grassland-http.ts#L20)。

`readErrorDetails` 和 `readError` 先调用 `response.json()`，解析失败后再调用同一 Response 的 `.text()`；响应体已被消耗，文本回退失败。使用真实浏览器 `Response('upstream unavailable', {status:503})`，函数返回 fallback，丢失原错误。大量只提供 `json()` 的 mock 无法检出这个行为。

**建议：** 一次读取文本后尝试 JSON 解析，或明确 clone 策略，并保留机器错误码、状态码与有界安全的显示文本。增加真实 Response 的纯文本、错误 JSON、空体和标准信封测试。

证据：[浏览器探针结果](../../test-artifacts/project-review-2026-09-20/frontend-probes.json)。
