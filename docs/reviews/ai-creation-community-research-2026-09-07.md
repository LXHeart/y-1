## 结论

九平台共用生成、素材和项目基础设施的方向合理。社区案例进一步支持：平台差异应落实到输入事实、内容结构、制作方式、交付字段和发布状态。

最值得增加的是“已有内容直接加工”的完整路径，包括原文排版、实拍选图、自有视频剪辑；同时把图卡与文章关联、长文资料依据和平台发布素材包做完整。自动发布适合在这些基础能力完成后分平台接入。

上轮发现的大众点评默认好评、知乎虚构资历诱因、独立视频平台信息遗漏等问题，仍应优先处理。本次还确认了非首张图卡单独重试时被当作封面策划的问题，见第三节。

## 一、GitHub 实现中值得借鉴的部分

### G1. RedInk：逐页策划、封面参考与部分结果恢复

项目：[HisMax/RedInk](https://github.com/HisMax/RedInk)。

**已核对实现：** 先生成封面，再将封面图片作为后续页面的参考；同时传入完整大纲和原始主题。按页索引合并已有图片，区分 `draft`、`partial`、`completed`，支持读取历史文件和单页重试。[图片编排](https://github.com/HisMax/RedInk/blob/427efb1da0e90d0343debc7bee77142f556da813/backend/services/image.py)、[历史图片合并](https://github.com/HisMax/RedInk/blob/427efb1da0e90d0343debc7bee77142f556da813/backend/services/history_image_merger.py)。

**对你的启发：** 封面应与整组内容共同策划，每张图有独立的信息任务。已成功的图片应被项目引用；失败后重试缺失页，并保留原页身份、事实、风格和顺序。图像参考是否可用取决于实际模型及适配器，不能只增加一个前端开关。

**使用反馈：** [Issue #62](https://github.com/HisMax/RedInk/issues/62) 报告中文错字，以及网络错误提示下已有部分图片成功的情形。这是特定模型和环境的用户报告，没有在本机复现，不能据此给所有图像模型的中文能力下结论。它提供了两个有价值的验收场景：图中文字核对、部分成功后的恢复。

### G2. guizang-social-card-skill：内容策划与可检查的排版

项目：[op7418/guizang-social-card-skill](https://github.com/op7418/guizang-social-card-skill)。

**已核对实现：** 内容与图片素材先组成逐页方案，再通过 HTML/CSS 和 Playwright 导出图片。页面可以承担封面、对比、清单、流程、截图证据等不同任务。校验脚本检查溢出、页脚碰撞、字号、标题间距等。[内容策划](https://github.com/op7418/guizang-social-card-skill/blob/cf4b810fac1c73fb65a2bb31d8c9278d82cbc4c5/references/content-planning.md)、[排版校验](https://github.com/op7418/guizang-social-card-skill/blob/cf4b810fac1c73fb65a2bb31d8c9278d82cbc4c5/validate-social-deck.mjs)。

**对你的启发：** 针对攻略、价格表、参数对比、教程，提供文字可编辑的排版路径。用户修改一个价格或标题时，只重新排版导出即可。插画类内容继续使用现有字图一体方案；两种方式由内容用途决定。

该项目的审美规则、图片尺寸和页数是自身模板选择，本次不把它们当作平台规则。借鉴的是结构化内容和可检查排版，不需要照搬它的整套视觉风格。

## 三、对照你当前代码后的修正

### 图卡已有不少基础，主要补全贯通与精度

你的 [图卡 composable](/Users/LXH/claude/y-1/src/composables/useCardSeries.ts:43) 和 [后端编排](/Users/LXH/claude/y-1/platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/cardseries/CardSeriesService.java:100) 已具备拆页计划、编辑、逐卡生成、部分成功、单卡重试和素材持久化。批量生成还有首卡 `revisedPrompt` 的文字风格锚。

建议在这些能力上补充：

1. 图卡计划、排序和选定图片关联到当前文章，并在完成页一起预览、导出和恢复。
2. 卡片保留稳定 ID、原始页码和角色，封面、内容页和总结页独立表达。
3. 在实际供应商支持时评估图片参考；统一记录主题、事实、配色和视觉要求。供应商不返回 `revisedPrompt` 时，仍有稳定的风格来源。
4. 保留现有字图一体制作；针对需要精确文字的内容，评估可编辑排版模式和错字核对。

当前 [后端提示词说明](/Users/LXH/claude/y-1/platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/cardseries/CardSeriesPrompts.java:4) 记录了 2026-09-02 选择字图一体的原因：旧叠字方案留白过多。上述排版建议应作为有实际样稿对照的可选扩展，设计时也要检查信息密度，不能只用文字准确率衡量成品。

### 新确认的问题：内容页单独重试会按封面生成

**源码事实：** 前端单卡重试仅发送一张卡片；后端按本次请求数组从 0 编号；提示词用 `index == 0` 判断封面，并且只在非首卡分支注入风格锚。

因此，重试原来的第 3 张内容卡时，提示词会要求生成“系列封面卡”，且不会使用此次传入的风格锚。前端返回后虽然把结果位置改回第 3 张，也不能修正已经发出的生成指令。

证据：[单卡请求与返回映射](/Users/LXH/claude/y-1/src/composables/useCardSeries.ts:165)、[从 0 遍历请求卡片](/Users/LXH/claude/y-1/platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/cardseries/CardSeriesService.java:100)、[封面判断和风格锚分支](/Users/LXH/claude/y-1/platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/cardseries/CardSeriesPrompts.java:43)。

**建议：** 以原始卡片身份和页面角色生成提示词，不使用请求内索引决定页面角色。验收时单独重试内容页，检查仍是对应内容页、风格参考仍在、其他已完成图片不重新生成。本次确认的是指令传递问题，未调用模型衡量其视觉影响。

## 四、九个平台对应的建议

| 平台 | 建议的主流程 | 本轮重点补充 |
| --- | --- | --- |
| 小红书 | 真实素材/知识依据 → 选题与首图 → 逐页方案 → 图片与笔记正文 → 发布包 | 实拍与知识图卡分流；已有文字可直接排版；图卡并入项目结果；保留单页编辑和重试 |
| 抖音 | 图集走逐图信息递进；视频走脚本、镜头和成片 | 区分图内文字、口播和发布描述；支持已有视频；平台发布适配按图集和视频分别验证 |
| 大众点评 | 真实体验 → 优缺点与具体事实 → 整理表达 → 人工核对 | AI 负责表达整理；保留用户评价方向。商家宣传与消费者评价分流，生成图片不作为消费体验依据 |
| 快手 | 人物/具体需求 → 实拍过程或演示 → 结果 → 成片与配文 | 提供自有素材制作；镜头适配内容；发布时确认上传完成、处理弹窗并限制重试 |
| 视频号 | 受众问题 → 案例或演示 → 结论 → 成片与分享配文 | 独立交付封面、发布描述、朋友圈或群分享配文；分别记录制作与发布状态 |
| B站 | 选题与资料 → 章节论证 → 口播/演示 → 剪辑工程 → 简介与来源 | 专题先做好资料和章节；允许交付脚本、素材包或剪辑工程，时长与当前渲染能力分开说明 |
| 公众号 | 资料与观点 → 文章 → 标题/摘要/封面 → 富文本预览 → 导出或草稿同步 | 原文排版单独成流程；正文图片地址和封面素材完整处理；草稿与公开发布分开 |
| 知乎 | 目标问题 → 结论与依据 → 回答 → 引用核对 → 交付 | 真实身份与经历来自用户资料；引用逐项支撑论点；回答开头与文章标题使用不同字段 |
| 朋友圈 | 已有图片/视频与真实感受 → 短文案 → 排序或裁剪 → 联合预览 | 直接使用已有媒体；视频配文独立；面向个人生活、经营动态等不同目的选择口吻 |

本次核对的社区项目，主要覆盖图卡、文章、视频制作和部分平台分发。它们不足以验证大众点评评价、朋友圈发布等全部渠道的接入能力；平台规则依据仍沿用上轮报告的官方来源，并在实际接入时复核。

## 五、建议补充的产品流程

### 入口围绕用户手上已有的内容

保留九平台导航，在创作来源中明确三种加工方式：

- **从资料创作：** 提供目标、事实、观点和素材，生成适合目标平台的初稿。
- **改编已有内容：** 保留事实与来源，按平台调整结构、长度和表达，能查看改动。
- **原文排版或素材整理：** 保持文字内容，完成排版、分页、选图、字幕或导出。版面放不下时提示拆页或由用户决定删改。

“原文排版”与“精确文字图卡”是两个不同选择：前者决定是否改动内容，后者决定如何绘制文字。长文全部保留可能需要更多页数，不能将“压缩成几张图”也默认称为原文不变。

### 一个项目关联多个平台版本

共同保存已确认事实、来源、自有素材和作者信息；各平台版本单独保存标题、正文、逐图计划、镜头、封面、配文、声明和导出结果。修改共同事实时，提示哪些平台版本需要重新检查。

例如同一次真实到店素材，可以分别组织成小红书体验分享、抖音过程短片、公众号介绍和朋友圈短动态。大众点评评价应由实际体验者确认，不应从商家宣传版本自动转换为消费者经历。

### 制作状态与发布状态分别记录

制作侧继续维护项目、文本版本、素材和生成运行。发布侧对每个平台记录实际达到的阶段，例如“平台草稿已保存”“已提交”“审核中”“已公开发布”“失败”“待确认”；并非所有平台都暴露所有阶段。

保存平台返回的作品 ID、草稿 ID、可用链接和最后核对时间。提交后超时先查询已有记录，确认未提交才重新发起，减少重复发布。人工发布的结果允许用户登记链接，并标明核验情况。

### 复盘围绕被采用的成品

首先记录用户修改量、首次可用率、完成时间、被采用成品的成本和失败恢复率。平台表现按账号可获取的数据、内容目的和观察周期评估，区分曝光、观看、收藏、咨询及转化。

可以比较同一账号相近选题的封面、开头或内容结构，但自然流量比较存在混杂因素。论坛单个爆款、低播放案例和项目 Star 数都不能代替这些评估。

## 六、实施顺序与验收

| 顺序 | 建议 | 最小可验收结果 |
| --- | --- | --- |
| P0，延续上轮 | 点评真实体验、作者身份与 AI/商业声明 | 缺少体验和资历时不补写；负面感受不会自动改成好评 |
| P1 | 补全平台、行业、风格和用户要求的传递 | 同一素材跨平台策划时能追踪平台要求进入了实际生成指令 |
| P1 | 图卡主流程、原始卡片身份与 #92 项目恢复 | 完成页有选定图卡；内容页重试仍是内容页；恢复后图序和已完成素材保留 |
| P1 | 已有内容加工入口与完整发布素材包 | 定稿文章可直接排版；已有视频可进入制作；公众号有摘要/封面，视频有发布配文 |
| P2，样稿验证后扩展 | 精确排版模式、资料依据和长内容 | 改价格不重做底图；引用可追溯到资料；B站章节对应实际脚本或成片 |
| P2，按渠道接入 | 草稿同步、有限重试、结果回读 | 公众号草稿不显示为公开发布；提交不确定时可查询，避免无依据地再次发布 |
| 持续 | 内容质量与成本复盘 | 能比较首次可用率、修改量和成品成本；效果指标注明平台口径 |

这里的优先级是产品改造顺序。现有缺乏事实支持的问题不能等待检索系统完成：先约束生成和补充输入，之后再扩展自动检索能力。
