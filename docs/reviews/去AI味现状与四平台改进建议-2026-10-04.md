# 去 AI 味现状与四平台改进建议

调研日期：2026-10-04（Asia/Shanghai）。接续原聊天的需求：梳理项目现有能力，结合 GitHub 与社区讨论，服务知乎、小红书、大众点评笔记和朋友圈。用户已确认同时用于个人分享与商家内容，需要区分身份。

范围：当前工作区代码静态阅读、5 个 GitHub 项目 README 与版本核验、V2EX / Reddit / Linux.do 的公开搜索摘录。代码基点为 `37d2b156`，工作区另有未提交修改；以下描述以实际读取的工作区为准。未运行生成模型、未查询运行库配置、未做发布或流量实验。

## 1. 结论

建议把产品目标定为“根据真实材料，用符合本人身份和习惯的表达完成内容”。当前项目已有去模板规则、身份事实简报、平台模板和改稿学习，主要缺口在这些能力的组合方式。

优先做三件事：

1. 清理生成源头的固定金句、互动收尾、闺蜜口吻和机械禁词，统一提示词优先级。
2. 把图片评价已有的改稿学习扩成四个平台共享、按作者身份区分的文风档案，再加入少量本人范文。
3. 对初稿做有条件的编辑与事实复核，用人工盲评和修改时间判断收益。

根据当前规则文本，现有三套中“改留对照”更适合作为保守基线；这只是待验证的选型建议，尚无本项目真实文案对照结果。暂时不需要增加第四套全局规则，也没有证据支持先做微调或购买“降 AI 率”服务。

## 3. 最值得修的冲突

### 3.1 生成模板持续制造固定腔调

| 位置 | 已确认要求 | 建议 |
|---|---|---|
| 知乎专栏与回答 | 固定三段配比、每约 800 字金句、末尾开放性问题 | 保留回答问题、证据和边界；金句、分论点数量和互动由内容需要决定 |
| 小红书文章模板 | 闺蜜/好朋友语气、每段 1–2 个 emoji、结尾总结推荐与“姐妹们冲”示例 | 身份和本人样例决定称呼、语气与表情；行动引导仅在明确目标需要时出现 |
| 朋友圈 | 结尾带约起/点赞/评论；探店风格要求第一人称到店体验 | 普通日常允许自然结束；探店自述必须有已确认的本人经历 |
| 图片评价 | 嵌入另一份 `HUMANIZER_ZH_RULES`，“居然”“竟然”等列为一律禁止 | 改成按语境识别空泛和夸张，保留作者真实惊讶；统一规则来源 |

证据：[知乎与小红书模板](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/article/ArticlePrompts.java#L131)、[朋友圈模板](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/moments/MomentsPrompts.java#L20)、[评价中的硬编码规则](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/imageanalysis/ImageAnalysisPrompts.java#L187)。

这些是代码层面的指令张力，不代表已经通过模型实验观察到每种错误。全局注入声明风格“最高优先级”，同时要求保留既定输出结构；若模板把金句或互动写成必要结构，单靠尾部补规则很难得到清楚一致的要求。应先在组装阶段消除矛盾。

### 3.2 文风学习没有区分个人与商家

当前偏好以 `account_id` 读写；检索到的 `StylePreferencesService` 消费方位于图片评价模块。一个账号的个人点评、店铺介绍、商业合作可能把不同要求合并到同一份列表。

建议增加作者档案或身份维度，再叠加平台微调。商家也可以使用第一人称，但应是“我们店今天……”，而不是代入“我第一次来这家店……”。商业合作与自费体验也应保留差别，不能只分“口语”和“正式”。

### 3.3 从改稿学习，需要先分清修改原因

现有总结提示让模型直接从两个版本提炼风格差异；合并时使用字符串去重，最多保留 100 条。[总结提示](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/imageanalysis/ImageAnalysisPrompts.java#L118)

下一步应把“事实纠错”“这篇临时要求”“长期表达偏好”分开。例如把 38 元改成 36 元属于事实修正；删掉此次活动的联系方式不一定意味着永远不用行动引导。持久偏好应让用户能确认、撤销，并在冲突时替换旧规则，避免列表越积越长。

## 6. 四个平台应怎样分别写

以下为产品默认建议，不是平台官方字数或算法规则。以作者明确要求和实际材料为准。

| 平台 | 个人真实分享 | 商家或商业合作 | 可选默认设置 |
|---|---|---|---|
| 知乎 | 先回答问题，给证据和适用范围；经历仅用本人确认内容 | 说明利益关系和适用条件，用案例、数据解释取舍 | 允许短答或长答；无强制金句、固定论点数量与提问结尾 |
| 小红书 | 一个明确场景，加少量有用细节、真实优缺点 | 用真实商家/合作身份写卖点、限制和选择建议 | 短段易读；称呼、emoji 和标签强度随本人习惯，行动引导可关闭 |
| 大众点评笔记 | 已确认的菜品、环境、价格、排队和服务感受；保留不满 | 店铺介绍或活动说明，不代写成普通顾客评价 | 图像仅支持可观察信息；口味、服务等感受从用户材料来 |
| 朋友圈 | 给熟人看的近况、片段或判断，可以很短 | 讲清今天提供什么、时间和条件；必要时一句联系提示 | 无须补足完整文章结构；普通日常默认可自然结束 |

示意：以下均使用虚构的演示材料，不是用户实际经历或店铺事实。

- 个人材料：“本人周六去过 A 咖啡店；点了 36 元的拿铁；二楼安静；楼梯较窄。”可写：“周六去了 A 店。拿铁 36，二楼挺安静，就是楼梯有点窄。”
- 商家材料：“A 店经营者；拿铁 36 元；二楼设座位；楼梯较窄。”可写：“店里二楼也有座位，拿铁 36 元。楼梯比较窄，带大件行李的话提前留意一下。”

两份材料不同，表达视角也不同；仅有商家材料时，不生成“我周六来探店”的经历。

## 7. 建议实现顺序

### P0：先把同一次生成的要求整理清楚

- 修改 `ArticlePrompts`、`MomentsPrompts`、`ImageAnalysisPrompts` 的强制文风要求。保留 JSON 字段、必要标题/标签字段和当前业务输出契约。
- 把图片评价本地禁词与全局规则归为一个明确的编辑策略。把“不得编造事实”与“不要空话”分开定义，避免全部被叫作最高优先级。
- 组装顺序明确为：事实与身份边界 → 明确任务和输出契约 → 当前作者要求/本人声音 → 平台阅读习惯 → 通用去模板建议。冲突在代码组装时处理。
- `format` 原文排版路径应明确跳过措辞改写，不依赖一条提示同时要求“原文不改”和“消除模板”。
- 更新现有库规则时保留自定义内容，登记旧版本、变更与回滚方式；不要靠重启期待种子覆盖。

### P1：共享作者文风，区分身份和平台

- 复用 `CreationBriefEditor`、现有风格偏好编辑/删除功能和 `saveFromEdits` 服务；将持久偏好从图片评价抽到共享域。
- 初版可用 `(account_id, profile_id)` 管理“个人分享”“商家”“商业合作”档案，再保存按平台覆盖的细项。遵守现有组织权限，不跨账号或组织混用样本。
- 每个档案收集少量本人已发布或认可的作品作为起点，例如 5–10 条；具体数量由样本质量决定，不把该数量当科学阈值。
- 保存简短风格卡：称呼、句子长短、用词、表情、观点强弱、结尾方式，加 2–3 个相近体裁例子。范文中的商家名、时间和经历只作原文内容，不成为新稿事实来源。
- 先使用身份、平台、体裁标签选择样本；样本量小时无需先搭向量库。允许用户关闭档案或临时覆盖。
- 改稿保存时区分事实修正与长期偏好，新增偏好可确认、可撤销；支持冲突替换，避免无限追加规则。

### P2：让编辑有目的，让效果可比较

- 默认用材料和文风一次生成。只有发现具体问题或用户请求时才进入编辑；记录改了哪里及原因，正常句子允许保留。
- 每次编辑回查原始事实材料，不能只对上一轮生成文本查重。数字、名称、否定词、条件和已确认体验做重点比对；仅靠正则无法检查全部语义漂移。
- 图片评价现有 2/3 阶段作为基线，与“首次生成吸收文风 + 按需编辑”对照后再决定是否减少调用，不能未经验证宣称质量或成本已改善。
- 利用现有执行链和消息捕获能力，记录规则版本、档案版本、平台模板版本、模型与参数；分阶段执行沿用计费、权限及错误处理，避免另建旁路。

## 8. 验证收益的方法

建议先收集 32 份材料：4 平台 × 2 类主要身份 × 4 种情形（材料充足、材料不足、带负面/限制、原文已自然）。商业合作作为身份边界补充案例；知乎再覆盖回答与专栏。保留一部分本人作品专用于评估，不参与提炼档案。

逐步对比，不把所有变化同时混入：

1. 当前已激活配置的基线；记录实际规则，不假定是哪一套。
2. 仅修复模板冲突。
