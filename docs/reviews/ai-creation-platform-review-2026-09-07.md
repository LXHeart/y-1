# AI 创作中心九平台创作逻辑评估

调研日期：2026-09-07。源码基线：`851f0691` 所在的当前工作区。

已整合为 [AI 创作中心九平台调研整合与改造总方案](ai-creation-center-integrated-upgrade-plan-2026-09-07.md)。后续改造与验收从总方案进入，本文保留原始调研记录。

补充调研：[GitHub 与 Linux.do、V2EX 的实现和使用反馈](ai-creation-community-research-2026-09-07.md)，包含图卡制作、已有内容加工、公众号草稿、发布状态及非首卡重试的新发现。

## 结论

现有架构适合继续迭代：九平台入口、共用生成引擎、任务上下文冻结、分步编辑、内容安全和视频制作管线都已有基础。问题主要集中在平台适配的信息传递、事实约束和最终交付。

建议优先调整大众点评的默认好评方向，修正常规视频分镜遗漏平台与风格信息的问题，再把图文、视频各自需要的发布素材串成完整项目。小红书、知乎、朋友圈已有的专用逻辑应继续保留。

本报告将“源码已证实的问题”“平台公开要求”“产品改进建议”分开表述。具体字数、时长、标签数量和内容节奏的建议，不等于平台硬限制，也不代表推荐算法公式。

## 一、评估范围

- 覆盖小红书、抖音、大众点评、快手、视频号、B站、公众号、知乎、朋友圈。
- 同时检查独立创作、热点创作、参考素材和草场任务创作。任务模式已有服务端冻结上下文，不能把独立模式的问题直接套到任务模式。
- 检查入口路由、前端输入、请求字段、Java 提示词、平台规则契约、结果出口及相关测试。
- 外部资料通过 agent-reach 技能提供的 Exa 后端检索；重要结论优先采用平台和监管部门页面。部分资料为检索摘录或媒体转述，见来源表。
- 未调用付费生成接口，未登录各平台发布后台，也未采集真实账号的流量和转化数据。因此本次可以判断设计与代码逻辑，不能给实际生成质量或增量收益打分。

## 二、当前九平台如何工作

公共入口是“平台 → 内容形式 → 创作来源 → 工作流”。视频还可以选择常规脚本、风格化喜剧或参考视频复刻。参考素材入口目前分析抖音或 B站视频，再交接到目标工作流；朋友圈的参考来源仍是 `planned`。

入口证据：[能力矩阵与工作流分派](../../src/config/ai-platform-capabilities.ts#L149)、[独立与任务来源](../../src/views/ai-center/AiCreationCenter.vue#L413)。

| 平台 | 当前实际路径 | 判断 |
| --- | --- | --- |
| 小红书 | 图文走主题、标题、大纲、正文、检查；另有图卡面板。视频走共用视频管线 | 专用文案方向合理，图卡与主流程衔接不完整 |
| 抖音 | 图集已有独立 `douyin` 提示词，走文章步骤、检查和配图；视频走共用管线 | 已区别于小红书，仍需加强逐图策划与视频适配 |
| 大众点评 | 图片、感受、字数 → 初稿 → 润色 → 个人风格优化；视频走共用管线 | 默认好评与真实评价的目标冲突，需优先调整 |
| 快手 | 视频入口，共用店铺照片、分镜、候选片段、合成流程 | 制作能力可复用，独立创作的快手专用策划不足 |
| 视频号 | 视频入口，共用管线；任务规则强调社交分享 | 对内容价值、账号定位和发布配文的适配不足 |
| B站 | 视频入口，默认横版，成片支持 15-180 秒 | 可覆盖部分短片；不足以代表完整的 B站知识、测评和中长视频创作 |
| 公众号 | 主题、标题、大纲、正文、检查、配图；默认 1500-3000 字 | 长文流程合理，内容子类型与公众号发布素材不足 |
| 知乎 | 已区分回答与文章，默认回答；回答走问题、开头、大纲、正文、检查、配图 | “围绕问题回答”正确，证据、身份与格式检查需修正 |
| 朋友圈 | 图片文字有独立流程，支持风格、短文案、图片排序、每图配文；视频文字走共用视频管线 | 图片文字相对贴合场景，视频文字缺独立配文交付 |

这里的“支持形式”是本产品目前的范围，并非各平台的完整能力。例如，不能从仓库的“快手仅视频”“知乎仅图文”推断这些平台没有其他内容形式。

值得保留的实现包括：抖音已经使用独立图集提示词；知乎已经有回答模式和目标问题锁定；朋友圈已经有独立的多模态输出结构；视频已经支持分镜编辑、候选选择、字幕、成片及剪映草稿/素材包导出。后续建设应建立在这些能力上。

## 三、优先处理的问题

以下优先级是本次产品整改顺序：P0 为首先处理的真实性与发布风险，P1 为核心流程和适配问题，P2 为后续效果优化，不表示发生了生产事故。

### F01 / P0：大众点评默认追求好评，没有先建立体验事实

**源码事实：** 生成提示词要求“整体风格偏自然好评”；无补充感受时“仅根据图片内容生成评价”。优化阶段继续要求“保留自然好评方向”。用户上传图片可以说明外观，却不足以证明口味、服务、实际消费金额和亲身到店经历。

证据：[初稿与优化提示词](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/imageanalysis/ImageAnalysisPrompts.java#L34)。现有“不得编造图片里明显没有的信息”约束，仍没有明确区分图片可观察事实与用户亲身感受。

**平台依据：** 大众点评用户条款要求客观、真实、亲身体验的点评；2026 年商户评价诚信规则明确抵制虚假好评、受利益干扰的评价和操控评价结果。[S02][S03] 诚信申诉页面还明确列出商家及利益相关方自评、雇佣第三方好评、利益换好评等情形。[S04]

**建议：** 先区分“消费者真实评价”“探店笔记”“商家经营内容”。评价模式收集实际体验、优缺点、消费信息和利益关系，AI 只整理表达；评分由用户决定。信息不足时先补充事实，或生成尚待填写的提纲。商家介绍和获客任务进入经营内容流程，不能直接生成伪装消费者口吻的评价。利益声明也不能替代平台对利益换评价行为本身的限制。

### F02 / P1：常规视频独立创作遗漏了平台、行业和风格信息

**源码事实：** 前端发送 `targetPlatform`、`industryType`、`videoStyle`。当前分镜的 system 只对 `moments` 有额外分支，user 仅拼接店铺、地址、简介、要求、参考结构、图片和时长，没有拼接上述三项。独立创作调用中又没有任务规则上下文。

证据：[前端请求](../../src/composables/useVideoProduction.ts#L296)、[分镜提示词](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/videoproduction/StoryboardPrompts.java#L48)、[独立/任务调用分支](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/videoproduction/StoryboardService.java#L64)。

因此，对同样的输入，选择抖音、快手、视频号或 B站，分镜模型收到的文字策划指令可能相同。B站的横版分辨率仍会生效，但横竖版不能代替叙事适配。任务模式会注入平台规则，影响范围需要分开看。该问题针对当前 `/storyboard` 路径，不能用旧 `/generate-script` 提示词来判断已经适配。

**建议：** 用统一的创作简报传入平台、内容子类型、行业、受众、目的、作者身份、风格和时长；每个平台再增加对应的结构要求。保留共用制作管线。

### F03 / P1：小红书图卡不在正常完成路径中，结果也未随文章交付

**源码事实：** 正文流完成立即进入检查；图卡只在 `content` 或 `images` 阶段显示；小红书检查后又跳过配图直接完成。用户依次前进，可以完成一篇没有图卡的“小红书图文”。

图卡计划和结果保存在面板内部 composable 中；面板只向父层发出放大预览事件，没有把生成图卡、顺序和素材 ID 交给文章结果。阶段切换卸载面板后，局部状态不能在当前文章中保留。手动保存到素材库的文件仍可保留，但不等于已经关联到文章。

证据：[图卡挂载条件](../../src/views/article/ArticleCreationView.vue#L158)、[正文自动进入检查](../../src/composables/useArticleCreation.ts#L393)、[小红书跳过配图](../../src/views/article/ArticleCreationView.vue#L340)、[图卡局部状态与事件](../../src/views/article/components/CardSeriesPanel.vue#L19)。

**建议：** 将“实拍图/图卡选择与排序”作为主流程的一步；图卡状态由项目持有；最终结果包含标题、正文、标签、图片及顺序。已有用户图片可以直接完成视觉步骤，不必强制再生成图卡。抖音图集同步复用这一交付能力。

### F04 / P0：知乎等内容有虚构资历、体验或证据的诱因

**源码事实：** 知乎文章要求第一人称资历介绍，示例为“我做这行 8 年”；回答开头和正文也要求资历或经历交代，并要求数据、案例、亲历细节。当前问题和补充说明并不是经过确认的身份/证据字段。

证据：[知乎文章提示词](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/article/ArticlePrompts.java#L177)、[知乎回答提示词](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/article/ArticlePrompts.java#L221)。

这不能证明每次都会编造，但明确增加了资料不足时补写虚构身份和经历的可能性。现有安全深检主要检查夸大承诺、导流和违法语境，没有拿作者身份、体验记录、数据来源逐项核对。[安全深检范围](../../platform-java/services/intelligence-service/src/main/java/com/grassland/intelligence/contentsafety/ContentSafetyAiChecker.java#L121)。

**建议：** 只有用户提供并确认的经历才使用第一人称背书；缺少经历时用中性说明。数据、引用、案例保留来源和时间，查不到的事实标待核实或删去。小红书探店、测评，公众号数据文章，朋友圈到店体验也应沿用同一事实约束。知乎官方创作者手册强调可信来源和资料出处。[S13]

### F05 / P1：创作中心补充要求在部分文章交接中丢失

**源码事实：** 创作中心会传递 `prefill.instructions`；文章视图仅在参考来源时将其并入主题，其他来源只取 `prefill.topic`。独立/热点来源填写的受众、角度或额外要求，在这个交接处没有被带入文章生成。任务模式另有服务端快照，不能视为同样全部丢失。

证据：[创作中心预填字段](../../src/views/ai-center/AiCreationCenter.vue#L828)、[文章预填处理](../../src/views/article/ArticleCreationView.vue#L348)。

**建议：** 把主题、补充要求、目标受众、事实和参考来源作为独立字段一路传递，并在每一生成阶段保留。热点只是选题来源，生成前仍应核对事件时间、事实和与目标内容的关联度。

### F06 / P1：平台规则没有区分发布字段与内容子类型

**源码事实：** 规则主要按平台定义一组正文上下限和标题上限。知乎回答把开头放在 `selectedTitle`，格式 composable 却没有回答模式参数，仍按知乎 30 字标题上限判断。候选步骤隐藏了标题提示，但完成页会展示 `formatIssues`，因而正常的 60-120 字回答开头可能被提示“标题超长”。

证据：[统一规则](../../contracts/platform-format-rules.json#L88)、[格式计算](../../src/views/article/composables/useArticleFormatRule.ts#L38)、[完成页提示](../../src/views/article/components/ArticleCompletedView.vue#L13)。

另一个例子：仓库的公众号标题口径为 64 字，本次检索到的微信新增草稿 API 文档写 32 字。[S11] 这不足以推断网页编辑器也只能写 32 字，但说明 API、网页、不同内容类型不能共用一个未标明来源的上限。

**建议：** 分开管理三类约束：平台发布硬限制、创作建议、当前生成引擎限制。规则至少按“平台 + 内容子类型 + 发布字段 + 发布渠道”查找，注明来源、核验日期和计数方式。发布文案、口播、图上文字、正文、回答开头必须分别校验。未知限制应留待核验，不能包装成官方规则。

### F07 / P0：AI 标识没有形成各平台统一的交付动作

**源码事实：** 在检查到的前端生成出口和 intelligence 源码中，明确的发布前 AI 声明提醒集中在知乎文章模式；知乎回答分支提前返回，只提醒挂回原问题。未发现统一覆盖九平台结果的标识与声明处理。

证据：[发布提示分支](../../src/views/article/ArticleCreationView.vue#L405)。这是已检查代码范围内的结论，不代表已经检测过第三方模型返回文件的元数据。

**平台依据：** 《人工智能生成合成内容标识办法》自 2025-09-01 施行，涉及显式、隐式标识和用户发布声明。[S01] 抖音、微信、B站及小红书的公开资料也涉及相应标识要求或治理措施。[S05][S06][S12][S14]

**建议：** 将 AI 生成情况、素材来源和应使用的平台声明入口纳入交付；按服务角色与适用规则处理生成文件及导出文件的标识，检查压缩、转码、裁切后的保留情况。发布声明、商业合作声明和原创声明分别记录。视频号的原创声明属于专门权益规则，不能把“能够发布”“拥有素材使用权”“可以声明原创”混为一件事。[S10]

## 四、九个平台建议采用的创作流程

以下是产品设计建议。文字长度、时长和结构应允许用户按素材与目标调整，最终以样稿和真实效果验证。

### 1. 小红书：按实拍分享与知识图卡分流

保留已有标题、体裁、文风和图卡能力。入口增加“实拍探店/体验分享”“攻略/清单图卡”“视频”等子类型；避免把所有账号都默认成闺蜜式种草口吻。

**输入：** 分享目的、目标人群、已确认体验、实拍素材、可核实的价格/门店信息、利益关系。做知识类内容时收集依据和适用范围。

**流程：** 事实与素材 → 选题角度 → 标题和首图一起策划 → 逐图内容或实拍排序 → 简短正文及相关话题 → 图文一致性检查 → 发布包。短笔记可以直接生成初稿，大纲作为可选编辑能力。

**交付：** 标题、正文、独立标签列表、有顺序的图片、封面、声明提示。实拍用于展示实际商品或场所；AI 插图用于解释或明确标注的创意内容。评价和体验不得从生成图片反推。真实表达与反对虚假人设有公开规则支持。[S05]

### 2. 抖音：图集与视频共享选题，分别组织成品

抖音图集已有独立提示词，应继续使用。主要改进是把“封面文字”“逐图文案”“发布描述”拆成不同字段，避免用一段图集发布文案同时承担所有用途。

**图集流程：** 受众和目标 → 首图表达 → 逐图信息递进 → 图片生成/上传排序 → 发布描述和话题 → 预览导出。

**视频流程：** 受众和目标 → 开场表达 → 实拍/口播/演示脚本 → 分镜和素材 → 配音字幕及剪辑 → 封面与发布描述。开场节奏是可测试的策略，不必把任何题材都写成强冲突。

**交付：** 图集或成片、封面、发布描述、话题、字幕、适用时的门店/商品信息和商业合作/AI 声明。只在账号具备相关发布能力时要求对应字段。抖音创作者中心本身区分图文、视频等体裁。[S16]

### 3. 大众点评：先体验，再组织评价

**消费者评价输入：** 真实到店/使用情况、门店、时间、消费项目、价格、优点、不足、适合谁、照片和利益关系。未知信息允许不填，不能由 AI 猜齐。

**流程：** 确认评价身份与实际体验 → 确认事实 → 提炼真实观点 → 润色 → 人工核对 → 选择评价或笔记对应的发布格式。

**交付：** 客观评价正文、按内容类型需要提供的标题、实拍图片及说明；评分保留用户原始决定。不能为达到字数而补出“服务很好”“回购多次”等没有依据的细节，也不必固定生成话题标签。

**商家内容分支：** 经营介绍、活动说明、产品展示与顾客评价分开。草场任务如涉及商业推广，先核对它适合哪类平台内容，不能自动归入消费者评价。[S02][S03][S04]

### 4. 快手：加强人物、过程和垂直内容

**输入：** 创作者或经营者的真实身份、服务人群、具体产品/技能、可展示过程、内容目的；方言与口吻由用户选择。

**流程：** 一个具体问题或需求 → 可见的过程/演示 → 结果与适用人群 → 自然交流。商业账号可增加直播预告等子类型，但并非每条视频都需要导购。

**交付：** 可拍摄脚本、镜头素材清单、字幕、封面、发布配文，适用时附直播预热版本。不要把平台适配简化为在文案中加“老铁”。

2026 年快手创作者大会强调多元特色、圈层、专业内容和短视频与直播协同，说明“接地气短促口播”不能覆盖整个生态。[S07][S08]

### 5. 视频号：围绕明确受众提供可理解、可分享的内容

**输入：** 账号定位、目标受众、要解决的问题、真实案例、希望受众采取的行动；需要关联公众号文章或经营内容时再填写相关材料。

**流程：** 明确问题/结论 → 可信案例或演示 → 简洁归纳 → 可选的自然互动。为陌生观众保留足够上下文，不能只按照熟人朋友圈的语境写。

**交付：** 视频、封面标题、发布描述、转发到群或朋友圈的配文、字幕；按实际情况处理 AI 与原创声明。

官方指南强调原创、人格化、高价值、封面标题、清晰制作和精准关键词；现有只强调熟人传播的规则应据此补充。[S09] 具体推荐权重不作推断。

### 6. B站：区分短片与有完整论证的专题视频

保留现有横版短片能力。增加“知识讲解”“测评/对比”“过程记录”等内容子类型，根据题材支持横竖版选择。B站并非所有内容都必须是中长横版。

**输入：** 主题或问题、个人观点、资料依据、演示素材、对照对象、期望深度和时长。

**流程：** 选题与资料 → 章节大纲 → 论点/证据/演示 → 口播与拍摄脚本 → 按章节组织镜头 → 剪辑 → 简介与章节信息。

**交付：** 脚本、成片或可继续剪辑的工程、封面标题、简介、适用时的时间轴、参考来源、标签、合作与 AI 声明。时间轴应由实际成片计算。

当前 15-180 秒、单镜 4-6 秒、最多 30 镜是生成管线的限制，应明确为产品能力。可以先支持长视频脚本和素材包，继续复用当前短片渲染能力。涉及时事、公共政策、社会事件时，B站另有明确的信息来源标注要求。[S14][S15]

### 7. 公众号：从文章正文扩展为完整编辑稿

**输入：** 目标读者、文章目的、稿件类型、核心观点、引用材料、作者及品牌口吻。区分活动通知、知识文章、品牌故事和图片消息等；不必全部写成 1500-3000 字“爆款长文”。

**流程：** 选题与事实 → 大纲 → 正文 → 按内容需要配图 → 标题、摘要、封面 → 排版预览 → 发布素材导出。

**交付：** 标题、摘要、正文、封面及裁切预览、文中图片、来源、分享配文。支持适合公众号编辑器的富文本/HTML 交付，并保留 Markdown 原稿。

若后续接公众号草稿箱，须按实际接口处理封面素材 ID、图片上传、正文格式及字段限制。当前官方新增草稿接口已经区分图文消息与图片消息，且具有摘要、封面和内容来源字段。[S11] 这些字段不能仅靠“复制正文”完成。

### 8. 知乎：围绕问题和证据回答

保留现有“回答/文章”双模式。默认回答有产品依据：知乎创作者手册建议新人优先参与问答；这不代表可以断言所有账号的回答推荐权重都高于文章。[S13]

**输入：** 问题原文、问题背景、作者观点、真实经验、数据或资料来源、利益关系。问题链接识别只是辅助定位，当前不会自动读取原问题正文，应维持清晰的输入边界。

**流程：** 理解问题 → 列结论与所需证据 → 补充资料 → 写回答 → 检查是否答题、证据是否支持结论 → 挂回问题。短回答可直接写作，长回答再经过大纲。

**交付：** 问题引用、开头、正文、证据来源、适用边界、利益相关与 AI 声明。回答开头使用独立字段和校验；配图按解释需要选择。不要强制资历背书、固定金句频率或所有问题都展开成 1000-3000 字。

### 9. 朋友圈：按关系与实际素材生成短表达

已有短文案、风格、图片排序值得保留。补充区分个人生活、个人真实体验、经营者动态和活动通知，避免所有内容都套用“自然安利”的表达。

**图片文字流程：** 已有图片和真实感受 → 文案候选 → 选图与排序 → 预览 → 复制文字及导出图片。“每图配文”更适合作为制作备注或可选图片文字，不应成为普通多图帖的主要交付。

**视频文字流程：** 已有实拍视频或生成的视频 → 独立的朋友圈配文 → 联合预览 → 视频与配文一起交付。已有视频应允许直接使用，不必再上传店铺图片从头生成。

**交付：** 共用短文案、有顺序的图片或视频、实际需要的声明。不要承诺固定字数就一定“不折叠”；折叠展示需要在目标客户端验证，现有 10-200 字可作为可调的创作建议。

## 五、建议的统一产品模型

### 创作简报保持一致

一次收集并贯穿标题、大纲、正文、图卡、分镜和改写：平台、内容子类型、目的、受众、作者身份、利益关系、事实、素材、观点、语气、长度/时长、来源和任务约束。

任务来源继续以冻结的服务端上下文为权威；独立来源同样要保留完整简报。外部参考中的“人物做过什么”“视频说了什么”属于参考信息，不能自动变成当前作者的经历。

### 共用引擎，按内容类型组织步骤

建议形成五类可复用流程：图集/短笔记、真实体验评价、短视频/专题视频、文章/回答、朋友圈短表达。平台配置进一步决定输入、叙事结构、图像选择、格式检查和发布字段。

公共顺序可以是：

`创作简报 → 事实与素材确认 → 平台内容方案 → 文本/图像/视频制作 → 联合检查 → 发布素材包 → 保存项目`

简单内容保留快速路径；复杂内容使用逐步路径。快速生成仍应使用同样的事实约束与平台规则。对于缺少店铺的个人创作，先支持纯脚本或自有素材流程，避免统一要求填写店名并上传店铺照片。

### 成品和生成任务分别管理

一个项目应关联标题/正文版本、图片及顺序、视频/字幕、封面、发布描述、来源、声明和检查结果。按资源 ID 持久化，失败可重试单张图或单个镜头，避免为了找回素材再次生成。

仓库已有 [任务书 #92](../任务书/草场任务书-92-AI创作中心工作流闭环与最近项目.md#L47)，状态为 `READY_FOR_IMPLEMENTATION`，覆盖最近项目、恢复和结果资产化。这里的项目建议应与 #92 合并排期；平台专用交付字段和事实约束仍需单独明确，不能把任务书里的计划当作当前已实现能力。

### 检查围绕成品的实际用途

现有内容安全检查继续保留，补充事实支持、标题与正文是否一致、图像与体验是否对应、字幕与口播是否匹配、时间轴是否真实、来源及声明是否完整。普通格式建议可以允许用户继续编辑；未确认的身份、体验和数据不应被系统擅自写成肯定事实。

## 七、如何验证“建议真的更合理”

先制作一组固定评估样稿，覆盖同一真实素材跨平台改写、只有图片无感受、负面体验、商家宣传、知识解释、活动通知、已有实拍视频等情形。每个平台至少覆盖核心子类型，避免只测餐饮推广。

人工评估重点是事实正确、符合发布目的、信息有用、口吻适合作者、可直接编辑、素材完整。记录用户修改量、首次可用率、完成所需时间、单份被采用成品的成本和失败恢复成功率。

上线后的指标按目的观察：小红书的有用反馈/收藏，视频的观看与互动，公众号的阅读完成与有效分享，知乎的答题质量与有用反馈，经营内容的实际咨询与转化。使用账号可获取且定义明确的数据，不把平台间不同口径的指标直接比较，也不把点赞量单独当作质量结论。
