# 草场任务书 #48：商家成员子账号体系（主体直建直发）

> 来源：2026-08-27 用户提出「店员没有平台账号无法加入门店」的管控诉求，对话中逐项对齐后定稿（方案 v2，用户四条拍板全部吸收）。改动面调研 2026-08-27 完成（main 快照）。
> 状态：**2026-08-27 已实现并验收**（S0–S5 同日落地；identity 全量 553 测试绿、edge 内部断言族绿、前端 test 898/typecheck/build 绿）。
> 产品口径已回写 PRD §2.1「成员与账号管理」。

## 目标

让商家不依赖店员自行注册就能把人管起来：

1. **成员账号由商家主体直接创建**：一次动作完成「建号 + 赋角色 + 挂门店」，创建即生效；初始凭据系统生成、一次性展示，商家线下交给本人，首登强制改密。全程没有任何被添加人的受理/申请环节。
2. **两级管理权**：组织 owner/admin 管全部账号并可直建任意角色；店长在本店内可加员工、停用/恢复员工——**默认全部免审即时生效**（仅事后站内知会），商家可按需开启「员工添加需主体审核」开关。
3. **账号停用 = 登录即拒**：复用 `app_users.status` 作唯一状态真相源，停用后该账号无法登录平台任何功能，恢复立即可用。

### 与现状的关系（动手前必须先认清）

现行体系是「成员表引用既有 accountId」：给门店加人的前提是对方**已经注册过平台账号**（邀请流 `organization_invitation` 或直接按 accountId 挂成员关系），小店店员没账号就卡死。本任务新增一条**主动建号通路**，与现有两条并存：

| # | 加人通路 | 前提 | 谁操作 | 本任务 |
|---|---|---|---|---|
| 1 | 直接挂既有 accountId 为成员 | 对方已有平台账号 | org admin / 店长 | 已存在（Slice 2G/2J），语义不变 |
| 2 | 邮件邀请 `organization_invitation`（pending → 本人接受） | 本人注册并点接受链接 | org admin 发起 | 已存在（V8/V32/V39），**原样保留不动** |
| 3 | **主体直建子账号 + 线下交付凭据** | 无任何前提 | org admin 直建任意角色；店长仅能建 staff | **本任务新增** |

三条通路最终都落到同两张成员表（`organization_membership` / `store_membership`），权限判定只此一处出口（`StoreAuthorization`）。

## 决策表（已定死，勿重开）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **建号权归属主体**：org owner/admin 可建任意角色子账号；店长只能建本店 staff；任命 manager 的门槛维持现状（org ADMIN+）。「主体开通资格随主体注册一次性获得」，此后每个成员都是主体自建自管 | 用户拍板「都是添加，不走申请流程」。角色枚举复用 `StoreRole`（manager/staff）与 `MembershipRole`，不新增角色层级 |
| D2 | **一次创建动作原子完成三件事**：插 `app_users` 行（随机密码 hash、status 见 D4/D5）→ 插对应成员行（org 层或 store 层）→ 写审计 outbox。响应体一次性返回明文初始密码，此后任何接口不再可读 | 建号没挂上成员关系是坏状态；凭据二次明文暴露是泄露面 |
| D3 | **凭据交付最低卫生线**：密码由服务端 CSPRNG 生成（≥16 位），创建成功页一次性明文展示供管理员抄走；账号带 `must_change_password=true`，登录成功但未改密前拦截业务 API（登录本身放行，改密端点除外）；org admin 可对成员触发重置（同样一次性展示+强制改密） | 商家代持凭据不可消除，但能把暴露窗口压到「第一次登录前」。防的是密码从群聊/纸条流出后永久有效 |
| D4 | **状态真相源 = `app_users.status`**：`active` / `suspended`（停用）/ `pending_review`（开审模式下店长代建待审）。登录只认 `active`（`AuthUser.isActive()` 现状即如此）；鉴权链路同步收紧为非 active 一律拒绝。**两张成员表不加 status 列** | 账号级停用天然覆盖「不能登录任何功能」的产品要求，且避免成员表/账号双状态漂移。`app_users.status` 是现成列，不用动表 |
| D5 | **邮箱冲突不静默绑定**：创建时目标 email 已存在于 `app_users` → 创建停在原地，报 409 让管理员二选一：「换个邮箱重建」或显式传 `confirmBindExisting=true` 把该既有 accountId 直接挂为成员关系（免审零额外流程） | 静默自动绑定等于输错一位字母就把门店权限送给同名陌生人。显式确认保留一步到位的体验，把判断留给知情的管理员 |
| D6 | **审核策略开关**：`organization` 表加 `member_review_required boolean NOT NULL DEFAULT false`。off（默认）：店长代建 staff 即刻 active；on：进 `pending_review`，org admin/owner 审批转 active 或驳回删号。**owner/admin 直建的账号永不 pending**（即使开关开着） | 默认免审保护单店小商户的零负担（用户拍板①）；开审满足连锁集中管控。审批只对「店长发起的授权」把关——自己开的号自己担责 |
| D7 | **停用与恢复全程无审核、即时生效**：店长可停用/恢复本店 staff；org owner/admin 可停用/恢复任何成员含店长。每次变更事后发站内通知知会受影响方（D10）。manager 之间互不可操作、store 成员不可跨店操作 | 授权从严、收权从宽；停用要等审核是风险敞口反模式（用户采纳修正案，拍板②保持一致性即免审模式恢复也直操作） |
| D8 | **四条保护规则**（写进服务层，逐条出测试）：①本店最后一个 `active` MANAGER 不可被停用/降级；②org OWNER 账号不可被任何人经本功能停用（平台 admin 链路不受限）；③操作者不能停用/审批自己的账号；④重复挂同一成员关系仍走 `UNIQUE` 409 | ①沿用 `guardLastManager` 并升级为「数 active 且未被 suspended 的 manager」（否则先停 A 再想停 B 时守卫失效）；②③④防自杀式误操作 |
| D9 | **免审模式下 pending 态不存在**：`member_review_required=false` 的组织里状态机退化为 `active ⇄ suspended` 两态；只有开审组织的店长代建路径出现 `pending_review`。免审组织里恢复（restored）也由店长直操作（用户拍板②） | 最简常态，两态逻辑单独成类可测，不与审批分支搅在一起 |
| D10 | **通知全部站内信**：复用 identity notification 表 + `NotificationEventProcessor.emit`。三类：①成员被停用/恢复 → 知会组织 owner/admin；②过审/驳回结果 → 发起创建的店长；③新账号建成 → 给新账号落一条欢迎通知（首登可见，避免「这号是谁建的」困惑）。不做短信/邮件推送 | 站内设施全套现成（V11/V12）；用户拍板③。新账号没人在线，站内信落库等待即可 |
| D11 | **被建账号的身份数据形态对齐邀请接受路径**：以「invitation accept 之后该账号拥有什么身份数据」为基准复刻（identity_profile/active_identity 等），不自创第三种形态；登录后的身份选择沿用 IA 现制（选身份且会话内定死） | 双身份模型已有大量基础设施；自创形态会在 `SessionIdentityResolver` 不变量处炸出隐性 bug |
| D12 | **审计事件三类入 outbox**：`OrgSubAccountCreated` / `MemberSuspensionChanged(suspended\|restored)` / `StaffCreationReviewed(approved\|rejected)`，payload 含操作者、目标账号、orgId/storeId、新旧 status | 停启用是敏感操作；排障与后续风控都需要谁在何时动了哪个号 |
| D13 | **不主动踢会话**：不撤销已发 token，靠鉴权处判 `app_users.status` 自然拒绝（下一个请求即生效） | JWT 黑名单整套基建当前不存在，为此引入大炮打蚊子；秒级收敛已满足需求 |
| D14 | **`app_users` 归属核对先行**：加 `must_change_password` 列前先验证 database-bootstrap Verifier 对「共享表多出一列」是否容忍（JBE-02 同款问题）；不容忍则侧表承载。✅ **结论（2026-08-27 实测）**：`DatabaseSchemaVerifier.verifyTable` 只逐一检查期望列的存在性/类型，不拒绝额外列——共享表运行期加列是安全的；但 identity 的 IT 里 `app_users` 由 `@BeforeAll` 手工建表（晚于本服务 Flyway），故 **DDL 仍必须落自有旁表 `account_flag`**（V42 即按此实现），生产与测试两态均成立 | bootstrap 归属雷区（#47 JBE-02 教训）+ 测试基建顺序约束叠加的结果：查询可碰共享表、DDL 不可依赖其存在时序 |
| D15 | 端点全部挂在既有 `/api/organizations/{orgId}/**` 家族下（如 `POST .../accounts`、`POST .../accounts/{accountId}/suspend|restore|review`），不新增 edge 前缀 | 新前缀不注册 RouteManifest 就是 404；旧家族天然注册过 |

## 边界

- **不做**：手机号通道（平台注册模型是邮箱，`RegisterRequest(email, password, displayName, verificationCode, initialIdentity)`，无手机字段）；短信触达；主动令牌吊销（D13）；成员表加状态列（D4）；单身份限制（同 #47 D10 记独立 epic）；改造或下线 invitation 流。
- **不动**：`StoreAuthorization` 的隐式继承规则（org owner/admin 隐式视为全部门店 MANAGER）；`StoreMembershipController` 现有契约（新增能力走新控制器，不在旧文件上做行为变更）；现有三级准入（permissionTier）与成员管理正交。
- **兼容**：通路 1/2 的存量行为逐字节不变是每片的自检断言；存量成员无 must_change 标记，行为不变。

## 验收标准（整体）

1. **直建闭环**：org admin 在工作台三次点击内建出一个「店长」子账号，拿到一次性初始密码；本人首登被迫改密，改密后业务功能全部可用。
2. **免审默认**：全新组织不开任何开关时，店长加员工/停用/恢复全部即时生效且流程中不存在任何审批动作；事后各收到一条站内通知。
3. **开审模式**：开启开关后店长新建 staff 为 pending_review，店长与本人的所有门店操作被拒；admin 过审后本人可登录，驳回后该账号彻底不可登录且不出现在任何列表。
4. **冲突护栏**：向已存在 email 建号得到 409 与两个选项；确认关联后既有账号密码不变、以成员身份出现。
5. **四守卫**：停最后一个 active 店长被拒；停 owner 被拒；停自己被拒；重复挂关系 409——各有锁定测试。
6. **停用真实性**：suspended 账号的**存量有效会话**下一个请求即 403/401，不仅挡新登录（验收改不了这个就是 D13 没做完）。
7. **降级安全**：`member_review_required=false` 与 `must_change_password=false` 组合下，登录、成员增删、AI 中心、任务流与今天逐字节一致（本条是回归底线，必须有对照 IT）。
8. **审计完整**：三类 outbox 事件在对应操作后均可查到，payload 字段齐。
9. **门禁全绿**：identity-service Java 测试 + 前端 test/typecheck/build 绿；CI 全量绿。

## 代码库陷阱清单（必读）

- **Java 构建**：JDK 25 显式路径 `JAVA_HOME=/opt/homebrew/opt/openjdk@25`（`java_home -v 25` 会静默回落 JDK 8）；全量 IT OOM 先查堆（已设 2g）
- **Reactor**：`switchIfEmpty` 参数装配期求值，副作用包 `Mono.defer`——`StoreAuthorization` 现有代码就是这个写法，扩展 roleOf 时别拆掉
- **Reactor Void 空信号歧义（本次新踩，两处实锤）**：`Mono<Void>` 成功完成 = 空信号，与「上游没发射」对下游 **不可区分**。①service 权限分支里成功路径的 `Mono.empty()` 被外层第二个 `switchIfEmpty` 误判为「无角色」，重入店长分支报权限不足——判定类链路用 `hasElement()` 收敛成恒发射 Boolean 再 flatMap，别让 Void 直接进 switchIfEmpty；②WebFilter 里 `chain.filter(exchange)` 也是完成即空，挂在 `switchIfEmpty(匿名兜底)` 下会让**每个已认证请求被二次放行**（FailureAfterResponseCompletedException）——每条分支以 `thenReturn(TRUE)` 收敛成哨兵值，`switchIfEmpty` 只服务真正的匿名空。凡看到「Void 链 + switchIfEmpty 兜底」组合都要先问一句：这个空是哪来的
- **Jackson record 陷阱**：Boolean 派生态 getter 别写 `isXxx()` 形参方法被当属性序列化（历史 bug：写库读回报「数据损坏」500）；请求 record 可选数值字段必须包装类型
- **迁移幂等**：一律 `ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS`，否则重放挂；迁移号先 `ls` 再写
- **共享表 DDL 时序（D14 结论）**：identity 的部分 IT（LoginControllerIT/MeControllerIT 等）自备容器 + 手工建共享表（identity-test-schema.sql 或 @BeforeAll），晚于 Flyway——本服务迁移可以 SELECT 共享表，但**不能 CREATE/ALTER 依赖它们存在**；新增共享表依赖时必须同步补 `identity-test-schema.sql`
- **授权治理清单**：identity 新增任何 Controller 必须登记 `IdentityAuthorizationManifest`（含方法级覆写），否则 `IdentityAuthorizationManifestTest` fail-closed——这是刻意的门，绕不过去就对了
