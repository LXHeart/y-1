# 草场任务书 #46：组合付费（佣金 + 霸王餐押金同任务）

> 来源：2026-08-20 全量盘点缺口 A3；ADR-D12 D1「组合模式后置」的后置项；改动面调研 2026-08-20 完成。
> 状态：2026-08-20 立项并同日实现。

## 目标

放开「赏金与霸王餐押金不可同设」的 v1 XOR：同一任务可同时配置 `bountyCents`（商家出资赏金腿）与 `freebieDepositCents`（推荐官预付押金腿）。两腿资金方向、账本、生命周期完全独立，靠同一 `engagementRef`（applicationId）关联。

## 决策表（定死）

| # | 决策 | 依据 |
|---|---|---|
| D1 | 组合语义 = 两腿正交：bounty 腿沿用 funds_reservation（商家预留→确认 capture 分账推荐官）；freebie 腿沿用 freebie_escrow（推荐官钱包预付→达标全额退）。finance 两表 DB 层天然允许并存 | ADR-D12 方向矩阵论证同构 |
| D2 | **阶梯佣金仍互斥押金**：`requirements.commissionLadder != null && freebieDepositCents > 0 → 400`（原 XOR 收窄为 ladder×deposit；ladder×组合不改）。前端 commission-ladder 校验与禁用保持 | 阶梯结算计划（D-02）只对 bounty 腿定义，押金叠加语义未定义 |
| D3 | 预留 Saga：`AcceptanceCommand`/`AcceptanceInput` 增 `freebieAmountCents`（`amountCents` 语义收窄=bounty 腿金额）；`reserveFunds` activity 内先 bounty reserve 后 freebieReserve；任一失败整 Saga 补偿（反向：先 freebieRefund 后 release，按已成功腿） | 单 activity 两腿顺序执行，不新增 Saga 步（Temporal 重试幂等键在 finance 侧兜底） |
| D4 | 结算（SettlementExecution 唯一钱侧入口）：freebie 不再短路——履约确认 = `freebieRefund`（退押金）+ bounty 腿照常（0 档 release / 固定 capture / 阶梯 capture(declared)）。先退押金后 capture；freebieRefund 幂等（409→成功）保证重试安全 | 现短路 return 会让组合任务 bounty 永不结算 |
| D5 | 商家取消（TaskController.refundOnCancel）：两腿都退（freebieRefund + release）；`refundDirection` 三值 `merchant/recommender/both` | 单值假设破坏 |
| D6 | finance 对账（EscrowLifecycleService.reconcile）：bounty 腿存在则按原矩阵对账；**freebie 腿存在也对账**（原「reservation 存在则不碰 freebie」回落逻辑改为两腿各自 reconcile）；两表皆缺保留 `reservation_missing` 契约 | 争议终局两条腿都要落定；ReservationReconciliationIT 锁的契约不变 |
| D7 | 统计口径不变：`reservedBountyCents`/`settledBountyCents` 只算 bounty 腿（组合任务押金不入这两个指标） | 展示口径与 PRD §2.4 任务花费统计对齐 |
| D8 | DB：V45 `ALTER TABLE task DROP CONSTRAINT IF EXISTS chk_task_funding_xor`（重放安全）；冻结快照/`task_application` 双列快照已带两值，零改动 | V40 注释预留的组合模式路径 |
| D9 | 前端：MerchantTaskForm 移除 bounty×deposit 双输入互斥禁用（ladder×deposit 禁用保留），hint 改「可组合：赏金由商家出资，押金由推荐官预付、达标全额返还」；大厅徽标同显（赏金标签+押金徽标） | 输入互斥是纯 UX 拦截 |
| D10 | `TaskFunds.fundsOrZero` 废弃删除（唯一 XOR 单值假设）；`isMonetary`/`bountyOrZero`/`freebieDepositOrZero` 不变 | 拆分控制器批次立下的资金判定收敛点 |

## 边界

- 不做：押金部分扣减（履约不达标的押金处置仍走争议对账 compensate/refund 矩阵）；组合任务的手续费合并口径（两腿各按各自费则）；`fundsOrZero` 语义的历史 ledger 修正（新逻辑只向前）。
- 通知：`EngagementRefunded` 带 `refundDirection=both`；既有消费方按字符串透传，无破坏。

## 锚点（实现顺序）

1. marketplace 契约：4 个 DTO（CreateTaskRequest/CreateDraftRequest/UpdateTaskRequest/ReviseTaskRequest）XOR→ladder×deposit 收窄；V45 迁移；TaskFunds 拆双值。
2. 预留链路：AcceptanceCommand/AcceptanceInput/starter/activity 双腿；compensate 双腿。
3. 结算链路：SettlementExecution 双腿；TaskController 取消双腿 + refundDirection 三值。
4. finance：reconcile 两腿化。
5. 前端：MerchantTaskForm/commission hint/测试。
6. 测试改写：FreebieEscrowFlowIT（XOR→组合 200 + accept 双腿 + 结算双腿 + 取消 both）；finance ReservationReconciliationIT 补组合对账；前端 freebie 测试反转断言。

## 验收

1. `POST /api/tasks` bounty+deposit 同 >0 → 201/200（发布成功）；ladder+deposit → 400「阶梯佣金不能与霸王餐押金同时启用」。
2. 组合任务 accept → 202：finance `reserve`（bounty）与 `freebieReserve`（deposit）都发生；余额不足任一腿 → 补偿回 pending，已成功腿退款。
3. 组合任务确认履约 → `freebieRefund` + `capture`（或 0 档 release）都发生；`EngagementSettled` 落 outbox。
4. 商家取消已接受组合报名 → `freebieRefund` + `release` 都发生，`refundDirection=both`。
5. 争议终局 `reconcile`：组合 engagement 两腿按 finalDecision 各自落定；两表皆缺 → `reservation_missing` 不变。
6. 全量门禁：marketplace + finance `test` 绿；前端 vitest + typecheck + lint 绿。
