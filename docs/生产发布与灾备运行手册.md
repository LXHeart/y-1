# 生产发布与灾备运行手册

本文对应 GL-P3-PLATFORM-001，规定当前 Compose 生产候选栈的可观测性、密钥、发布、回滚和备份恢复操作。Kafka/Temporal 的生产拓扑和验收要求见 [生产 Kafka 与 Temporal 部署方案](生产Kafka与Temporal部署方案.md)。

已在任一发布环境应用的 Flyway migration 必须保持字节级不可变，包括注释。`platform-java/deploy/released-migrations.sha256` 记录已发布文件，`scripts/validate-released-migrations.sh` 在 CI 与生产发布门禁中校验 SHA-256；任何 schema 或说明变更都必须新增 migration 或修改普通文档，禁止改写历史文件或用自动 `flyway repair` 掩盖漂移。

## 一、生产边界

- 公网只暴露 TLS 终止后的 frontend/Edge 入口；Prometheus、Alertmanager、Grafana 和各 Java 服务 management 端口保持私网。
- 真实 PSP 仍受 D-01 渠道准入门禁约束。未接真实渠道时，只能验证内部账务和模拟支付状态。
- 基础 Compose 的单 broker Kafka 与 `start-dev + SQLite` Temporal 只用于开发。生产发布脚本固定叠加 `docker-compose.production.yml`，应用仅连接外部 HA Kafka/Temporal，本地开发实例不会进入生产启动依赖。
- 回滚只恢复应用镜像和路由配置，不自动逆向 Flyway migration。数据库变更必须采用 expand/contract，旧版本须能读取新 schema。
- Redis 中的身份断言 replay key 是短期防重放状态，不纳入业务备份。

## 二、密钥管理

真实密钥由 Vault、云 Secret Manager 或 SOPS 在部署机临时物化。仓库只保留 production-secret-contract.csv 与两个 example 文件。

生产前执行：

~~~bash
chmod 600 /run/secrets/grassland/alertmanager-webhook-url
chmod 600 /run/secrets/grassland/grafana-admin-password
scripts/validate-production-secrets.sh --env-file /run/secrets/grassland/production.env
~~~

生产环境至少需要：

- `PUBLIC_FORWARDED_PROTO=https`，且 `SESSION_COOKIE_SECURE` 不得为 `never`；Nginx 据可信协议配置发送 HSTS。
- Redis replay 防护开启。
- MinIO root 凭据只用于 bootstrap，运行服务使用不同的受限 service account。
- ALERTMANAGER_WEBHOOK_URL_FILE 和 GRAFANA_ADMIN_PASSWORD_FILE 指向权限不高于 0600 的真实文件，不得指向仓库 example。
- 身份断言 17 对密钥及 access-token 签发/验签配置一致。
- Kafka 使用外部 bootstrap、`SASL_SSL + SCRAM-SHA-512` 和只读 PKCS12 truststore；Temporal 使用独立 namespace、HTTPS/mTLS 与权限不高于 0600 的客户端私钥。

轮换 access token 或断言密钥时执行三阶段流程：

~~~bash
scripts/rotate-identity-keys.sh plan-access-token access-token-202608
scripts/rotate-identity-keys.sh plan-assertion EDGE_USER_FINANCE edge-user-finance-202608
~~~

先把新 key 放入 verifier 的 previous slot，再滚动 signer/current verifier，等待 TTL + leeway 后移除旧 key。每阶段都重新执行 validate-production-secrets.sh，禁止单边直接替换。

三阶段真实滚动和回退验证完成后，将不含 secret 的结果整理为 `identity key rotation evidence v1`，再执行发布门禁：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env key-rotation-promote \
  --release-id 2026-08-13.1 \
  --rotation-evidence /secure-drills/2026-08-13/access-token-rotation-evidence.txt \
  --rotation-max-age-seconds 604800
~~~

校验器要求 old/new `kid` 不同、三阶段严格顺序、Phase 2 后完整等待 TTL + leeway、每阶段配置验证和回退检查均通过，且旧 key 已退休。证据只记录 key id 和状态，绝不能记录 key material；`key-rotation-promote` 还会重新执行生产 secret contract 校验。

## 三、可观测性

启动私网观测栈：

~~~bash
ALERTMANAGER_WEBHOOK_URL_FILE=/run/secrets/grassland/alertmanager-webhook-url \
GRAFANA_ADMIN_PASSWORD_FILE=/run/secrets/grassland/grafana-admin-password \
docker compose --profile observability up -d prometheus alertmanager grafana
~~~

Prometheus 抓取 Edge、Identity、Marketplace、Finance、Trust、Intelligence 六个 Java 服务。Grafana 自动加载 Platform Overview，包含服务存活、HTTP 请求/5xx、JVM heap 和 process CPU。统一规则覆盖：

Edge 在公网边界统一生成或规范化 `X-Request-Id`、W3C 32 位 `X-Trace-Id` 和 `X-Correlation-Id`，并将三者回传响应、透传给 Java 上游及内部身份断言。非法、超长或全零 trace 值会被替换。六个 Java 应用服务均已引入 Spring Boot OpenTelemetry starter，并统一声明只消费/生成 W3C Trace Context；本地默认关闭 tracing/OTLP trace export，采样率由 `OTEL_TRACING_SAMPLING_PROBABILITY` 控制。Boot starter 同时带入的 OTLP metrics exporter 已显式关闭，指标继续由 Prometheus 抓取，避免应用默认连接 `localhost:4318`。Identity/Marketplace 的 Kafka consumers 和五个 Kafka producers 已显式开启 Spring Kafka observation，允许 W3C trace context 随消息传播。Marketplace/Trust 已接入 Temporal 官方 OpenTracing bridge：Spring OTel tracer 通过官方 client/worker interceptors 跨 workflow/activity 边界传播。`scripts/local-otel-trace-smoke.sh` 已验证本地 collector 的 OTLP/HTTP receiver 到 debug exporter 的真实 delivery；这不是生产证据。生产 overlay 强制 `OTEL_TRACING_ENABLED=true`、`OTEL_EXPORT_ENABLED=true`，并要求 `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` 是显式、非本机的 HTTPS traces endpoint；缺失、HTTP、localhost 或采样率越界都会在 Compose 门禁 fail-closed。生产仍须部署真实 collector，保存真实 trace delivery evidence。

- 服务连续 2 分钟不可抓取。
- 5xx 比例连续 10 分钟高于 5%。
- JVM heap 连续 15 分钟高于 85%。
- process CPU 连续 15 分钟高于 90%。
- identity 邮件死信与 marketplace 运营死信领域规则。
- 五个领域服务 outbox 最老未发布事件超过 60 秒，并在服务可抓取但 outbox gauge 缺失时告警。
- Identity/Marketplace Kafka consumer lag 连续 5 分钟超过 1000，并在服务可抓取但 lag 指标缺失时告警。

生产部署需在私网 ingress 或 VPN 单独暴露 Grafana，不应把 3000/9090/9093 直接发布到公网。`production-release.sh` 的 preflight/plan/deploy/rollback 都执行 `scripts/validate-observability-config.sh`，静态校验六个 scrape target、六服务 OTel starter/W3C/opt-in 配置、核心/消息规则、secret-backed receiver 和 Grafana 面板。每次真实发布仍须检查 Prometheus target 全绿、规则 health=ok、Alertmanager receiver 可达并保存测试告警送达时间；静态校验不能替代真实告警或 trace 送达证据。

真实观测栈验收后，必须将 Prometheus 查询、Alertmanager 路由、receiver 送达和 resolved 通知整理为脱敏 evidence，再执行发布侧门禁：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env observability-promote \
  --release-id 2026-08-13.1 \
  --observability-evidence /secure-drills/2026-08-13/observability-evidence.txt \
  --observability-max-age-seconds 86400
~~~

校验器要求 alert firing、receiver、delivery、resolved、targets 和 smoke 均为 `passed`，时间顺序正确且证据新鲜；`observability-promote` 只校验记录，不触发测试告警、不修改观测栈。

## 四、发布

生产镜像变量必须固定到 repository digest，例如：

~~~dotenv
RELEASE_IMAGE_FRONTEND=registry.example/grassland/frontend@sha256:...
RELEASE_IMAGE_DATABASE_BOOTSTRAP=registry.example/grassland/database-bootstrap@sha256:...
RELEASE_IMAGE_EDGE_BFF=registry.example/grassland/edge-bff@sha256:...
RELEASE_IMAGE_IDENTITY_SERVICE=registry.example/grassland/identity-service@sha256:...
RELEASE_IMAGE_MARKETPLACE_SERVICE=registry.example/grassland/marketplace-service@sha256:...
RELEASE_IMAGE_FINANCE_SERVICE=registry.example/grassland/finance-service@sha256:...
RELEASE_IMAGE_TRUST_SERVICE=registry.example/grassland/trust-service@sha256:...
RELEASE_IMAGE_INTELLIGENCE_SERVICE=registry.example/grassland/intelligence-service@sha256:...
COSIGN_PUBLIC_KEY_FILE=/run/secrets/grassland/grassland-cosign.pub
MIGRATION_COMPATIBILITY_APPROVED=yes
FINANCE_RELEASE_APPROVED_BY=<审批人或工单号>
PUBLIC_HEALTH_URL=https://api.example.com/health
~~~

标准流程：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env preflight
scripts/production-release.sh --env-file /run/secrets/grassland/production.env plan --release-id 2026-08-11.1
scripts/production-release.sh --env-file /run/secrets/grassland/production.env deploy \
  --release-id 2026-08-11.1 \
  --backup-manifest /secure-backups/2026-08-11/manifest.txt
scripts/production-release.sh --env-file /run/secrets/grassland/production.env deploy \
  --release-id 2026-08-11.1 \
  --backup-manifest /secure-backups/2026-08-11/manifest.txt \
  --execute
~~~

`preflight`/`plan`/`deploy`/`rollback` 都会执行 `scripts/validate-production-compose.sh` 和 `scripts/validate-image-provenance.sh`：合并后的生产配置不能包含本地 Kafka/Temporal，必须保留外部 Kafka SASL_SSL/SCRAM truststore、Temporal HTTPS/mTLS、只读凭据挂载、七个应用 readiness gate，以及 Edge 等待领域服务 `service_healthy`；八个镜像必须是 digest、通过 cosign 签名和 SPDX attestation 验证，部署公钥由 `COSIGN_PUBLIC_KEY_FILE` 指向 Secret Manager/SOPS 物化的只读文件。`deploy` 必须提供已通过 `scripts/backup-restore-drill.sh verify` 的 `--backup-manifest`；未提供、缺 checksum、被篡改或版本未知都会 fail-closed。

生产 overlay 对 frontend、database-bootstrap、Edge 和五个 Java 领域服务统一声明 CPU/memory `limits` 与 `reservations`。默认值为 CPU limit `2.0`、memory limit `2G`、CPU reservation `0.25`、memory reservation `256M`，可由 `PRODUCTION_SERVICE_*` 环境变量按容量评审覆盖；`validate-production-compose.sh` 会校验合并后的每个服务均为正数和带单位内存值，缺失或非法配置直接 fail-closed。

不带 `--execute` 只做预演。真正执行前会重新校验密钥、外部 Kafka/Temporal 契约、migration 兼容性审批、finance 人工审批、生产 Compose 语义和镜像 digest；执行时把旧容器 image ref、image ID、repo digest 写入被 git 忽略的 `.release-state/<release-id>/`，复制已校验的 backup manifest，然后等待应用 readiness 和 `PUBLIC_HEALTH_URL`。公网 health 通过后自动运行只读 smoke：`/health`=200、`/internal` 与 `/api/internal`=404、未知 `/api`=404、匿名 `/api/tasks/feed`=401；只有显式提供短时 `RELEASE_SMOKE_ACCESS_TOKEN` 才追加认证 Marketplace feed 读取，未提供时明确标记为 skipped，不冒充完整业务验收。

发布完成后至少手工验证登录、任务读取、余额只读、媒体读取，并观察 15 分钟 5xx/CPU/heap。涉及真实 PSP 时还需在 PSP 沙箱验证支付、退款、分账、提现、Webhook 和对账各一笔。

## 四点五、视频生产证据晋级门禁

视频 Webhook 与归档演练会生成两份脱敏证据，但演练证据不等于晋级证据。正式晋级前必须由同一 Job、同一 provider 和同一维护窗口产生两份文件，并由校验器验证版本、字段完整性、时间新鲜度、Job 关联、单调进度、Finance authority、私有对象下载摘要和货币换算策略版本。`policy_missing` 或 `passed_with_monetary_policy_pending` 只能留作技术演练记录，不能进入正式晋级。

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env promote \
  --release-id 2026-08-13.1 \
  --webhook-evidence /secure-drills/2026-08-13/video-webhook.txt \
  --archive-evidence /secure-drills/2026-08-13/video-archive.txt \
  --job-id <production-drill-job-uuid> \
  --provider seedance \
  --max-age-seconds 3600
~~~

未显式提供 `--policy-version` 时，脚本使用 `--env-file` 中已校验的 `FINANCE_CREDITS_CENTS_POLICY_VERSION`。该命令只校验证据并输出晋级门禁结果，不切流量、不修改容器。校验失败时必须重新执行真实 provider/对象存储演练；禁止手工编辑证据绕过门禁。证据目录应由维护工单引用并至少保留一个发布周期，访问令牌、Webhook secret、签名 URL 和完整 provider payload 不得写入文件。

CI 的 `image-security` job 会先初始化 Docker Buildx 并执行 daemon/builder 预检，再构建 frontend、database-bootstrap、Edge 和五个 Java 领域镜像；固定版本 Trivy 阻断全部 HIGH/CRITICAL 漏洞，为每个镜像上传 SPDX JSON SBOM，并在上传前校验八份漏洞报告、八份 SPDX JSON 和签名状态文件完整且可解析。2026-08-13 本地缓存基线（`IMAGE_SECURITY_PULL=false`）已生成八份报告并清零 HIGH/CRITICAL；其中 Intelligence 运行时已切换到 Temurin 25 Alpine，并保留 Chromium/FFmpeg/Playwright driver。该本地结果不替代 CI 的 `--pull` 新鲜基础镜像扫描。镜像签名不在未推送 registry 的构建阶段伪造；发布系统必须在生成不可变 registry digest 后接入 cosign/attestation，并把签名验证作为 production preflight 的后续部署门禁。真实 registry digest、签名和 SPDX attestation 仍未完成。

## 五、Canary 发布门禁

Canary 目前由 `scripts/production-canary-plan.sh` 生成只读 dry-run 计划，不会修改流量、容器或路由。生产操作人必须在已批准的 ingress/LB 工单中执行实际流量切分，并在每个 hold point 保存 Prometheus 查询结果和审批记录：

~~~bash
scripts/production-canary-plan.sh plan \
  --release-id 2026-08-13.1 \
  --service edge-bff \
  --canary-image registry.example/grassland/edge-bff@sha256:<64hex> \
  --baseline-image registry.example/grassland/edge-bff@sha256:<64hex> \
  --public-health-url https://api.example.com/health \
  --prometheus-url https://prometheus.example.com \
  --output /secure-drills/2026-08-13-canary.txt
~~~

计划阶段固定为 0% warm-up 5 分钟、1% 至少 10 分钟、10%/25%/50% 各至少 10 分钟，再经 incident commander 批准提升到 100%。每个阶段都要记录 canary/baseline 的 5xx、p95、JVM、readiness、outbox age、consumer lag、依赖错误率、告警送达和只读 smoke 结果。5xx 超过 5% 连续 2 分钟（或高于基线 2 个百分点）、p95 超过 2 秒连续 2 分钟（或高于基线 50%）、readiness/依赖/安全/资金对账异常时立即停止扩容，按计划将流量切回 baseline digest。不得自动逆向数据库迁移；真实 canary、TLS/LB、告警送达和 RTO/RPO 仍需部署侧证据。

canary 实际切流完成后，操作人必须按固定 v1 字段生成脱敏 evidence（不得把上面的 dry-run plan 当 evidence），再执行机器晋级门禁：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env canary-promote \
  --release-id 2026-08-13.1 \
  --evidence /secure-drills/2026-08-13/canary-evidence.txt \
  --service edge-bff \
  --canary-image registry.example/grassland/edge-bff@sha256:<64hex> \
  --baseline-image registry.example/grassland/edge-bff@sha256:<64hex>
~~~

校验器要求 warm-up、1%/10%/25%/50%/100% 每个 hold point 均通过且至少满足规定时长，readiness、依赖、Finance 对账、告警送达、smoke 和 rollback-ready 均为 `passed`；超过 5xx 或 p95 abort 阈值、证据过期、digest 错配或重复字段都会 fail-closed。`canary-promote` 只验证记录，不执行切流。

## 六、失败回滚

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env rollback \
  --release-id 2026-08-11.1
scripts/production-release.sh --env-file /run/secrets/grassland/production.env rollback \
  --release-id 2026-08-11.1 \
  --execute
~~~

先审查生成的 rollback.compose.yml，再执行。脚本使用发布前记录的 repo digest/image ref 和 --no-build 恢复旧容器，并再次等待公网 health。若新 migration 破坏旧版本兼容性，停止自动回滚并按数据库事故流程处置；禁止对生产库直接执行手写逆向 DDL。

## 七、备份与恢复演练

备份依赖 pg_dump 和 mc，输出 PostgreSQL custom dump、MinIO 文件镜像和 SHA-256 manifest：

~~~bash
DATABASE_URL=postgresql://... \
MINIO_ENDPOINT=https://minio.internal \
MINIO_ACCESS_KEY=... \
MINIO_SECRET_KEY=... \
MINIO_BUCKET=grassland \
scripts/backup-restore-drill.sh backup --destination /secure-backups/2026-08-11

scripts/backup-restore-drill.sh verify \
  --manifest /secure-backups/2026-08-11/manifest.txt
~~~

恢复只能指向隔离环境：数据库 host 必须是 localhost 或名称包含 restore/drill/staging，且目标 bucket 必须以 grassland-restore-drill- 开头。命令默认 dry-run：

~~~bash
scripts/backup-restore-drill.sh restore \
  --manifest /secure-backups/2026-08-11/manifest.txt \
  --target-database-url postgresql://restore_user:...@restore-db.internal/grassland_drill \
  --target-bucket grassland-restore-drill-20260811

scripts/backup-restore-drill.sh restore \
  --manifest /secure-backups/2026-08-11/manifest.txt \
  --target-database-url postgresql://restore_user:...@restore-db.internal/grassland_drill \
  --target-bucket grassland-restore-drill-20260811 \
  --execute
~~~

执行恢复使用 pg_restore --clean --if-exists --no-owner，MinIO 镜像写入显式目标 bucket，完成后查询 app_users 和 organization 基本行数。演练还要抽查登录、任务、资金台账只读一致性和媒体对象下载；不得对恢复环境触发真实 PSP、邮件、短信或推送。

## 九、外部依赖故障演练计划

在任何真实视频演练前，先执行不打印值的输入检查。它会拒绝 Sandbox、占位 provider、缺失公网地址、缺失对象存储配置和未批准的 Finance credits↔cents policy：

~~~bash
scripts/validate-video-production-drill-inputs.sh --env-file /secure/prod/grassland.env
~~~

该检查通过只表示凭据和配置文件存在且满足基本格式，不代表 provider、MinIO、公网入口或 Finance 已完成真实联调。

故障演练先生成计划，不由仓库脚本直接切断生产网络或权限：

~~~bash
scripts/production-failure-drill.sh plan \
  --scenario kafka-unavailable \
  --drill-id 2026-08-13-kafka-01 \
  --output /secure-drills/2026-08-13-kafka-01.txt
~~~

支持 `kafka-unavailable`、`temporal-unavailable`、`minio-unavailable`、`video-provider-unavailable`、`readiness-failure`。计划固定包含前置条件、注入范围、观测指标、恢复步骤、终止条件和证据清单；实际注入命令必须由基础设施负责人在批准的维护工单中填写并执行。Kafka/Temporal/MinIO 的真实 ACL、网络、证书、跨区恢复和告警送达仍须在部署环境完成并记录实测 RTO/RPO。

真实故障注入和恢复完成后，必须将实测结果整理成 `failure evidence v1`，再执行发布侧恢复门禁。计划文件不能直接晋级：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env failure-promote \
  --release-id 2026-08-13.1 \
  --failure-evidence /secure-drills/2026-08-13/kafka-failure-evidence.txt \
  --failure-scenario kafka-unavailable \
  --failure-max-age-seconds 604800
~~~

校验器要求故障注入/恢复时间顺序正确，注入、恢复、告警送达、readiness、smoke、数据一致性、Finance 对账和回滚准备均为 `passed`，并记录非负实测 RTO/RPO。`failure-promote` 只验证记录，不注入故障、不切流量；证据过期、场景错配、重复字段、告警缺失或 secret 被记录都会 fail-closed。

### 视频 provider 公网 webhook 演练

先为真实 provider 创建一个专用、可由操作人查询且尚未终态的视频 Job，确认 `provider_task_id` 已写入，并在短时演练窗口内暂停该 Job 的 provider polling 或确认不会竞争更新。先生成不发送请求的计划：

~~~bash
scripts/video-webhook-drill.sh plan \
  --base-url https://api.example.com \
  --provider minimax \
  --provider-task-id PROVIDER_TASK_ID \
  --job-id JOB_UUID \
  --drill-id 2026-08-13-video-webhook-01 \
  --output /secure-drills/2026-08-13-video-webhook-01-plan.txt
~~~

将与生产 `VIDEO_GENERATION_WEBHOOK_SECRET` 相同的值和 owner 短时 access token 分别写入部署主机上的 0600 文件。不要把二者放进命令行、仓库或演练证据。审批后显式执行：

~~~bash
scripts/video-webhook-drill.sh run \
  --base-url https://api.example.com \
  --provider minimax \
  --provider-task-id PROVIDER_TASK_ID \
  --job-id JOB_UUID \
  --drill-id 2026-08-13-video-webhook-01 \
  --access-token-file /run/secrets/grassland/drill-owner-token \
  --secret-file /run/secrets/grassland/video-webhook-secret \
  --output /secure-drills/2026-08-13-video-webhook-01-evidence.txt \
  --confirm-live-webhook-drill
~~~

脚本依次验证有效 80% 回调、完全相同事件的重放、新事件携带迟到 20% 进度、owner-scoped Job 查询仍保持 `processing:80`，以及坏签名必须返回非 2xx。证据文件只记录状态码、事件 ID、最终状态/进度和时间戳，不记录 token、签名或 secret。工单还必须附 ingress 日志、inbox claim 数、Job/AI Run/补偿对账、告警送达和演练后 polling 恢复结果。只有真实公网入口执行结果才可作为 B5 生产证据；仓库内 mock 契约不能替代该证据。

### 视频归档与 Finance 权威 operation 对账演练

真实 provider Job 完成并归档后，先生成只读演练计划：

~~~bash
scripts/video-archive-reconciliation-drill.sh plan \
  --base-url https://api.example.com \
  --job-id JOB_UUID \
  --drill-id 2026-08-13-video-archive-01 \
  --output /secure-drills/2026-08-13-video-archive-01-plan.txt
~~~

将 Job owner 与 platform admin 的短时 access token 分别放入 0600 文件。审批后执行：

~~~bash
scripts/video-archive-reconciliation-drill.sh run \
  --base-url https://api.example.com \
  --job-id JOB_UUID \
  --drill-id 2026-08-13-video-archive-01 \
  --owner-token-file /run/secrets/grassland/video-owner-token \
  --admin-token-file /run/secrets/grassland/platform-admin-token \
  --output /secure-drills/2026-08-13-video-archive-01-evidence.txt \
  --confirm-live-archive-drill \
  --ack-monetary-policy-missing
~~~

演练要求管理员对账中的指定 Job 为 `consistent`、Finance 权威 `credits_consume_operation` 为 `consumed`，owner 下载端点签发 HTTPS URL，且实际对象下载非空、不超过 200 MiB；证据只保存对象大小和 SHA-256，不保存 token 或签名 URL。Finance 当前积分含 paid 与免费 quota 两种来源。只有所有版本化 policy 字段都通过校验时，报告才返回对应的 `monetaryConversionState=<policy-version>`；否则返回 `policy_missing`，脚本必须显式要求 `--ack-monetary-policy-missing` 并输出 `passed_with_monetary_policy_pending`。即使 policy 已配置，本演练也不自动执行金额换算，仍需 Finance 产品批准后才能标记金额层完成。这证明 operation ID、账号、feature、consume/compensation fence 与 Intelligence cents 计量可以联合审计，不代表积分金额已经按某个比例折算成功。
