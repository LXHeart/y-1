# 草场工作台 UI 实测清单

> 至今所有 e2e 都走 HTTP 层（curl），**Vue 组件的渲染与交互从未在真实浏览器中跑过**。
> 类型检查与构建只能保证「代码合法」，保证不了「点了有反应」。本清单覆盖只有真浏览器能暴露的问题。

## C. 异步 202 轮询 —— **最需要人眼看的部分**

这几条是 UI 与后端语义差异最大的地方：接口返回 202，真实结果靠轮询。

| # | 操作 | 预期 | 结果 |
|---|---|---|---|
| C1 | 切回商家 → 点报名行的「接受」 | 「结果」列先显示 **「处理中…」** | ✅ |
| C2 | 等 1–3 秒 | 自动变为 **「已接受（资金已预留）」**，无需手动刷新 | ✅ 修缺陷 4 后 |
| C3 | 观察余额 | 从 ¥10000 扣为 **¥9500**（预留 ¥500） | ✅（本轮基数 ¥9700→¥9200） |
| C4 | 点「确认履约」 | 先「结算中…」→ 数秒后「已结算（资金已确认扣款）」 | ✅ |
| C5 | 轮询期间按钮状态 | 处理中时按钮 **disabled**（不可重复点击） | ✅ |

**C 组实测时间线**（DOM 采样器每 50ms 快照；轮询期间**零额外请求**，避免上轮探测 fetch 干扰时序的问题）：

接受（¥500 任务，余额 ¥9700 起）：

| t | 状态 | 结果列 | 按钮 | 余额 |
|---|---|---|---|---|
| 0ms | 待处理 | — | 接受✓ 拒绝✓ | ¥9700 |
| +0.2s | 待处理 | **处理中…** | 接受✗ 拒绝✗ | ¥9700 |
| +1.75s | 已接受 | **已接受（资金已预留）** | — | ¥9700 |
| +1.85s | 已接受 | 已接受（资金已预留） | 确认履约✓ | **¥9200** |

确认履约：`结算中…`（按钮全程 disabled）→ **+5.9s** → `已结算（资金已确认扣款）`，
余额仍 ¥9200（capture 只翻状态，钱在 reserve 时已扣）。DB 对账一致：
`funds_reservation=captured/50000`、`balance_cents=920000`。

> ⚠️ C2/C4 若一直停在「处理中…」不动，是轮询逻辑问题（`pollReservation`/`pollSettlement`）。
> 若直接跳过中间态，说明后端返回过快，不算缺陷。

逐秒递减实录 29→28→27→…→17（每档间隔 1000±3ms）。
**D7–D9 计票条**：1 票 14% → 2 票 29% → 3 票 43% → 4 票 **57%**（按面板 7 人算宽度），
第 4 票时底部文案由「尚无一方过半（平票将重开下一轮）」翻为 **「已过半：商家方胜诉」**（4×2>7）。
**D8**：judge1 第二次改投「支持推荐官」，计票**不变**（商家方 1 / 已投 1）——每官每轮一票不可改。

**额外实证（时间驱动主链路，浏览器内首次跑通）**：投票窗口到期 → workflow **自动 tally** →
状态转「已判决（上诉窗口内）」、判决「商家方胜诉」，倒计时**自动切到「上诉窗口」**；
当事方点「对判决提起上诉」→「已上诉（待客服终审）」，倒计时行随之消失（窗口 phase→none）。

- **F2**：所有 `/api/*` 均带 `cookie: y1.sid=…`，`sec-fetch-site: same-origin`（dev proxy 经 edge-bff），无 CORS。
- **F3**（真机 375×812 模拟）：`documentElement.scrollWidth == clientWidth`，**零元素越界**；

  靠压缩换行自适应。实测三张表 min-content 宽 174–203px «« 卡片内宽 353px，**当前列数下不可能溢出**，
  故未修；若后续加宽列（长标题/多列），需补 `overflow-x:auto` 包裹层。
- **F5**：真人双击节奏（间隔 80ms）**能正确拦截**——首次点击后 16ms（一帧）按钮即 disabled，80ms 时仍 disabled。
  ⚠️ 但**同一 tick 内连点 5 次会发出 5 次请求**：Vue 的 `disabled` 是异步 flush 的，
  同步点击风暴跑在它前面。人手无法造出这种时序（需程序化触发），故记录不修；
  真要根治需在 composable 里加 in-flight 去重，而非依赖 UI 层 `:disabled`。

## 浏览器实测发现并修复的缺陷（2026-07-26，chrome-devtools 驱动）

实测进度：**A–F 六组全部跑完**（共 7 个缺陷，全部已修）。
第一轮（A/B 组）修了 1–3；第二轮（C/D/E/F 组）修了 4–7。

| # | 缺陷 | 现象 | 根因 | 状态 |
|---|---|---|---|---|
| 1 | **首次进入工作台数据全空** | 余额显示 `¥—`，账户/任务接口全 403「需要商家身份」 | `onMounted` 直接拉数据，未先激活活动身份。新登录 session 是「消费者」，只有点视角切换才会激活 | ✅ 已修 |
| 2 | **视角切换 UI 与后端不一致** | UI 切到「推荐官视角」，后端仍是 merchant，报名 403「需要推荐官身份」 | `switchSide` 不检查 `activateIdentity` 返回值，失败仍切 UI。账号未开通 recommender 档案时后端 409 | ✅ 已修（失败回滚 UI + 自动尝试开通） |
| 3 | **任务列表不刷新** | 后端 3 个任务，UI 只显示 2 个 | `loadOrganizations` 只在「首次选中组织」时拉任务；`App.vue` 用 `<component :is>` 复用组件，重进标签页不重拉 | ✅ 已修（无条件刷新） |
| 4 | **202 轮询在竞态窗口提前收工**（C2/C3） | 点「接受」后永久停在「处理中…」，余额也不更新；**后端其实全对**（已 accepted、已预留 ¥300） | `pollReservation` 判据是「≠reserving 即终态」。accept 返回 202 后 Saga 的 `beginAcceptance`(pending→reserving) 要几百毫秒才跑，这期间后端回 **`pending`** → 被当成终态，**只发了 1 次轮询就退出**，落到 `'处理中…'` 兜底文案 | ✅ 已修（判据改为「到达终态 accepted/compensated 才停」；`pollSettlement` 同款竞态 `not_confirmed` 一并修；补 4 条回归测试） |
| 5 | **启动审判后倒计时不出现**（D4） | 点「启动审判」后无倒计时，**必须手点一次「刷新」**才显形；上诉/终审后还会残留上一阶段的旧秒数 | `startAdjudication`/`appeal`/`submitFinalDecision` 各自直接 `snapshot.value = …`，只有 `refresh` 会重置 `remaining` 并起表 | ✅ 已修（抽 `applySnapshot()` 统一入口，快照与倒计时同步；终局无窗口时停表） |
| 6 | **审判官看不到自己要投的争议**（D6） | judge 填入争议 ID 后看板恒显示「无权查询该争议」，**投票按钮组根本渲染不出来** | `castVote` 用 requireJudge+面板成员放行，但 `getAdjudication` 只认「当事方 org / marketplace 服务」→ 审判官恒 403。**快照本就是脱敏的（D-10），审判官正是它的目标读者** | ✅ 已修（放行本轮面板成员；非面板推荐官仍 403，补 2 条 IT） |
| 7 | **客服看不到自己要覆盖的判决**（E1–E4） | 客服填入争议 ID 后看板显示「无权查询争议」，连「客服终审」折叠区都渲染不出来，**终审在 UI 上完全不可达** | `resolvePartyOrService` 只收 merchant/recommender/marketplace，客服（平台角色，无业务身份、无 org）被直接过滤 | ✅ 已修（resolver 放行客服 + 控制器允许客服跨 org；补 1 条 IT） |

### 第二轮的方法改进（解上轮「最终态没能干净捕获」）
上轮在轮询期间插入探测 `fetch` 观察状态，干扰了时序。本轮改为**点击前先装 DOM 采样器**
（`setInterval` 每 50ms 读 DOM、变化才记录，附 `performance.now()` 时间戳），
点击后**全程不发任何额外请求**，事后一次性取回轨迹。
结果不仅干净捕获了中间态，还直接定位到缺陷 4 —— 网络面板显示 accept 之后**只有 1 条**轮询请求，
证明是前端提前退出而非后端慢。

## 已在代码层面发现并修复的问题（无需浏览器即可确定）

1. **✅ 主题变量名全错**：组件用了 `--border-color` / `--tag-bg` / `--accent-color`，但项目实际是
   `--color-border` / `--color-surface-strong` / `--color-accent` —— **三个变量在项目里都不存在**，
   全部回落到 fallback 的浅色硬编码值。而**项目默认是深色主题**（`src/style.css` 用 `[data-theme="light"]` 切浅色），
   等于草场工作台在默认主题下配色是错的。已全部改为真实变量。
2. **✅ 按钮/输入框无文字颜色**：`background: transparent` 且未声明 `color`，深色背景下回落为浏览器默认黑字，
   几乎不可读。已补 `color: var(--color-text)` + 输入框底色 + 按钮 hover 态。
3. **✅ 告警/计票条硬编码浅色**：改用 `color-mix(in srgb, var(--color-danger) 14%, transparent)` 一类写法，
   深浅两色主题下都自适应。

> 上述三条本可在浏览器里一眼看出，但通过比对 `src/style.css` 的变量定义同样能确定 —— 仍建议 F4 复核实际观感。

## 浏览器确认结果（原「仍需确认的潜在问题」）

1. **D4 倒计时漂移** —— ✅ 已确认，行为正确。归零后显示「已到期，等待系统处理」并**停在该文案**（不变负数）；
   窗口到期后 workflow 自动 tally，看板随之转「已判决」。本地 tick 与 Temporal Timer 的秒级偏差未造成误判。
2. **B1 视角切换失败无提示** —— ✅ 第一轮已修（缺陷 2）：失败回滚 UI + 自动尝试开通，本轮切换全程无 403。
3. **C5/F5 重复点击** —— ⚠️ **部分确认**：真人双击节奏能正确拦截（16ms 内 disabled），

   受影响的**非幂等**操作：充值 / 创建组织 / 发布任务（accept·confirm·报名·投票·开争议后端均已幂等或去重）。
