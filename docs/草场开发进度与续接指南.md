## 一、项目定位

草场（Grassland）：连接商家与推荐官的营销内容撮合平台。
原为 Vue 3 + Express TypeScript 单体，正在按 **Strangler Fig 模式**渐进迁移到 Java 微服务。

- 旧库（根目录 `server/`、`src/`）：仍承载全部业务，**不要改动其行为**
- 新库（`platform-java/`）：草场领域新代码的落点
- 迁移安全机制：`edge-bff` 用 RouteManifest 逐路由切换，每条路由有 `enabled` 开关，可零重启回滚到 Express

### Epic 2 Slice 2K：BFF 内部身份断言签发（HLD 7.4）
- **共享契约模块 `platform-identity-assertion`**（镜像 platform-storage）：`IdentityAssertion` record（claims：account_id/active_identity_type/session_token/auth_method/auth_strength/reauthenticatedAt/request_id/trace_id/audience/issuedAt/expiresAt）+ `IdentityAssertionCodec`（Jackson + base64url，前向兼容忽略未知 claim）+ `IdentityAssertionSigner`（HMAC-SHA256 token `<payload>.<mac>`，`MessageDigest.isEqual` 常量时间比较，expiry+audience+leeway 校验，任何失败返回 empty 不抛）+ `IdentityAssertionProperties`（enabled 时强校验 secret）+ autoconfigure（signer bean，opt-in）
- **edge-bff 签发**：`EdgeR2dbcConfig`（@ConditionalOnProperty `edge.identity.from-database-url`，从 DATABASE_URL 派生只读 ConnectionFactory；排除 Boot `R2dbcAutoConfiguration` 自管，未启用时纯代理启动）+ `EdgeCookieSigner`（Node 兼容 unsign，局部不共享 identity bean）+ `SessionIdentityResolver`（cookie→sid→session.sess.user.id→app_users→identity_session.active_identity_type；任一空=匿名）+ `InternalAssertionFilter`（WebFilter：所有请求剥离 denylist 伪造头，仅内部 Java 上游签发并附加 `X-Grassland-Identity`，匿名/legacy 不附）+ `UpstreamResolver.isInternalUpstream`（命中 route 上游 ≠ legacy default）

### D-05 硬限额执行（跨服务小闭环，marketplace + finance）
- 背景：identity 2L 已定义三项额度策略（`PermissionQuotaPolicy`：`maxActiveTasks`/`maxMonthlyTasks`/`maxTxAmountCents`），但执行侧只做了第一项（4B 发布数量闸门）。本轮补齐另两项。
- **marketplace 发布侧**：`PublishQuotaPolicy` 从只暴露 `maxActiveTasks` 扩为三项全暴露（`maxMonthlyTasks` DRAFT=0/BASIC=20/FINANCE=500；`maxTxAmountCents` DRAFT=0/BASIC=0/FINANCE=10_000_000，与 identity 同值）+ `TaskRepository.countCreatedThisMonthByOrganization`（`created_at >= date_trunc('month', now())`，跨月自动重置无需定时清算）+ `TaskController` 闸门扩为 5 道：① org 归属 ② tier 可发布 ③ **资金型任务须有交易权限（bounty>0 且 maxTx=0 → 403）+ 赏金不超单笔上限（→409）** ④ 活跃数上限 ⑤ **本月新建数上限（→409）**。
- **finance 交易侧**：新 `FinanceTxQuotaPolicy`（finance 本地 tier→上限映射，无法 import identity 的 `PermissionTier`；未知/null 保守按 0）+ `EscrowController.reserve` 校验 `amountCents ≤ maxTxAmountCents`（超 → 409）。
- **关键决策——服务断言豁免**：marketplace Saga 的服务断言 `permissionTier=null`（`ServiceAssertionIssuer` 刻意不带 tier）。若在 finance 一刀切按 tier 拦截，`null→DRAFT(0)` 会**拦死 4F 的 `AcceptApplicationReservationWorkflow`**。故 reserve 闸门仅对终端商家用户断言执行，服务断言豁免——其金额已在 marketplace 发布任务时按同值 `maxTxAmountCents` 校验（两侧同值由单测锁定）。`EscrowControllerIT.serviceAssertionExemptFromTxCap` 专门锁住这条。
- **测试期语义修正（真实缺陷暴露）**：既有资金链路测试（4F Saga / 5A 结算 / 6A 争议）普遍用 `basic_publish` 建资金型任务、直调 escrow——那是「tier 只管发布数量、与资金无关」时期的写法，与 D-05 语义冲突，接闸门后 19 个测试红。修法是让测试用与语义相符的 tier（`ApplicationControllerIT.publishTaskBounty` + `EscrowControllerIT` 全部 escrow 操作改 `finance_transaction`），**而非放宽生产逻辑**——资金型任务本就该由可交易 tier 发起，这正是 D-05 要建立的约束。跨 org 403 场景与 `AccountControllerIT`（开户/查询，不涉交易额度）保持 `basic_publish` 不变，正好验证闸门未误伤。

### 审判 UI + 审判官池入口（解 6C 遗留缺口）
- **背景**：Slice 6C 建了完整审判能力，但 `judge` 表无 HTTP 入口 → `adjudicate` 恒 503；UI 也只做到「开争议」。
- **审判官池入口**（trust）：`POST /api/trust/judges`（推荐官自主报名，幂等 upsert；商家 403——不得自任裁判）+ `GET /api/trust/judges/me` + `DELETE /api/trust/judges/me`（软删 `active=false`，保留历史面板/投票完整性；再报名复活同一行）。`JudgeRepository` 加 `enroll`/`findByAccountId`/`deactivate`。
- **审判 UI**（`AdjudicationPanel.vue`）：状态/轮次/面板进度 + **计票条**（按面板满员算宽度，直观看出投票进度与过半线）+ 分角色操作区（审判官报名·投票 / 当事方上诉 / 客服终审）。挂在工作台「争议审判」卡片，开争议后自动填入争议 id。

#### ⚠️ e2e 联调抓到的架构缺陷（已修）
**`judge` 身份无法通过任何正常途径获得** —— identity 的 `IdentityType` 只有 `merchant`/`recommender`，
而 trust 的 `requireJudge` 要求断言 `activeIdentityType == "judge"`。真实链路下 `/api/me/identities` 拒绝 `type=judge`（400），
导致**投票端点恒 403**。Slice 6C 的 IT 直接 mint 带 `judge` 的断言，掩盖了这个集成缺口——**单测覆盖不到的跨服务不一致**。

修法（选定「trust 改用入池判定」，不动 identity 架构）：
- `requireJudge` 语义改为「推荐官」，**入池校验移至 `AdjudicationController.castVote`**（`filterWhen` 查 `judge.active`；放在 controller 而非 resolver，避免 `TrustCallerResolver` 依赖 repo）
- 语义变为 **审判官 = 推荐官 + 已入池**，符合 HLD 3.1「符合条件的推荐官」；入池/退池即权限开关
- 补 2 个回归测试：`voteRejectsJudgeNotInPool`（未入池 403）/ `voteRejectsJudgeWhoLeftPool`（退池后失权）；修正 `voteRejectsOpenDispute`（须先入池否则测不到 409 那条）

- **实跑验证**（真实容器）：7 个平台级审判官入池 → `adjudicate` **202 + 7 人面板**（此前恒 503）→ 4 名审判官投票 → 计票累计至 **`majority: for_recommender`**（4×2>7 达阈值）。另验证：唯一审判官与争议**同组织时被冲突排除** → 503（利益冲突逻辑实证）。
- 测试：trust 51→**60**（`JudgeControllerIT` 7 + 投票门禁回归 2 + 修正 1）；前端 449 全绿、typecheck/build 干净。
- **本轮未做**：**客服终审仍不可用**——后端要求断言 `reauthenticatedAt` 在 5 分钟内，但当前登录链路不产生该字段（edge-bff 签发时恒 null），UI 已做但会 403，已在界面显著标注。需补 MFA 重认证流程。

### MFA 重认证（identity V7 + edge-bff 断言透传）
- **背景**：trust 客服终审要求断言 `reauthenticatedAt` 在 5 分钟内，但 edge-bff 签发时**硬编码** `authStrength=level1` / `reauthenticatedAt=null` → 恒 403。
- **identity**：V7 迁移给 `identity_session` 加 `reauthenticated_at`/`auth_strength`（**按 session 记录**——一个设备重认证不提升另一设备权限，与活动身份同粒度）+ `POST /api/me/reauthenticate`（校验密码 → upsert 时间戳；用 upsert 而非 UPDATE，因 session 行是懒创建的，客服未必开通过业务身份）+ `LegacyUserLookup.findLoginUserById`（含哈希，与不带哈希的 `findById` 分开，避免哈希外泄到一般解析链路）。
- **edge-bff**：`SessionIdentityResolver` 读出两列（`SessionState` record）→ `ResolvedIdentity` 扩字段 → `InternalAssertionFilter` 签进断言（替换硬编码）。
- **安全**：密码错误与其它失败**统一返回 403「重认证失败」**，不区分，避免成为密码探测口。
- **实跑验证**：密码错 403 / 正确密码 200 返回 `{authStrength:"level2", reauthenticatedAt:...}` / 缺字段 400；V7 在真实 neon applied（now at v7）。
- 测试：edge-bff 35→**37**（新增「重认证 session 断言带 level2+时刻」「普通登录无 MFA 证明」两条回归，锁死硬编码不复现）；identity 120 全绿；前端 449 全绿。

### 断言携带 role → 客服终审打通（审判链路收尾）
- **背景**：`customer_service` 是 judge 问题的第二次出现——不在 identity 的 `IdentityType`（只有 merchant/recommender），身份无法获得 → 客服终审恒 403。选定「按 `app_users.role` 判定」（客服是**平台角色**，与业务身份正交），但断言当时不携带 role。
- **共享契约变更**（`platform-identity-assertion`，被 5 服务依赖）：`IdentityAssertion` 末尾追加 `role` + `hasRole()`（服务断言恒 false，防冒充）。
- **⚠️ 爆炸半径控制**：全仓有 **19 处 `new IdentityAssertion(...)`**。保留 **15 参便捷构造器**（`role=null`）——服务断言天然无用户 role，该重载语义即「无 role」，非权宜之计。故仅需真正用 role 的构造点改动，其余 18 处零改动。
- **前向兼容**（滚动发布安全）：codec 已关 `FAIL_ON_UNKNOWN_PROPERTIES`，新字段末尾追加 → 旧 token 解出 `role=null`。加 3 条测试锁死：role 往返 / **旧 token（无 role 字段）仍可解且不误授权** / 服务断言 role 恒 null。
- **edge-bff**：`buildAssertion` 签入 `identity.role()`（`ResolvedIdentity` 早已解析出该值，只是从未签进去）。
- **trust**：`Caller` 加 `role`；`isCustomerService()` 改按 role 判定（`admin` 为客服超集）；删除死代码 `isJudge()`（按 `activeIdentityType=judge` 判定，永远返回 false）。
- **实跑验证**（完整链条）：账号 role 设为 `customer_service` → ① 未重认证 **403**「需要客服近期重新认证（MFA）」 → ② 重认证 200 → ③ 客服终审 **200**：状态 `final`，`finalDecision=for_recommender` **覆盖**面板判决 `for_merchant`（5:0 多数决），正是客服兜底应有语义。
- 测试：共享模块 26→**29**、trust 60→**62**（admin 可终审 / 服务断言不可冒充客服）、edge-bff 37；**全平台 Java 386 测试全绿**；前端 449 全绿。
- **实跑中遇到的非缺陷现象**（记录备查）：① 投票窗口是生产配置 **24h**，e2e 无法等到自然 tally，最终用 repo 直接置 `appealed` 完成客服终审验证（该路径 IT 已覆盖）；② neon 偶发 `08006 Connection closed during SSL negotiation`（容器重启后连接池重建期），重试即通，非代码缺陷。

### 审判窗口秒级配置 + 看板倒计时
- **背景**：窗口只有小时粒度（`vote-window-hours` 最小非零值 1 小时），dev/e2e 无法验证「窗口到期→自动 tally→decided→上诉窗口→终局」这条**时间驱动主链路**；且 UI 只显示 `voting`，用户不知要等 1 分钟还是 24 小时。
- **秒级覆盖**：`AdjudicationProperties` 加 `voteWindowSeconds`/`appealWindowSeconds`（>0 时优先于小时值）+ `*SecondsEffective()` 换算方法。对齐 marketplace 的 `SETTLEMENT_WINDOW_SECONDS` 既有约定；**生产留 0 即用小时值**。compose 中 dev 默认 60s。
- **看板倒计时**：snapshot 增加 `window` 段（`phase`=vote/appeal/none、`durationSeconds`、`startedAt`、`deadline`、`remainingSeconds`），前端本地每秒 tick 平滑显示（避免为走秒轮询后端），归零显示「已到期，等待系统处理」。
  - ⚠️ `remainingSeconds` 是**估算展示值**——真正到期由 Temporal Timer 驱动，二者可能有秒级偏差（workflow 重放/重试），不作判定依据。已在类型注释与后端 javadoc 标注。
- 测试：新 `AdjudicationPropertiesTest`(5：小时回落 / 秒级优先 / 两窗口独立 / 负值视作未覆盖 / 非法小时兜底)；**Java 386→391 全绿**，前端 449 全绿。

#### ⚠️ 时间驱动主链路 e2e **未能完成验证**（环境阻塞，非代码缺陷）
本轮目标之一是实跑验证「窗口到期→自动 tally」，**没有做到**，如实记录：

- 窗口配置**确认生效**：启动审判返回 `window={phase:vote, durationSeconds:60, deadline:..., remainingSeconds:20}`（不再是 86400）
- 投票累计**确认正常**：5 票达 `majority=for_recommender`
- 但窗口到期后状态**持续停在 `voting`**，未触发 tally。查日志根因是 **neon 反复 `08006 Connection closed during SSL negotiation`** —— trust-service 的 R2DBC 连接池整体失效，连 HTTP 读路径都 500；重启后短暂恢复又复发。workflow 的 tally activity 每次读 DB 均失败，Temporal 持续重试。
- **此前把该现象记为「偶发、重试即通」，严重程度被低估**——它是持续性的，会阻塞所有依赖 DB 的 workflow activity。
- 该编排逻辑本身**有测试覆盖**：`DisputeAdjudicationWorkflowReplayTest`(4) 用 `TestWorkflowEnvironment` 覆盖 Timer→tally→decided/重开/升级/等客服全分支（Timer 在 test env 自动推进）。但**测试通过 ≠ 真实环境可用**，这条链路仍需在 DB 稳定后重跑 e2e 确认。

### neon 连接故障排查（结论：**问题在 neon 侧/网络，不在代码**）
排查了阻塞时间驱动链路 e2e 的 `08006` 连接故障。**两个基于推理的假设先后被实跑推翻**，最终靠对照实验定性。

**排查过程（含两次错误判断，留作教训）：**

| # | 假设 | 依据 | 实跑结果 |
|---|---|---|---|
| 1 | 无连接池导致握手风暴 | 5 服务全是裸 `ConnectionFactories.get`，无池 | ❌ 加池后 40 次请求仍从第 9 次起持续 500 |
| 2 | PgBouncer 与 prepared statement 冲突 | URL 确为 `-pooler` 端点（PgBouncer transaction 模式） | ❌ 禁缓存后**更糟**：40 次仅成功 2 次 |
| 3 | **问题在 neon 侧/网络** | — | ✅ **对照实验**：绕开全部服务代码、从宿主机 `npx tsx` 直连 neon，3 次 **2 次失败**，成功一次耗时 **15.9s** |

**结论**：故障与本仓代码无关。此前观察到的 `08006 SSL negotiation` / `Connection unexpectedly closed` /
`SocketTimeoutException: Read timed out`（后者来自 **JDBC**，非 R2DBC）都是同一网络层问题的不同表征。

**教训**：应当**先做对照实验**（绕开自己代码验证外部依赖）再动手改，能省掉两轮无效修改。
「日志里有连接错误」不等于「连接配置有问题」。

**保留的改动（合理加固，但已明确标注不是本次故障的解法）：**
- `TrustR2dbcConfig` 加 `ConnectionPool`（`validationQuery`/`maxIdleTime`/`maxAcquireTime`，参数可配）——
  裸工厂每次查询新建 TCP+SSL 确实是缺陷，只是不是这次的原因
- pooler 端点自动追加 `preparedStatementCacheQueries=0` —— 与 PgBouncer transaction 模式配套的正确设置
- 新 `TrustR2dbcConfigTest`(6) 锁 URL 转换（pooler 判定 / 直连端点保留 prepared statement / 参数归一 / channel_binding 剔除）
- **两处代码注释已显式标注**「本改动不是 neon 故障的解法」，防止后人误判问题已解决

**后续**：已改用本地 postgres 做 e2e（见下节），连接问题绕过，时间驱动主链路**已验证通过**。
其余 4 个服务（identity/marketplace/finance/edge-bff）**同样无连接池**，若要推广需分别改（本轮只改 trust 做验证，未推广）。

### e2e 改用本地 postgres（解 neon 阻塞）+ 时间驱动主链路验证通过 ✅
- **方案**：compose 加 `postgres-local` 服务（**无 profile 常驻**，同 kafka/redis/minio；postgres 18-alpine 与 neon 同版本），`.env` 的 `DATABASE_URL` **默认指向它**。生产另行换库（用户决定）。
- **启动方式**（与之前一致，无需额外参数）：
  ```bash
  docker compose --profile java-edge up -d
  ```
- **⚠️ 初始化顺序（空库必做）**：Java 服务的 Flyway **只建草场新表**；`session`/`app_users` 等 **legacy Express 表**由 `server/sql/` 管理，空库上不存在 → identity 启动报 `relation "session" does not exist`。须先跑：
  ```bash
  npm run db:migrate:local   # 8 个 legacy 迁移，55ms
  npm run e2e:seed           # 种 e2e 数据（下节）
  ```
  之后重启 identity-service 即可。最终 34 张表（legacy + 4 服务 Flyway）全部就位。
- **两套迁移机制并存**（技术债）：legacy 用 `server/sql/` + `run-migrations.ts`，Java 用各服务独立 Flyway。
  neon 上因表早已存在而未暴露；空库初始化必须记得先跑 legacy 那套。长期应统一入口。
- **踩坑**：postgres 18+ 镜像要求 volume 挂 `/var/lib/postgresql`（**非** `/data` 子目录），否则报 incompatible data directory 并重启循环。
- **效果对比（同一压测：40 次连续请求）**：

  | 环境 | 结果 | 耗时 |
  |---|---|---|
  | neon | 成功 2 / **失败 38** | 422s |
  | 本地 postgres | **成功 40 / 失败 0** | **3s** |

  这也**反证**了上节结论：代码无问题，故障确在 neon 侧。

- **✅ 时间驱动主链路验证通过**（此前在 neon 上反复失败、始终无法验证）：
  开争议 → 启动审判（7 人面板、**30s 窗口**）→ 4 票达多数 → **窗口到期后 workflow 自动 tally** →
  判决 `for_recommender` → 上诉窗口 30s → **自动终局 `final`**。全程无人工干预，
  证明 `DisputeAdjudicationWorkflow` 的 Timer 编排在真实环境按预期工作。

### 浏览器 UI 实测第二轮：C/D/E/F 组全部跑完（4 个缺陷已修）
- 清单与逐项证据见 **[`docs/草场前端UI实测清单.md`](./草场前端UI实测清单.md)**。A–F **六组全通**，累计 7 个缺陷全部修复（第一轮 1–3，本轮 4–7）。
- **方法改进**（解上轮「轮询最终态没能干净捕获」）：不再于轮询期间插探测 `fetch`（会干扰时序），改为**点击前装 DOM 采样器**（50ms 读 DOM + `performance.now()` 时间戳，变化才记录），点击后全程零额外请求，事后一次性取回轨迹。这既干净捕获了中间态，也直接定位到缺陷 4——网络面板显示 accept 之后**只有 1 条**轮询请求，证明是前端提前退出而非后端慢。
- **缺陷 4（前端，C 组）202 轮询在竞态窗口提前收工**：`pollReservation` 判据是「≠`reserving` 即终态」，但 accept 返回 202 后 Saga 的 `beginAcceptance`(pending→reserving) 要几百毫秒才执行，这期间后端原样回 **`pending`**（`ApplicationController.reservationOutcome` 的 `defaultIfEmpty`）→ 被当成终态，只轮询 1 次就退出，UI 永久停在「处理中…」（**后端其实全对**：已 accepted、已预留 ¥300）。修法：判据改为**到达终态才停**（accepted/compensated）；`pollSettlement` 同款竞态（confirm 后 `confirmed_at` 落库前回 `not_confirmed`）一并修；`ReservationOutcome` 类型补 `pending`（原类型漏了这个真实返回值）。补 4 条回归测试锁死。
- **缺陷 5（前端，D4）启动审判后倒计时不出现**：`startAdjudication`/`appeal`/`submitFinalDecision` 各自直接 `snapshot.value = …`，只有 `refresh` 会重置 `remaining` 并起表 → 必须手点一次「刷新」倒计时才显形，且上诉/终审后残留上一阶段旧秒数。修法：抽 `applySnapshot()` 作为写快照的唯一入口，快照与倒计时同步；终局无窗口时停表。
- **缺陷 6（trust，D6）审判官读不到自己要投的争议** + **缺陷 7（trust，E 组）客服读不到自己要覆盖的判决**：`getAdjudication` 只认「当事方 org / marketplace 服务」，审判官恒 403（投票按钮组渲染不出来）、客服恒 403（连「客服终审」折叠区都不渲染，**终审在 UI 上完全不可达**）。修法：控制器放行**本轮面板成员**（`filterWhen` + `judges.isPanelMember`，非面板推荐官仍 403），`resolvePartyOrService` 放行**客服**并允许跨 org（平台职能）。快照本就脱敏（D-10），审判官/客服正是其目标读者；读快照严格弱于二者已被授权的写动作。补 3 条 IT。

### 按邮箱邀请成员（identity V8，解「成员管理只能填 UUID」）

- **背景**：上一轮实测记下的能力缺口——加成员只能填 account UUID，邀请人根本拿不到对方 UUID，功能实际不可用。
- **为什么不做「按邮箱查人」**：那等于给任何能建组织的人一个**账号枚举探针**（输入邮箱即可判定是否注册）。
  改做**邀请流**：邀请只记邮箱，系统对「该邮箱是否有账号」**一律不作答**，由对方登录后自行接受。
- **Flyway V8**：`organization_invitation`（org/email/role/status/invited_by/accepted_by/expires_at）；
  partial unique `(organization_id, email) WHERE status='pending'`——终态不占位，撤销/谢绝后可重新邀请。
  过期**不是状态**（避免为翻状态引定时任务）：`expires_at` 与当前时刻比较，读侧过滤 + 接受侧守卫各判一次。TTL 默认 168h（`identity.invitation.ttl-hours`）。
- **org 侧**（`/api/organizations/{orgId}/invitations`）：POST 发邀请（OWNER，role 仅 admin/member，重复 pending→409）
  / GET 列全部（MEMBER+）/ DELETE 撤销（OWNER，已终态→409）。outbox `MembershipInvited` / `MembershipInvitationRevoked`。
- **被邀请人侧**（`/api/me/invitations`）：GET 列「发给我这个邮箱」的未过期邀请（带组织名，**不含** email/status）
  / POST `{id}/accept`（落成员关系）/ POST `{id}/decline`。outbox `MembershipInvitationAccepted` / `MembershipGranted` / `...Declined`。
- **三条安全口径**：① 接受时校验「当前登录账号邮箱 == 邀请邮箱」，id 泄露也无法冒领；
  ② 邮箱不匹配返回 **404 而非 403**——403 会变相确认「这个 id 是个真邀请」，成为探测口；
  ③ 邮件正文**不含任何一次性凭据**（接受必须登录本人账号操作），故邮件泄露不等于邀请被劫持。
- **顺序与幂等**：先 guarded UPDATE（pending→accepted，并发只有一个赢家）再建成员关系；
  对方已是成员时唯一约束冲突视为**幂等成功**（邀请照样消费，返回 `alreadyMember:true`，且**不降级**其既有角色）。
- **前端**：`useGrassland` +6 方法；`OrgTeamCard` 改为「发出邀请」为主路径（UUID 直接添加收进 `<details>` 次要入口）+ 邀请记录表（撤销）；
  新 `MyInvitationsCard.vue` 挂在角色切换之外（任何账号都可能被邀请）。
- **浏览器实测抓到的缺陷（已修）**：`MyInvitationsCard` 原本只在 `onMounted` 拉一次，
  而工作台在未登录时也已挂载 → **同一页面内登录后列表仍停在「暂无邀请」**，必须手点刷新才出现。
  改为 `watch(() => currentUser.value?.id, ..., {immediate:true})`：换账号重拉、登出清空（不把上个账号的邀请留在界面上）。
  这与上一轮的「缺陷 5：启动审判后倒计时不出现」同源——**组件内部状态没跟着外部状态变**，单测覆盖不到。
- **实测走通**（真实容器 + 真 DB 对账）：商家发邀请 → 被邀请人登录后自动看到「我的邀请 1」+ 组织名 →
  **接受 → 真的进成员表**（judge2 从无到 member）；对已是成员者接受 → 「你本来就是…的成员」且既有 admin 角色不被降级；
  **撤销** → 状态翻「已撤销」、撤销按钮消失；撤销后**可重新邀请**；重复 pending 邀请 → 后端原文「该邮箱已有待接受的邀请」；
  **谢绝** → 状态翻「已谢绝」且未产生成员关系。outbox 事件计数一致。
- 测试：identity 120→**131**（`InvitationControllerIT` 11：完整接受链路 / 未注册邮箱响应与已注册**逐字一致** / 重复 409 /
  非 owner 403 / 冒领 404 / 过期 410 / 撤销 / 谢绝后可重邀 / 已是成员幂等 / 非法邮箱与 owner 角色 400 / 401）；
  前端 462→**466**（邀请请求契约 4：email≠accountId、accept/decline 无请求体、两侧字段不对称、DELETE 路径）。typecheck / build 干净。

`GrasslandWorkbench` 同样只在 `onMounted` 初始化，而它在未登录时就已挂载、切标签页又不重挂载

**② 邮件其实一直发不出去（`.env` 里明明配了 QQ SMTP）**
实测时 `emailSent:false` 我记成了「本地未配 SMTP」，**这个判断是错的**——日志里其实是
`MailSendException: Exception reading response`。两个真实缺陷：
- `SmtpMailSender` 读的是 `spring.mail.properties.mail.from`，而 application.yml 配的是 `mail.smtp.from`——
  **这个 key 根本不存在**，于是永远用占位地址 `noreply@grassland.local` 发信；
- QQ/163 等 SMTP 要求发件人**必须等于认证账号**，占位地址会被服务器直接断连（即上面那个报错）。

修法：发件人按 `SMTP_FROM` → `spring.mail.username` → 占位地址回落（`.env` 没配 SMTP_FROM 时自动用 SMTP_USER）；
yml 里 `mail.smtp.from` 默认值同样改成 `${SMTP_USER:}`，并补 connection/read/write 超时（否则 SMTP 卡住会占死
`boundedElastic` 线程）。**这同时修好了注册验证码邮件**——那条路径用同一个 `from`，指南「已知问题」里挂了很久的
「SMTP_FROM 待验证」就是它。
实跑验证：向 `.env` 里那个自己的邮箱发了一封邀请信，`emailSent:true`、日志无异常（测试用的邀请随后已撤销）。

### 推荐官钱包 + capture 分账 + 提现（闭合「商家扣款 → 推荐官到账」的断口）

- **背景（全局盘点后确认的最大结构性缺口）**：`grep recommender|payout|withdraw` 在 finance **零命中**——
  finance 只有按 org 唯一的商家账户。资金流原本是「reserve 扣商家余额 → capture 只翻状态、**不动任何余额**」，
  钱扣完就停在平台账上，推荐官既没有账户也拿不到钱，PRD 第八章的资金流根本没闭环。
- **Flyway V3**（finance_flyway_schema now at v3）：`recommender_wallet`（账号级，`balance_cents >= 0`）+
  `wallet_ledger`（append-only，金额**带符号**，`fee_cents` 记平台抽成）+ `funds_reservation.payee_account_id`
  / `payout_cents`。不复用 `finance_account`——那是 `UNIQUE(organization_id)` 的商家账户，推荐官不属于任何 org。
- **收款人从哪来**：finance 只认 `engagementRef`，不知道钱该付给谁 → 由 marketplace 在 reserve 时传
  `payeeAccountId`。取值在 activity 里**现查报名记录**而非加进 `AcceptanceInput`——workflow 入参变更会影响
  在途实例反序列化，而那里本来就要读库。
- **capture 分账**：`reserved→captured` + 净额入推荐官钱包 + 流水 + outbox `SplitCompleted`。
  无收款人（存量预留/非撮合场景）→ 维持旧行为不动钱，向后兼容。
- **平台抽成**：`finance.split.platform-fee-bps` **默认 0**——PRD 十写明前期冷启动全免费、中期才「建议 5%-10%」，
  抽成率是产品决策，不由实现拍板。取整向下，零头归推荐官。单测锁住 0 / 5% / 边界。
- **冲正（D-06）的正确性关键**：已分账后判商家胜诉时，**先从推荐官钱包按净额扣回、再退商家**；
  扣 `payoutCents` 而非毛额（否则把平台抽成也从他身上扣走）；钱包不足（多半已提现）→ **409 中止整个冲正**，
  商家不退款、预留仍是 captured，宁可挂起等人工，也不能一边退款一边让余额变负 = 凭空造钱。
- **提现（sandbox）**：`GET /api/finance/wallets/me` + `POST .../withdrawals`。accountId 只取自断言（无越权维度），
  **服务断言不可动钱包**（服务身份是给 Saga 用的）。条件扣减防并发双花。未接真实支付通道，UI 明写。
- **前端**：`Wallet`/`WalletEntry` 类型 + `useGrassland` +2 方法 + `MyWalletCard.vue`（余额/流水/提现，
  挂推荐官视角）。空流水如实说明「钱在托管中」，避免被当成钱丢了。
- **全链路浏览器实测（两个隔离上下文 = 商家 + 推荐官）**：商家发 ¥300 赏金任务 → 推荐官报名 →
  商家接受（202 轮询→已接受，资金已预留）→ 确认履约（202 轮询→**已结算**，商家余额 ¥10000→¥9700）→
  **推荐官「我的收益」到账 ¥300**、流水「任务结算入账 +300.00」→ 超额提现按钮禁用 → 提现 ¥120 →
  余额 ¥180、流水多一行「提现 -120.00」。DB 对账一致（钱包 18000 分 / 两条流水 / `payout_cents=30000` /
  `SplitCompleted` + `WithdrawalCompleted` 各 1）；存量无收款人的预留仍 `payout_cents` 为空、未被分账。
- 测试：finance 36→**47**（`WalletControllerIT` 7 含冲正扣回与「已提现则整单中止」+ `PlatformFeePolicyTest` 4）、
  marketplace **86**（reserve 传收款人的回归）、前端 484→**490**（`MyWalletCard.test.ts` 6）。typecheck / build 干净。
- **本轮未做**：真实支付通道（PRD 8.5，提现仍是 sandbox 出账）/ 到店核销与霸王餐两种资金模式 /
  T+2 结算周期与月度账单（现窗口由 `SETTLEMENT_WINDOW_SECONDS` 控制）/ 提现风控与最小提现额 /
  平台抽成的收入侧记账（现只在流水里记 `fee_cents`，平台自身没有账户）。

### 履约交付物 + 凭证提交（补上撮合闭环缺的一环）

- **背景**：此前 accept 之后商家直接就能点「确认履约」——推荐官交了什么、商家在确认什么，
  系统里**没有任何记录**，确认是凭空点的。PRD 九「自动核实引擎」第一步就是「推荐官提交凭证」，
  没有这张表，核实引擎、争议证据（`dispute_case.evidence_ref` 早有列却没人写）都无处落脚。
- **Flyway V5**（marketplace_flyway_schema now at v5）：`engagement_submission`（application 真 FK +
  `content_url` + `note` + status submitted/accepted/rejected + `review_note`）；
  partial unique `(application_id) WHERE status='submitted'` —— 同时只允许一份待核验，
  被退回后不占位，于是「提交→退回→重交」能循环。附件（截图/数据）留待接入既有对象存储三步上传，不预造字段。
- **端点**：`POST/GET /api/tasks/{id}/applications/{appId}/submissions`（提交须本人+已接受；商家与本人可列）
  + `POST .../submissions/{sid}/reject`（商家退回带原因）。outbox `DeliverableSubmitted`/`DeliverableRejected`。
  `contentUrl` 强制 http(s)——收「已发布」这种自由文本等于没有凭证。
- **confirm 语义修正**：确认履约现在**必须先有待核验的交付物**（否则 409），确认即等于核验通过该份交付物
  （置 accepted）。既有两条 confirm 测试相应改为先提交再确认——是语义修正，不是放宽实现。
- **前端**：`EngagementSubmissionPanel.vue`（同一份数据两个视角，用 `role` 区分动作），
  商家侧挂在报名列表下、推荐官侧挂在「我的履约与争议」下。

#### 顺带修掉的两个既有缺陷（都由浏览器实测暴露）

1. **推荐官永远看不到自己的报名**：`GET /api/tasks/{id}/applications` 是 owner-only（非 owner 一律 403），
   于是推荐官工作台里「我的履约与争议」永远是空的——提交履约、开争议这些**本该由推荐官发起**的动作
   根本无从挂载。改为**按调用者过滤**：owner 看全部，其他人只看得到自己那条，不相干的人拿到空列表
   （不泄露有几人报名），也就不必再开一个 `/api/me/applications`。任务大厅顺带支持点标题选中任务。
2. **marketplace outbox 发布器一直在空转**：`markPublished` 写的是 `CAST(:id AS bigint)`，
   而 `marketplace_outbox.id` 是 **uuid**（`trust_outbox.id` 才是 bigint，finance 早就是 uuid）。
   后果不是「发不出去」而是更隐蔽的**发了但标不上**：每轮调度把同一批事件重发一次，
   at-least-once 退化成「永远重发」，日志里只有一串 `BadSqlGrammarException`。修后实测：
   积压的 23 条一次性全部标为 published，错误归零。
- **全链路浏览器实测**（商家 + 推荐官两个隔离上下文）：发 ¥200 任务 → 报名 → 接受 →
  **无凭证点确认 → 409「推荐官尚未提交履约凭证，无法确认」** → 推荐官提交链接+说明（按钮随即禁用并说明原因）→
  商家看到链接、**退回补交**并写原因 → 推荐官看到退回原因、改链接重交 → 商家确认 → 交付物翻「已核验通过」→
  结算完成，商家 ¥9700→¥9500、推荐官钱包 ¥180→¥380。DB 对账一致。
- 测试：marketplace 86→**89**（提交/退回/重交全循环 + 无凭证确认 409 + 越权与非法链接 + 报名可见性改判）；
  前端 490→**498**（`EngagementSubmissionPanel.test.ts` 8）。identity 134 / finance 47 / trust 76 无回归。
- **本轮未做 / 如实记录**：
  - 截图与数据附件未做（对象存储三步上传仍零前端使用）；自动核实引擎本身（指标抓取/达标判定）未做，
    当前仍是商家人工核验。
  - 交付物面板**没有推送或轮询**：商家退回后，推荐官那边要刷新页面（或重新选中任务）才看得到退回原因。
    实测时我就被这个绊了一下——面板停在旧状态、提交按钮是禁用的，点了没反应。
  - 实测中确认履约那一次前端弹出过一次 **「Internal Server Error」**，但四个服务日志都没有对应报错，
    且结果完全正确（capture HTTP 200、交付物 accepted、余额与钱包都对）。**未能定位来源**，如实记下。

### 推荐官画像 + 声誉 + 等级 + 商家筛选（PRD 五 / 六）

- **背景**：商家收到报名，界面上只有一串 `3214348b…`——谁报的、做什么内容的、靠不靠谱全不知道，
  **接受/拒绝是盲选**。撮合平台的撮合质量是它存在的理由，这个洞比「少一种付费模式」更伤产品。
- **为什么先做这条**（相对于核实引擎/到店核销）：声誉所需的事实**已经全在库里**
  （报名/接受/退回/争议结果/收入），能从既有事实算出来，不依赖平台数据采集或支付通道这些
  不在我们这边的不确定项。且它能顺手拔掉 trust 里「审判官资格用配置阈值占位」那根钉子。
- **Flyway V9**（identity now at v9）：`recommender_profile`（display_name / bio / `content_tags text[]` /
  `domain_tags text[]` / `social_accounts jsonb`）。标签用数组不建关联表——本轮标签是自选短字符串，
  没有独立生命周期；等 PRD 六说的「系统自动打标」要记打标来源/置信度时再拆。
- **端点**：`GET/PUT /api/me/recommender-profile`（自维护，PUT 整份覆盖）+
  `GET /api/recommenders/{accountId}/profile`（商家审核报名时看对方画像）。
- **两条口径**：① 社交账号在库里是 jsonb，**出到 API 是真数组对象**，JSON 字符串只存在于 DB 与
  repository 之间（本项目被「请求收对象、响应回字符串」坑过，不重犯）；② 没填过资料返回**空画像而非 404**——
  「这人没填」本身就是商家要的事实。
- **可见性**：任何登录用户可按 accountId 读画像，但只回画像字段、**不回邮箱等账号信息**，
  也**没有「按条件搜人」的入口**（那会把平台变成人肉数据库）。商家拿到 accountId 的唯一途径是对方主动报名。
- **粉丝量是自报值**，本轮不做平台核验（真核验属 PRD 九自动核实引擎）。UI 展示时须让商家知道。
- 测试：identity 134→**140**（`RecommenderProfileControllerIT` 6：自维护 / 整份覆盖清空 / 他人可读 /
  未填空画像 / 标签清洗与超量 400 / 401）。

3. **连接池**：仅 trust 使用有界 validated R2DBC pool；identity/marketplace/finance/intelligence/edge 仍为 raw factory，扩副本前需统一连接预算。
4. **可观测性**：当前主要只有 health/info；补 Prometheus/OTel、trace/request correlation、outbox age、consumer lag、DLT 告警。
5. **部署与 readiness**：Temporal 仍 start-dev/SQLite，基础镜像存在 `latest`，MinIO 默认 root key，缺 Java/Kafka/MinIO health gate、

7. **回滚口径**：当前 route `enabled` 是启动期配置，并非真正零重启控制面；STYLE 回滚只切路由、不双写数据，会读到 stale legacy 偏好。
