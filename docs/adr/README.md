# 草场架构决策记录（ADR）

本目录记录进入 LLD（详细设计）前必须冻结的决策，编号对齐 HLD §19《进入 LLD 前的决策清单》的 `D-xx`，**不重编号**。每条 ADR 是一个业务/架构取舍：把背景、当前代码现状、可选方案与取舍、推荐结论、需要拍板的开放问题写清楚，供决策者高效定夺。

> 本目录由 `GL-P2-ADR-001` 驱动建立（2026-08-02）。HLD §21 末尾明确：标记为 `DECISION REQUIRED` 的事项未完成前，相关金融、核实、争议或消费者交易模块**不得视为可直接进入生产实现的最终设计**。

## 状态约定

| 状态 | 含义 |
|------|------|
| 草案 | 已起草（背景/方案/推荐齐备），等待决策者确认或回答开放问题；**未冻结**，相关模块不能进生产 LLD |
| 已采纳 | 决策者已确认；约束下游 LLD 与实现，变更须经新 ADR |
| 已驳回 | 经评估否决（保留作为「为什么不选它」的证据） |
| 已废弃 | 被后续 ADR 取代 |

本批 ADR 全部以**草案**状态建立。「推荐」是起草者基于 HLD/PRD/代码现状给出的倾向，不是既定决策——每条末尾的「待你拍板」才是真正需要业务/合规/财务取舍输入的地方。决策者确认后，把状态改为「已采纳」并补日期与决策者。

## 依赖关系

```
D-01 (PSP/托管/合规)  ← 根决策，阻塞所有资金相关
 ├─→ D-02 (资金模式组合)   三种模式的资金流都依赖托管能力
 ├─→ D-06 (争议资金处置)   冲正/追偿依赖资金是否可逆，而可逆性由 D-01 的托管形态决定
 └─→ D-07 (订单/分账)      到店核销的消费者支付与分账依赖 D-01

D-03 (确认超时/失联)  与 D-01 解耦，但拒绝/失联的退款走 D-01 的退款通道

D-10 (数据保留/脱敏)  独立，合规驱动
D-11 (AI 计费)        独立，依赖 D-01 仅在「AI 付费走真实收款」时
```

**推荐推进顺序**：先 D-01（根），再 D-02/D-03（解锁任务资金闭环 LLD），再 D-06/D-07（解锁争议与消费者交易 LLD），D-10/D-11 可并行。

## ADR 模板

每条 ADR 包含以下小节（缺失小节需写明「无」并说明原因）：

```
# ADR-Dxx：<决策标题>

| 状态 | 日期 | 决策编号 | 阻塞范围 | 依赖 |
|------|------|----------|----------|------|

## 背景
为什么需要这个决策（HLD/PRD 出处 + 触发场景）。

## 当前代码现状
决策落地时仓库的实际状态（已建的表、服务、原语），作为「不能破坏什么」的基线。

## 方案与取舍
列 2–4 个真实可选方案，每个写明优点、缺点、适用条件。不发明不存在的方案。

## 推荐
起草者倾向的方案 + 理由。是倾向，不是既定决策。

## 待你拍板
只有决策者能回答的开放问题（选型、合规主体、业务阈值等）。逐条列出。

## 影响
采纳后解锁什么、约束什么、波及哪些已有设计。

## 不在范围
本 ADR 明确不解决、归到别处的事项。
```

## 范围外（不属于本批 ADR）
