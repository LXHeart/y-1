## 决策记录（部分采纳，2026-08-02）

**决策者拍板**：资金对接哪个平台尚未确定，但当前系统必须先记录资金流转，**预留与其他平台对接的口子**先开发；选定平台后再开发对接接口。

**采纳范围（Sandbox 已落地）**：
- 采纳本 ADR「保留 `reserve/release/capture/reverse/reconcile` 状态机、底层升级为双录账本」的核心架构——**Approach B（双写投影）**：余额行保留为缓存投影 + 并发守卫，同事务追加不可变 `journal`/`posting`（HLD §6.4 双录：每 journal ≥ 2 posting、借贷合计为零、Finalized 不可改、错误经 Reversal Journal、余额可由 Posting 重建）。OPENING 回填存量余额使投影自迁移起可重建。
- 落地 **`PaymentProviderAdapter` seam**（HLD §12.2 命名）：首期 `SandboxPaymentProviderAdapter`（`@ConditionalOnProperty finance.psp.mode=sandbox`，只写内部账本、不真发外部调用）；真实 PSP impl 替换该 bean 即生效，无需改调用点。供应商 DTO 停留 adapter 层，不进领域模型。
- 接线 6 处资金操作同事务双写账本（credit/reserve/release/capture/reverse/withdraw），**HTTP/outbox 事件/身份契约零变**。
- 到店支付、退款、核销分账和钱包提现统一登记 `finance_provider_operation`；记录稳定的内部 `operation_id`、通道引用、金额、币种与通道状态。提现请求新增可选 `operationId`，旧请求兼容，显式传入时重复请求不重复扣款。
- V12 增加 Webhook Inbox 与外部对账单行：`finance_provider_webhook_event` 以 `(provider,event_id)` 幂等，未知引用只记 `ignored`、不改账本；`finance_provider_reconciliation` 给出 `matched/mismatch/unmatched`，匹配后将 operation 标为 `reconciled`。
- 财务角色可通过 `/api/admin/finance/sandbox/webhooks` 和 `/sandbox/reconciliation` 完整模拟回调与对账，并通过 provider operations/webhooks/reconciliation 三个只读端点检查结果。Sandbox 模拟端点不接受非 `sandbox` provider。
- 新增集成测试覆盖 Webhook 重投、未知操作、对账匹配/差异/未匹配、支付/退款/分账/提现 operation 登记及提现幂等。

**仍延后（待真实 PSP 接入，不阻塞账本）**——下方「待你拍板」6 项全部降级为「PSP 接入时再答」：
1. 资金存管合作方 / 2. 合规主体 / 3. 二清合规结论 / 4. PSP 首期范围 / 6. 外部对账事实源——这五项在「不动真钱」阶段不实质化（二清风险只在真实归集第三方资金时触发）。
- 第 5 项「退款资金来源」随真实退款通道落地。
- 真实 PSP adapter（支付会话、退款、原生分账、付款）、Webhook 签名验真、外部对账文件拉取、KYC/KYB/MFA 和 Payment Recovery 一并延后；真实 adapter 必须复用现有 operation/inbox/reconciliation 契约，不得把供应商 DTO 泄漏进领域模型。

> 即：**资金主干的内部记录已可上线，真实收钱/出钱仍卡在平台选定**。采纳本部分不等于解锁真实资金生产——真实 PSP 接入前，finance 仍是「内部账本真相源 + sandbox 余额」，不触碰真实第三方资金。

## 背景

HLD §12.1 把支付列为 `DECISION REQUIRED`（供应商和合规模式未定）；§10.4 给出消费者支付→核销→分账的时序；§6.4 规定金融不可变（Finalized Journal 不可改、只能追加冲正、余额可由 Posting 重建）；HLD §18 把「支付和分账能力未确定」列为头号风险，缓解措施是「真实资金前只用 Sandbox」。

PRD §8《资金托管与结算》明确三种模式的资金流**都经过「平台托管账户」**：

- 佣金模式：商家预付佣金 → 平台托管冻结 → T+2 打款推荐官 / 未达标返还商家
- 霸王餐模式：推荐官预付 → 平台托管冻结 → 达标全额返还推荐官 / 未达标释放给商家
- 到店核销模式：消费者扫码支付 → **全额进入平台托管账户** → 核销后分账给推荐官与商家

PRD §8.5 要求支持微信支付、支付宝、银行卡、信用卡，「具体接入方案待定」。

核心矛盾：PRD 的「平台托管账户归集第三方资金」模型，在中国大陆监管下命中**「二清」（无证支付聚合/资金归集）风险**——平台代收代付第三方资金需持支付牌照或经持牌机构/银行存管。本决策要先选定**资金归集的合规结构**，再选 PSP，再确定退款/付款/对账能力边界。这是 D-02/D-06/D-07 的前置。

## 当前代码现状

finance-service 目前是 **Sandbox「内部账本 + 通道生命周期」模型**，不接任何 PSP：

- 余额投影、reservation、推荐官钱包、不可变 Journal/Posting 双录账本和 outbox 已落地。
- 原语（`EscrowLifecycleService`）：`reserve` / `release` / `capture` / `reverse` / `reconcile`，**全部作用于内部余额行**，不是真实 PSP 资金。
- 到店 `Payment/Refund/Split`、钱包提现、provider operation、Webhook Inbox 和对账单行已落地；`SandboxPaymentProviderAdapter` 不发外部请求。
- Sandbox 可完整测试支付、退款、分账、提现、回调和对账，但没有真实支付会话、回调验签、外部清算或实际到账。
- trust 的争议 hold 经 `SettlementHeld` 事件让 marketplace 的 `settlement_reconciliation` 落 `blocked`，再由 finance `reconcile` 处理——**资金实际未移动**，因为 Sandbox 余额不对应真实账户。

> 即：内部账本与通道生命周期契约已经固定。选定渠道后新增真实 adapter、签名验证器和对账文件解析器；现有领域事实、幂等键和资金状态机不因供应商 DTO 改写。

## 方案与取舍

资金归集的合规结构有三类现实选项，PSP 选型是其上的第二层决策。

### 方案 A：平台商户号归集（PRD 字面模型，二清高风险）

平台以自身主体在微信支付/支付宝开商户号，所有第三方资金（商家佣金、推荐官预付、消费者支付）先进平台商户号，平台再「付款」给商家/推荐官。

- ✅ 产品最简单：三种模式资金流统一进一个托管账户，PRD §8 的归集/冻结/分账时序可直接落地。
- ✅ 到账可控、对账内部闭环。
- ❌ **命中「二清」**：无支付牌照的平台代收代付第三方资金违规。合规路径只有两条——平台申请支付牌照（重）、或与持牌机构/银行做资金存管（见方案 B）。
- ❌ 资金池混同，需严格备付金隔离与审计。

### 方案 B：银行/持牌机构资金存管（合规稳健，接入重）

平台与银行或持牌支付机构签资金存管/托管协议，资金进**存管账户**（户名仍是交易双方或存管方，非平台），平台只发指令（冻结/解冻/分账/退款），不触碰资金。平台侧的「托管账户」是存管账户的账面映射。

- ✅ **合规**：资金不经平台主体，规避二清；这是监管认可的互联网平台资金处置主流路径。
- ✅ 平台不承担资金池风险，备付金天然隔离。
- ❌ 接入复杂、有存管费、到账可能慢于直连。
- ❌ 存管方能力（实时分账、部分退款、对账文件格式）决定产品上限，需逐项对齐。

### 方案 C：PSP 原生分账，平台不归集（合规，但产品受限）

用微信支付/支付宝的**分账**能力：消费者/推荐官支付直达**商家商户号**（或平台代开的二级商户号），平台在交易成功时按比例分账抽佣，**平台主体从不归集资金**。

- ✅ **合规**：资金不过平台，无二清；接入相对成熟（微信/支付宝都有现成分账 API + 二级商户体系）。
- ✅ 无资金池、无备付金管理负担。
- ❌ **不满足 PRD §8 的「平台托管账户」归集语义**：霸王餐「推荐官预付→达标返还」、佣金「商家预付→未达标返还商家」要求资金**先冻结在托管态再按结果流转**，原生分账的「支付即进商户号」做不到「先托管后裁决」。
- ❌ 分账比例有上限（微信默认 30%，可申请提高）、退款/争议跨商户号处理复杂。
- ❌ 推荐官/商家都需要开二级商户号（KYC/KYB 负担）。

### 方案 D：混合——存管托管（B）为主 + PSP 分账（C）为到店核销兜底

托管型资金流（佣金预付、霸王餐预付）走方案 B 的银行存管；到店核销的消费者实时支付可走方案 C 的 PSP 原生分账（消费者支付→核销→即时分账，无需长期托管）。

- ✅ 各模式用最贴合的合规结构：需「先托管后裁决」的走存管，需「即时分账」的走 PSP 分账。
- ✅ 全程合规。
- ❌ **两套资金通道并行**，finance 要同时对接存管 API 和 PSP 分账 API，对账复杂度翻倍。
- ❌ 首期工作量最大。

## 推荐

**目标态采用方案 D（混合），首期生产发布先用方案 B（银行/持牌机构存管）单一通道覆盖全部三种模式，到店核销的实时分账作为方案 C 的增量在第二期叠加。** 理由：

1. **合规是硬约束**，方案 A（PRD 字面）的二清风险不可接受；方案 B/C/D 都合规，取舍在产品契合度与接入成本。
2. 三种模式中有两种（佣金、霸王餐）的语义是「先冻结、后按结果流转」，**必须托管**，方案 C 单独无法满足。方案 B 能统一覆盖三种模式，是首期最小可行合规全集。
3. 到店核销的「支付即分账」用方案 C 更顺滑，但它不阻塞首期（首期到店核销也可走存管：消费者支付进存管→核销→分账出账，只是非实时）。作为二期增量降低首期接入面。
4. 与 HLD §6.4 金融不可变 + §2.3 事实单写一致：存管账户是外部资金事实，finance 写双录 Journal 镜像存管状态，余额投影可重建。

**PSP 选型倾向**：首期到店核销若做，优先**微信支付**（小程序生态、分账 API 成熟、PRD §8.5 首列）；支付宝作为二期对等接入。银行卡/信用卡经微信/支付宝聚合或后续独立网关，不在首期。**但 PSP 选型强依赖存管合作方的通道能力，应与存管方一起定。**

## 待你拍板

1. **资金存管合作方**：选定银行或持牌支付机构（这是落地前置，决定 API 形态、分账能力上限、对账文件格式）。是否已有意向机构？
2. **合规主体**：资金存管协议签在哪个法律主体下（与平台运营主体是否分离）？需法务/财务确认。
3. **二清合规结论**：请法务/财务明确确认「平台不得以自身商户号归集第三方资金」这一前提成立（若你们持牌或已获许可，方案 A 可能可行，需重评）。
4. **PSP 首期范围**：到店核销是否进首期？若进，是否首期即上微信支付分账（方案 C），还是首期到店核销也走存管、二期再切实时分账？
5. **退款资金来源**：退款发生时资金从存管账户出账，若存管余额不足（例如已分账出账），是用平台垫付还是拒绝退款？这关系 D-06。
6. **对账口径**：以存管方对账文件为外部事实源，还是以 PSP 结算单？需财务定。

## 影响

- **解锁**：D-02（资金模式组合）、D-06（争议资金处置）、D-07（订单/分账）可进入 LLD；finance-service 从 Sandbox 升级为真实双录 + 存管 Adapter（对应 backlog `GL-P2-FIN-002` 的 Journal/Posting、Payment/Refund/Payout/escrow 幂等、对账）。
- **约束**：`EscrowLifecycleService` 的 `reserve/release/capture/reverse/reconcile` 状态机保留，底层换成「写 Journal + 调存管 Adapter」；新增 `PaymentProviderAdapter`/`CustodianAdapter`（HLD §12.2 示例接口），供应商 DTO 不进领域模型。
- **波及**：marketplace 的 `settlement_reconciliation` blocked 行的 `reconcile` 调用语义不变，但 finance 侧 reconcile 会真实驱动存管出账/冲正；OPS 运营台（`GL-P1-OPS-001`）的「重试对账」动作底层变真实，但其 HTTP 契约不变。
- **不破坏**：HLD §6.4 金融不变量、Sandbox 期余额可重建、Outbox/Inbox 跨服务一致性。

## 不在范围

- 具体 PSP/存管 API 的 LLD（采纳后由 `GL-P2-FIN-002` 承接）。
- KYC/KYB 流程与商家三级权限材料（D-05）。
- 跨境/多币种（PRD 范围为人民币境内，HLD §13 部署为境内 K8s）。
- 真实提现（Payout）的到账时效、手续费、失败恢复和人工处置策略——归 `GL-P2-FIN-002` LLD；Sandbox 提现记录与幂等已在范围内。
