## 模型与关键技术真相（动手前必读）

1. **后端分页能力三分类**（探索结论，2026-08-28）：
   - 已有完整 limit/offset 但前端没用：仅 `GET /api/admin/tasks/review`（TaskController.java:433-454，参数齐全还带 meta.queue 统计，**但无 total**）。
   - 有 limit 截断无 offset（拿不到第 2 页）：finance journals（limit 默认 50）、trust risk cases（limit 默认 100）、commerce orders/redemptions（limit 默认 200）、公共素材与门店媒体（limit 服务端硬编码 200）。
   - 完全无 LIMIT 全量：admin users、KYB 待审、推荐官认证、主体更名。
2. **驳回的数据流**：`reviewReject`（TaskController.java:519-540）→ `TaskRepository.reviewReject`（:363-371）`UPDATE task SET status='draft', version=version+1` → note 只写 `task_review`（V19：task_id/action ∈ {submitted,approved,rejected}/reviewer_account_id/review_note/created_at，索引 (task_id,created_at) 与 (action,created_at)）。**task 表无任何 review 列**。
3. **task_review 有三类写入**：人工 approve/reject、商家 submit 时追加 submitted（reviewer=null）、策略自动通过 approved（reviewer=null, note=policy_xxx 原因）。D 决策的「最新记录」语义天然兼容三者。
4. **edge-bff 纯透传 query**（application.yml 路由表 + RoutingProxyHandler），分页参数直达下游，**无需改路由**。
5. **前端现状**：无通用分页组件；页码式 UI 先例 = `src/components/MySessionsCard.vue:169-171`（上一页/下一页 + `第 x / y 页 · 共 n 条`，本地 slice）；治理台表格样式 = AdminView.vue scoped `.table-card/.user-table` + 全局 `.gl-field button/.gl-num/.badge`（src/style.css:282-313）。`src/ops/DESIGN.md` 无分页组件定义（规范空白），用既有 token 组合即可，禁止硬编码新色值/圆角。
6. **AdminView.test.ts 两条红线**：①多处测试**按下标**点页签（AdminView.vue:63-64 有注释警告），**不得增删页签**；②mock 是 fetch-stub 白名单（未匹配 URL 直接 throw），初始挂载必 mock `/api/admin/users` + `/api/admin/kyb-requests`，信封一变这些 mock 全要适配。

## S1 · 后端

### S1.1 统一分页信封（12 端点）

每端点统一改造为：`limit`（默认 50，钳 1–200）、`offset`（默认 0，负数归 0），Repository SQL 加 `LIMIT :limit OFFSET :offset` + COUNT 取 `total`（总数与筛选后同口径），响应 `data: {items, total, limit, offset}`（`success` 外壳不变）。

- COUNT 与行查同 WHERE 口径；现有 `ORDER BY` 全部保留（分页不换序）。
- 硬编码上限的（#7 SEARCH_LIMIT、#11/#12 的 200）改为暴露参数并沿用钳制区间。
- 任务审核（#4）：`data` 从裸数组改信封，`meta.queue`（pending/overdue/approvedLast24Hours/rejectedLast24Hours）原样保留，meta 补 `total`。
- 各 Controller 现有响应构造是 `Map.of("data", list)` 形态，注意 LinkedHashMap（Map.of 不接受 null 的教训见 MerchantProfileController 注释）。

### S1.2 任务审核 rejected 视图（D 决策）

`TaskRepository.findReviewQueue`（:392-410）扩展：`status=rejected` 时改走新查询——

```sql
SELECT t.*, tr.review_note AS last_review_note, tr.created_at AS last_review_at
FROM task t
JOIN LATERAL (SELECT action, review_note, created_at FROM task_review
              WHERE task_id = t.id ORDER BY created_at DESC LIMIT 1) tr ON true
WHERE t.status = 'draft' AND tr.action = 'rejected'
  [AND 既有 q/organizationId 过滤]
ORDER BY tr.created_at DESC, t.id LIMIT :limit OFFSET :offset
```

- 语义红线：**「最新一条审核记录是 rejected」**，不是「历史上被驳回过」（后者会把已重新上架的任务误列进来）。LATERAL 取最新一条同时把驳回原因/时间带出。
- 行响应（toBody）增 `lastReviewAction`/`lastReviewNote`/`lastReviewedAt`（仅 rejected 视图有值即可，其余视图可 null）。
- 其余 status 值沿用现有过滤：待审核=`pending_review`（默认，与现状一致）、已通过=`published`。
- rejected 视图同样受 q/organizationId 筛选与分页限制；total 同口径 COUNT。

### S1.3 商家端驳回原因（E 决策）

- `GET /api/tasks`（按组织列表，TaskRepository.findByOrganization :467-483）：LATERAL join task_review 最新一条，`toBody`（TaskController.java:849-871）增 `lastRejectedNote` + `lastRejectedAt`——仅当任务 status='draft' 且最新记录 action='rejected' 时非 null，其余恒 null（避免已上架任务泄漏历史驳回）。
- 前端类型 `src/types/grassland/task.ts` 补这两个可选字段。

### S1.4 后端测试

- 每个 Controller 的 IT 补三类用例：分页生效（offset 翻页取到第二页）、total 与筛选同口径、钳制边界（limit=0→50、limit>200→200、offset<0→0）。
- TaskControllerIT 新增：①`status=published` 列已上架；②`status=rejected` 列被驳回任务且带驳回原因/时间，**重新提交后移出 rejected 视图**（submit 追加 submitted 记录后查不到）；③历史上被驳回现已 published 的任务不出现在 rejected 视图；④商家端 `GET /api/tasks` 对被驳回草稿带 lastRejectedNote、published 任务为 null。
