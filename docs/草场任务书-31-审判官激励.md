## 目标（PRD §7.2：审判官可获得平台奖励（积分/佣金）作为参与激励）

- 陪审轮终局后，对**该轮实际投票**的审判官自动发放激励
- trust（投票事实与策略）+ finance（发放）+ identity（通知）三服务协同，复用既有 outbox/消费/幂等机器

**现状**：trust judge 域仅报名/查询/退出（`JudgeController.java:47-76`）；outbox 争议事件无奖励族；`V3__adjudication.sql` 无奖励列；finance 无审判奖励逻辑（唯一"reward"是 AI 积分赠送路径 `CreditsService.java:126-133`：注册赠送 / admin 正向调整）。

## 激励规则决策包（Phase A 誊写为 ADR）

### D1 奖励形式 = AI 积分；佣金后置

- v1 发 AI 积分（走 finance credits 既有账户/流水/幂等机器）。**不做现金佣金**：向钱包入现金会制造平台内闭环下提不出去的应付负债，与 2026-08-15「付费平台内闭环、不接第三方支付」拍板冲突；佣金形式与真实 PSP 同批再做（ADR 登记边界）
- 积分的副作用是正向的：驱动审判官使用 AI 创作工具

### D2 触发与范围 = 陪审轮终局、按实际投票、逐人事件

- 触发点：**每轮审判终局**（多数票达成或投票窗到期裁决）与 `DisputeDecided` **同事务**发 outbox
- 奖励对象：该轮**实际投出且计入裁决**的票（early conclusion 时未投票者无奖励；超时默认弃权无奖励——PRD §7.2 的弃权语义）
- 打平重选 / 上诉后重开（`AdjudicationReopened`）：每轮各自计发（轮次号参与幂等键）
- **客服终审轮不发**（非陪审，无投票事实）

### D3 金额 = 平坦 per-vote 配置，不做方向加权

- `trust.judge-reward.credits-per-vote`（默认 20，运营可调）
- **刻意不做**「与多数一致才多给」的质量加权：少数派判决可能是正当异议，加权会制造从众偏差与合谋套利面；平坦金额同时消除了「为钱站队」的激励（ADR 明记此论证）。质量加权登记为远期选项
- v1 无日上限（分案随机 + 争议量天然限速；日上限登记为升级杠杆，配额机器将来可直接加）

### D4 跨服务 = outbox 事件 → finance 异步消费，不占审判关键路径

- trust 同事务发**逐审判官**事件（量小：≤7/轮，且 finance/identity 双消费方都好处理）：

```json
"JudgeVoteRewarded": { "disputeId": "...", "round": 2, "judgeAccountId": "...", "credits": 20 }
```

- finance 新增 Kafka 消费者（镜像 identity 通知中心的 inbox 幂等模式：`consumer_name + event_id` inbox + 处理器），调用**本服务内** `CreditsService` 赠送路径入账
- **幂等键**：`operation_id = judge-reward:{disputeId}:{round}:{judgeAccountId}`——credits 流水既有 operation 唯一索引吸收 Kafka at-least-once 重放
- **绝不在审判终局事务里同步调 finance**（finance 不可用会拖死裁决主链路；这正是 outbox 存在的理由）

### D5 防刷

- 主闸复用既有：审判官 = Lv5 + 运营准入（trust V8 准入版本与只追加审计 + marketplace 权威声誉快照门），高弃权率可由运营用既有撤销工具处理——零新代码
- 平坦金额（D3）消除方向性套利；投票窗约束刷量节奏；Kafka 重放由幂等键吸收
- ADR 登记：合谋（审判官与当事方）在本方案下无金钱放大器（奖励与结果无关）

### D6 记账与审计

- finance migration：`credits_transaction.type` CHECK 扩展新值 `judge_reward`（镜像当年加 `refund` 的先例，先 grep 该 CHECK 所在迁移版本）
- **trust 侧不建奖励表**：outbox（决策痕迹）+ credits 流水（发放痕迹）双痕迹即审计面；operation_id 可双向对账
- 消费失败走既有 DLT/重试语义，处理进度暴露 pending/lag 指标（对齐五个 outbox owner 的观测约定）

### D7 通知（搭 #28 便车）

- identity `NotificationTemplates` 加 `JudgeVoteRewarded`：DISPUTE 类，收件人 = `judgeAccountId`（payload 直读），深链 `/me/disputes`，文案含积分数；payload 不泄露其他审判官
- 邮件经 `MailTemplates` 委托自动覆盖（DISPUTE 在高价值子集）

### D8 前端零新增（v1）

审判官在既有积分历史（`/api/credits/history`，类型 label 加「审判奖励」）+ 通知中心看到结果；审判台不改造。

## Phase B 实施阶段

### Stage B1 — trust：轮终局发奖事件

- `AdjudicationActivityImpl` 轮终局处：收集该轮计入裁决的票 → 与 `DisputeDecided` **同事务**逐 judge append `JudgeVoteRewarded`（确定性 event_id：`type+disputeId+round+judgeId`，镜像既有命名 UUID 去重手法）
- 配置 `trust.judge-reward.credits-per-vote:20`；金额策略集中在 trust（finance 只执行）
- **测试**：多数票提前终局→已投者有事件、未投者无；窗口到期裁决同；重开轮各自计发（round 递增幂等）；客服终审轮零事件；事件与 DisputeDecided 同事务（回滚即都不发）

### Stage B2 — finance：消费者 + 入账

- finance 首个 Kafka 业务消费者：inbox 表 + processor（镜像 identity 形态；consumer group、DLT、lag 指标对齐既有观测约定）
- `CreditsService` 赠送路径接入 `judge_reward` 类型 + `judge-reward:{disputeId}:{round}:{accountId}` operation_id
- migration：type CHECK 扩展
- **测试**：入账正确（余额+流水+类型）；同 event 重放不重复入账（inbox 幂等 + operation 唯一双保险）；坏消息进 DLT 不阻塞分区

### Stage B3 — identity：通知模板

- `NotificationTemplates` + `NotificationRecipientResolver` 加 `JudgeVoteRewarded` case（D7）
- **测试**：镜像 `ExternalNotificationRoutingTest` 的 #28 样板（收件人/分类/深链/payload 不泄露）

## 验收标准

1. 一轮 7 人陪审、5 人按时投票、多数票终局：5 名审判官各 +20 积分（余额与流水可查、类型 `judge_reward`），2 名未投者无任何发放；通知送达 5 人
2. 打平重选：两轮的按时投票者各自获得两轮奖励；重放/消费者重启不重复入账
3. 客服终审（上诉后）不产生任何奖励事件
4. `DisputeDecided` 与奖励事件同事务：裁决回滚则奖励不发
5. finance 消费者 DLT/lag 指标可见；坏消息不阻塞分区
6. 既有审判/争议/credits 测试零回归

## 代码库陷阱清单（必读）

- Java 构建：JDK 25（`JAVA_HOME=/opt/homebrew/opt/openjdk@25`），入口 `platform-java/` 下 `./gradlew`
- **outbox 与领域写同事务**（R2D2 纪律）：奖励事件必须与轮终局状态变更同一 R2DBC 事务 append
- **不在审判关键路径同步调 finance**（D4）；消费者侧一切外部效果幂等（inbox + operation 双保险）
- 消费者形态镜像 identity `NotificationEventProcessor`（inbox `consumer_name+event_id`、DLT、事务边界），别自创

- Jackson 3：事件/请求 record 可选数值字段必须包装类型；`is` 前缀派生态加 `@JsonIgnore`
- 通知 payload 不泄露其他审判官账号（#28 测试断言样式）
- migration 版本号动手前 `ls` 确认；积分为整数运算
