<a id="production-infrastructure"></a>

## 一、生产边界与外部基础设施

- 公网只开放经 TLS 终止的应用入口；治理台按部署策略限制来源，Java management 端口、数据库、消息与观测服务保持私网。生产 overlay 不代替部署侧端口、防火墙和 LB 配置审查。
- 真实 PSP 受 D-01 渠道准入约束；生产 Compose 门禁拒绝 Sandbox PSP 和 Sandbox AI provider。未接真实渠道时，模拟支付与内部账务验证只能作为隔离环境证据。
- 基础 Compose 的单 broker Kafka 和 `start-dev + SQLite` Temporal 仅用于开发。发布脚本固定叠加 [production overlay](../../docker-compose.production.yml)，默认启动集排除本地 Kafka/Temporal，应用连接外部 HA 集群；生产环境不要启用 `development` profile。
- 数据库变更采用 expand/contract，旧版本须兼容新 schema。应用回滚不撤销已执行的 migration、Kafka 事件或 Workflow history。
- Redis 身份断言 replay key 是短期防重放状态，不纳入业务备份。

<a id="kafka-temporal"></a>

### Kafka 与 Temporal 生产基线

下表的副本数、故障域、留存和恢复要求由部署方落实；仓库提供客户端配置、契约和静态门禁，不能据此认定外部集群已达标。

| 组件 | 部署要求 | 仓库侧配置与契约 |
|---|---|---|
| Kafka | 至少 3 broker，跨 3 个故障域；replication factor 3，`min.insync.replicas=2`；按环境隔离账号与 ACL | `KAFKA_BOOTSTRAP_SERVERS` 指向外部集群，`SASL_SSL + SCRAM-SHA-512`；PKCS12 truststore 只读挂载，禁止匿名公网与 PLAINTEXT |
| Kafka 事件 | 配置保留期与 DLT 处置 SLA；监控 lag、outbox age 和死信 | 五个领域 Topic：`grassland.identity.events`、`grassland.marketplace.events`、`grassland.finance.events`、`grassland.trust.events`、`grassland.intelligence.events`，以及所需的 `.DLT`；生产者保持 `acks=all`、idempotence 与有限重试，Outbox/Inbox 保持幂等 |
| Temporal | 托管或独立多副本集群，持久层跨可用区；禁止 start-dev/SQLite | 独立非 default namespace，建议 `grassland-production`；外部 target、TLS/mTLS、只读客户端证书与私钥、正确的服务端名称 |
| Temporal worker | `marketplace-saga`、`trust-adjudication` 两个业务队列各至少 2 个 worker 副本，按 backlog 扩容 | namespace retention 覆盖最长业务窗口、客服等待期和恢复时间；变更 Workflow 前执行 replay 验证，观测 poller、schedule-to-start latency 与 stuck workflow |

证书、ACL、Topic/Namespace 创建、broker/worker 副本、history 归档和持久层备份均由外部基础设施管理。单机应用 Compose 不自动提供上述 HA 或 worker 多副本能力。

### 首次上线验收

1. 在隔离生产候选环境准备 Topic、DLT、ACL、Namespace、证书和留存配置。
2. 执行[发布 preflight](#production-release)，核对默认启动集与依赖，确认应用不再依赖本地 Kafka/Temporal。
3. 走通任务预留、确认结算、争议审判，核对 Outbox → Kafka → Inbox 和 Temporal history；确认 lag/outbox/DLT 告警与 receiver 送达。
4. 在基础设施负责人批准的范围内分别演练 broker、worker、持久层副本故障，核对一致性、恢复耗时、告警和实际 RPO/RTO。
5. 演练证书轮换、消费者版本回退和 Workflow worker 回退，复核 history 归档及持久层恢复。

事件 schema 向后兼容扩展，Workflow 变更保持 replay 兼容。无法消费旧事件或历史时停止发布；不得通过清空 Topic、随意重置 offset 或终止 Workflow 代替兼容性修复。

## 二、密钥管理

真实密钥由 Vault、云 Secret Manager 或 SOPS 在部署机临时物化，[生产密钥契约](../../deploy/security/production-secret-contract.csv)与示例配置仅描述要求。每项密钥选定一个权威来源；SOPS 可作 GitOps 加密载体，不与云 Secret Manager 独立维护同一“当前值”。加密文件、KMS/age recipient 和凭据台账存私有部署仓库或安全工单系统。

使用 SOPS 时，先创建权限为 0700 的目标目录，再做一次 dry-run；脚本将解密到同目录的 mode-0600 临时文件，完整执行生产 secret contract，只有通过后才允许原子替换：

~~~bash
install -d -m 0700 /run/secrets/grassland

scripts/materialize-production-secrets.sh \
  --input /secure-config/grassland/production.env.enc \
  --output /run/secrets/grassland/production.env

scripts/materialize-production-secrets.sh \
  --input /secure-config/grassland/production.env.enc \
  --output /run/secrets/grassland/production.env \
  --execute --replace
~~~

脚本拒绝相对输出路径、符号链接、组/其他用户可访问的目标目录、空解密结果和不完整生产配置；不会把解密值写到 stdout。云 Secret Manager/Vault 应由部署身份以同样的 mode-0600 临时文件契约物化，再执行 `validate-production-secrets.sh`。应用运行身份只读当前版本，轮换身份才拥有创建、禁用和销毁版本权限。

生产前执行：

~~~bash
chmod 600 /run/secrets/grassland/alertmanager-webhook-url
chmod 600 /run/secrets/grassland/grafana-admin-password
chmod 600 /run/secrets/grassland/production.env
scripts/validate-production-secrets.sh --env-file /run/secrets/grassland/production.env
~~~

生产环境至少需要：

- `PUBLIC_FORWARDED_PROTO=https`，且 `SESSION_COOKIE_SECURE` 不得为 `never`；Nginx 据可信协议配置发送 HSTS。
- Redis replay 防护开启。
- MinIO root 凭据只用于 bootstrap，运行服务使用不同的受限 service account。
- ALERTMANAGER_WEBHOOK_URL_FILE 和 GRAFANA_ADMIN_PASSWORD_FILE 指向权限不高于 0600 的真实文件，不得指向仓库 example。
- 按[断言密钥登记表](../../deploy/security/identity-assertion-key-pairs.csv)逐对配置，保证 access-token 签发/验签一致，不固定依赖历史密钥对数量。
- `CONFIRMATION_WINDOW_SECONDS >= 259200`，Finance credits↔cents policy 已批准且 Finance/Intelligence 两侧一致；完整要求以校验脚本为准。
- Kafka 使用外部 bootstrap、`SASL_SSL + SCRAM-SHA-512` 和只读 PKCS12 truststore；Temporal 使用独立 namespace、HTTPS/mTLS 与权限不高于 0600 的客户端私钥。

轮换 access token 或断言密钥使用三阶段流程。`rotate-identity-keys.sh plan-*` **会生成并输出新密钥材料**，应保存为受控的 0600 文件，不能直接输出到共享终端日志或当作脱敏 evidence：

~~~bash
(
  umask 077
  set -e
  set -o noclobber
  scripts/rotate-identity-keys.sh plan-access-token access-token-20260915 \
    > /run/secrets/grassland/access-token-20260915.plan
  scripts/rotate-identity-keys.sh plan-assertion EDGE_USER_FINANCE edge-user-finance-20260915 \
    > /run/secrets/grassland/edge-user-finance-20260915.plan
)
~~~

每次轮换用新的文件名；计划文件不自动写入 Secret Manager 或更新容器。

先把新 key 放入所有 verifier 的 previous slot，再更新 signer/current verifier 并保留旧 key；从实际切换完成时起等待 TTL + leeway 后移除旧 key。每阶段重新执行 `validate-production-secrets.sh` 并验证回退，禁止单边直接替换。

三阶段真实滚动和回退验证完成后，将不含 secret 的结果整理为 `identity key rotation evidence v1`，再执行发布门禁：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env key-rotation-promote \
  --release-id 2026-09-15.1 \
  --rotation-evidence /secure-drills/2026-09-15/access-token-rotation-evidence.txt \
  --rotation-max-age-seconds 604800
~~~

校验器要求 old/new `kid` 不同、三阶段严格顺序、Phase 2 后完整等待 TTL + leeway、每阶段配置验证和回退检查均通过，且旧 key 已退休。证据只记录 key id 和状态，绝不能记录 key material；`key-rotation-promote` 还会重新执行生产 secret contract 校验。

历史 SMTP、provider API key、数据库账号、对象存储 service account 等非 identity 凭据必须逐项生成独立证据 worksheet。`old/new-credential-id` 只能填供应商 key ID、Secret Manager version 或数据库角色名，禁止填密钥值：

~~~bash
scripts/create-credential-rotation-evidence.sh \
  --output /secure-drills/2026-09-15/smtp-credential-evidence.txt \
  --release-id 2026-09-15.1 \
  --target smtp-password \
  --backend sops \
  --old-credential-id smtp-key-v1 \
  --new-credential-id smtp-key-v2 \
  --services identity-service \
  --rollout-mode maintenance \
  --revocation-method provider-revoked \
  --approval-reference SEC-2026-0915
~~~

按实测结果填写所有 `PENDING` 字段后执行：

~~~bash
scripts/validate-credential-rotation-evidence.sh \
  --evidence /secure-drills/2026-09-15/smtp-credential-evidence.txt \
  --release-id 2026-09-15.1

scripts/production-release.sh \
  --env-file /run/secrets/grassland/production.env \
  credential-rotation-promote \
  --release-id 2026-09-15.1 \
  --credential-evidence /secure-drills/2026-09-15/smtp-credential-evidence.txt
~~~

晋级门禁要求：新值已物化、发布完成、readiness/smoke 通过、回退演练通过、旧凭据已在源系统吊销、旧凭据负向验证失败，并有审批和审计引用。仅从 Secret Manager 删除旧值不算吊销。回退演练必须发生在吊销前；吊销后禁止重新启用已暴露旧凭据，应用回退仍使用新凭据。

### CRYPTO_KEK_BASE64（信封加密根密钥）的特殊轮换语义

`CRYPTO_KEK_BASE64` 的契约责任方为 `security+intelligence`，必须解码为 32 字节。它用于解开 BYOK、平台凭据和 KYB 敏感字段，不能按普通 API key 的“换新后吊销旧值”处理。

1. **新旧版本并存**：通过受控配置设置新当前版本和显式旧版本映射，确保所有读写服务具备所需密钥。例子只说明格式：

   ```dotenv
   CRYPTO_KEK_BASE64=<新的32字节Base64>
   CRYPTO_KEK_VERSION=2
   CRYPTO_KEK_PREVIOUS=1=<旧的32字节Base64>
   ```

   密文首字节记录版本；旧版本配置为逗号分隔的 `version=base64`。缺失版本时解密显式失败，不回落当前 KEK。新写入使用当前版本，存量仍依赖对应的旧版本。

2. **重加密存量**：至少覆盖下表；轮换前按当前源码的 `EnvelopeEncryption` 调用点重新盘点，不能只处理 BYOK。

   | 数据类别 | 当前持久化位置 |
   |---|---|
   | 个人/组织 BYOK、平台模型凭据 | `ai_provider_key.encrypted_key`、`platform_provider_credential.encrypted_key` |
   | 用户集成、首页热榜 | `user_settings` 中的 `integrations.feishu.appSecretEncrypted`、首页热榜配置的 `alapi_token_encrypted` |
   | KYB 敏感字段 | `merchant_profile.legal_person_id_number`、`withdrawal_account.account_number_encrypted` |
   | 创作提示词 | `creation_text_proposal.prompt_ciphertext`、`creation_visual_plan.prompt_ciphertext` |
   | 公众号绑定凭据 | `creation_wechat_account.encrypted_secret` |

   加密字段更新时同步维护对应版本列；微信公众号 access token 等 Redis 加密缓存另按 TTL/定向失效处理，在线仍需旧 KEK 的缓存未过期前不能撤走旧版本。

   **仓库目前没有完整重加密工具**；应先实现可恢复、可审计的工具并在恢复环境验证。`EnvelopeEncryption.rotateKey()` 是 no-op，不执行此操作，不能用它宣告 KEK 轮换完成。

3. **验证版本与可解密性**：工具逐表输出计数，检查密文实际版本和解密结果。下列 SQL 仅辅助检查有 `key_version` 列的两张表，不能覆盖 JSON/KYB 字段，也不能代替解密验证：

   ```sql
   SELECT COUNT(*) FROM ai_provider_key
    WHERE encrypted_key IS NOT NULL AND key_version IS DISTINCT FROM 'v2';
   SELECT COUNT(*) FROM platform_provider_credential
    WHERE encrypted_key IS NOT NULL AND key_version IS DISTINCT FROM 'v2';
   ```

4. **退休旧版本**：确认在线数据全部迁移且回退兼容后，才从在线 `CRYPTO_KEK_PREVIOUS` 移除旧版本。仍可能恢复的历史备份若依赖旧 KEK，必须继续受控保留该版本；只有所有依赖解除后才能销毁。KEK 退休以[密钥与数据联合恢复验证](#production-backup)为依据，不能套用普通凭据的吊销门禁。

## 三、可观测性

完成生产环境配置并确保应用已启动后，在同一 Compose 项目中启动私网观测服务：

~~~bash
docker compose --env-file /run/secrets/grassland/production.env \
  -f docker-compose.yml -f docker-compose.production.yml \
  --profile observability up -d --no-deps prometheus alertmanager grafana
~~~

`--no-deps` 避免此操作重新拉起应用依赖；应用镜像更新统一走发布流程。Alertmanager/Grafana 使用第二节的真实 secret 文件。Grafana 通过私网 ingress 或 VPN 访问，不将 3000/9090/9093 直接开放到公网。

Prometheus 抓取 Edge、Identity、Marketplace、Finance、Trust、Intelligence 六个 Java 服务，Grafana 自动加载 Platform Overview。当前规则见[观测配置目录](../../platform-java/deploy/observability/)：

| 规则 | 阈值与持续时间 |
|---|---|
| 服务不可抓取 | 连续 2 分钟 |
| HTTP 5xx | 比例高于 5%，连续 10 分钟 |
| JVM heap / process CPU | 分别高于 85% / 90%，连续 15 分钟 |
| Identity 邮件死信 / Marketplace 运营死信 | 存在死信，分别持续 1 分钟 / 2 分钟 |
| 五领域 Outbox | 最老未发布事件超过 60 秒，持续 2 分钟；可抓取但指标缺失持续 5 分钟另告警 |
| Identity/Marketplace consumer lag | 超过 1000，持续 5 分钟；可抓取但 lag 指标缺失持续 10 分钟另告警 |

### Trace 与日志

Edge 规范化并回传 `X-Request-Id`、W3C 32 位 `X-Trace-Id` 和 `X-Correlation-Id`，透传 Java 上游。六服务使用 Spring Boot OpenTelemetry starter 和 W3C Trace Context；Kafka producer/consumer observation 与 Marketplace/Trust Temporal tracing bridge 已接线。生产输出 ECS JSON 日志，指标继续由 Prometheus 抓取，OTLP metrics exporter 关闭。

生产 overlay 启用 `OTEL_TRACING_ENABLED=true`、`OTEL_EXPORT_ENABLED=true`，要求 `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` 为非本机的 HTTPS traces endpoint，并校验采样率在 0–1。应用接线和配置校验不证明跨 HTTP、Kafka、Temporal 的真实 trace 已送达，必须在部署环境保存链路证据。

本地 OTLP receiver 验证单独运行：

~~~bash
scripts/local-otel-trace-smoke.sh
~~~

该脚本启动固定隔离项目 `grassland-otel-smoke` 的 collector，发送唯一 trace，从 debug exporter 核对 trace/span ID，并默认清理容器。它只证明本地 OTLP/HTTP 投递；本地 collector 不进入生产 overlay，也不能代替生产 collector 或告警 receiver 验收。

### 告警送达门禁

发布脚本的 preflight/plan/deploy/rollback 会执行 `validate-observability-config.sh`，检查 scrape target、starter/W3C 配置、规则、secret-backed receiver 和 Grafana 面板。每次真实发布还应检查 target 全绿、规则 health=ok，并测试 firing → receiver delivery → resolved 通知。

真实验收结果整理为脱敏 evidence 后执行：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env observability-promote \
  --release-id 2026-09-15.1 \
  --observability-evidence /secure-drills/2026-09-15/observability-evidence.txt \
  --observability-max-age-seconds 86400
~~~

校验器要求 firing、receiver、delivery、resolved、targets 和 smoke 均通过，时间顺序正确且证据新鲜。`observability-promote` 只校验记录，不触发测试告警或修改观测栈。

## 四、发布与迁移

当前发布脚本采用单栈 Compose 更新，不提供逐副本流量编排。单机按维护窗口执行；需要无中断更新时，由部署侧建立蓝绿双栈并在 LB 切流，或在 Kubernetes 配置 `maxUnavailable=0`、`maxSurge=1` 与 readiness gate。真实发布或切流没有完成时，证据中的 `rollout_status` 不能标为 passed。

下面是生产配置中的发布字段示例，不是完整 env 文件。八个受发布脚本管理的镜像必须固定到 repository digest：

~~~dotenv
RELEASE_IMAGE_FRONTEND=registry.example/grassland/frontend@sha256:...
RELEASE_IMAGE_DATABASE_BOOTSTRAP=registry.example/grassland/database-bootstrap@sha256:...
RELEASE_IMAGE_EDGE_BFF=registry.example/grassland/edge-bff@sha256:...
RELEASE_IMAGE_IDENTITY_SERVICE=registry.example/grassland/identity-service@sha256:...
RELEASE_IMAGE_MARKETPLACE_SERVICE=registry.example/grassland/marketplace-service@sha256:...
RELEASE_IMAGE_FINANCE_SERVICE=registry.example/grassland/finance-service@sha256:...
RELEASE_IMAGE_TRUST_SERVICE=registry.example/grassland/trust-service@sha256:...
RELEASE_IMAGE_INTELLIGENCE_SERVICE=registry.example/grassland/intelligence-service@sha256:...
COSIGN_PUBLIC_KEY_FILE=/run/secrets/grassland/grassland-cosign.pub
MIGRATION_COMPATIBILITY_APPROVED=yes
FINANCE_RELEASE_APPROVED_BY=<审批人或工单号>
PUBLIC_HEALTH_URL=https://api.example.com/health
PUBLIC_SMOKE_BASE_URL=https://api.example.com
~~~

### 镜像与迁移前置条件

CI 的 [image-security 脚本](../../scripts/ci-image-security.sh)扫描 **9 个镜像**，包含 `release-migrator`，以 Trivy 阻断 HIGH/CRITICAL 并生成 SPDX JSON。真实 registry digest 生成后仍需 cosign 签名与 attestation；本地缓存扫描不能替代 CI 的新鲜基础镜像扫描。

### 标准发布流程

确认上述前置条件、凭据、兼容性审批和备份均已准备，再依次执行：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env preflight
scripts/production-release.sh --env-file /run/secrets/grassland/production.env plan --release-id 2026-09-15.1
scripts/production-release.sh --env-file /run/secrets/grassland/production.env deploy \
  --release-id 2026-09-15.1 \
  --backup-manifest /secure-backups/2026-09-15/manifest.txt
scripts/production-release.sh --env-file /run/secrets/grassland/production.env deploy \
  --release-id 2026-09-15.1 \
  --backup-manifest /secure-backups/2026-09-15/manifest.txt \
  --execute
~~~

`preflight`/`plan`/`deploy`/`rollback` 均校验生产 Compose、镜像来源、可观测性和已发布迁移。默认启动集须排除本地 Kafka/Temporal，保留外部 TLS/mTLS、只读凭据挂载、七个常驻应用 readiness gate，以及 Edge 对领域服务的 `service_healthy` 依赖。八个受管镜像使用 digest，并通过 `COSIGN_PUBLIC_KEY_FILE` 对应公钥的 cosign 签名与 SPDX attestation 校验。

`preflight` 执行完整密钥/Finance policy 检查；`plan` 和 `rollback` 不会重复全部密钥校验，不能跳过 preflight。`deploy` 另要求 `--backup-manifest`，并核对备份目录及其 checksum；单独复制 manifest 而缺少原备份文件不能通过。

生产 overlay 为应用与迁移服务声明 CPU/memory limits 与 reservations，默认分别为 `2.0 CPU / 2G`、`0.25 CPU / 256M`，按容量评审用 `PRODUCTION_SERVICE_*` 调整。当前资源校验覆盖八个受管服务；它检查配置，不证明容量、主机资源预留或 HA 已达标。

不带 `--execute` 时不改容器或数据库，但 plan/deploy 会在本地生成发布配置，镜像验签也会访问 registry。实际部署重新检查门禁、执行迁移、保存旧容器镜像引用与发布状态到被 Git 忽略的 `.release-state/<release-id>/`，复制 manifest 后以 `--no-build` 更新应用，等待 readiness 和 `PUBLIC_HEALTH_URL`。保留此状态目录及原备份目录供回退；health 失败只会报错提示，不会自动回滚。公网 health 通过后自动运行只读 smoke：`/health`=200、`/internal` 与 `/api/internal`=404、未知 `/api`=404、匿名 `/api/tasks/feed`=401；只有显式提供短时 `RELEASE_SMOKE_ACCESS_TOKEN` 才追加认证 Marketplace feed 读取，未提供时明确标记为 skipped，不冒充完整业务验收。

发布完成后至少手工验证登录、任务读取、余额只读、媒体读取，并观察 15 分钟 5xx/CPU/heap。涉及真实 PSP 时还需在 PSP 沙箱验证支付、退款、分账、提现、Webhook 和对账各一笔。

### Edge 路由契约与重建

Edge BFF 是唯一 API 入口：`API_UPSTREAM` 必须保持 `edge-bff:8080`（生产 overlay 与基础 Compose 同值），不配置自动 upstream failover，避免非幂等 POST 被两个上游重复执行。未登记路由、方法不匹配或 `EDGE_ROUTE_*` 关闭的路径一律 fail-closed 返回 404，不回退到任何旧 Node 后端；JBE-04 之后不再支持整入口回退。

RouteManifest 变更（含路由开关调整）后必须重建 Edge 容器才生效。适用条件与命令：

- 本地基础栈（`.env.docker`）：`docker compose --env-file .env.docker up -d --no-deps --force-recreate edge-bff`
- 生产 overlay：通过 `production-release.sh` 的受管发布流程更新 Edge 镜像；仅当路由开关属于运行时环境调整（不换镜像）时，才用等价的 `up -d --no-deps --force-recreate edge-bff`（`--env-file` 指向生产 env）单独重建，并保留发布记录。

### 模型控制面升级与功能开放

当前模型端点、模型名和凭据由治理台控制面管理：`platform_model_config`、`platform_provider_credential`、`platform_trusted_origin` 与价目表。视频生成/TTS 也读取对应能力行。保留的模型迁移顺序只适用于从仍依赖旧 env 的版本升级：

1. **先配置**：旧版运行期间准备全部能力行、真实凭据、受信端点和价目；对旧 V46/V50 无密钥回填行补齐凭据。在隔离环境逐能力冒烟。
2. **再发布**：确认相关增量迁移执行、KEK 已配并可解密后升级，验证控制面路径。
3. **再移除废弃注入**：按 `validate-production-compose.sh` 的确切封禁表移除旧模型连接/凭据变量。涉及 `QWEN_BASE_URL/API_KEY/MODEL`、`AI_SPEECH_API_KEY`、`AI_EMBEDDING_API_KEY`、图片模型连接字段以及 `VIDEO_GENERATION_MODE/BASE_URL/API_KEY/MODEL/WEBHOOK_SECRET` 等；不要按通配符删除所有同前缀参数。
4. **保留受控回退版本**：旧版仍依赖的 Secret Manager 配置版本保留到回退窗口结束，避免“从当前部署移除”变成“物理销毁所有旧配置”。

`IMAGE_GENERATION_PRICING_VERSION`、`IMAGE_GENERATION_UNIT_PRICE_CENTS`、视频 worker 运行时参数与 Finance policy 仍是有效部署参数。`CRYPTO_KEK_BASE64` 是平台凭据落库与解密的必要条件，不能因去 env 而删除。

生产 overlay 的 `EDGE_ROUTE_CREATION_STUDIO_INTELLIGENCE` 和 `EDGE_ROUTE_CREATION_WECHAT_INTELLIGENCE` 默认关闭。新能力开放需满足[任务书 #101](../任务书/草场任务书-101-AI创作工作流与图文交付升级.md)的迁移、配置和试点条件，不因应用 health 通过自动开放。

## 五、Canary 发布门禁

Canary 目前由 `scripts/production-canary-plan.sh` 生成只读 dry-run 计划，不会修改流量、容器或路由。生产操作人必须在已批准的 ingress/LB 工单中执行实际流量切分，并在每个 hold point 保存 Prometheus 查询结果和审批记录：

~~~bash
scripts/production-canary-plan.sh plan \
  --release-id 2026-09-15.1 \
  --service edge-bff \
  --canary-image 'registry.example/grassland/edge-bff@sha256:<64hex>' \
  --baseline-image 'registry.example/grassland/edge-bff@sha256:<64hex>' \
  --public-health-url https://api.example.com/health \
  --prometheus-url https://prometheus.example.com \
  --output /secure-drills/2026-09-15-canary.txt
~~~

计划阶段固定为 0% warm-up 5 分钟、1% 至少 10 分钟、10%/25%/50% 各至少 10 分钟，再经 incident commander 批准提升到 100%。每个阶段都要记录 canary/baseline 的 5xx、p95、JVM、readiness、outbox age、consumer lag、依赖错误率、告警送达和只读 smoke 结果。5xx 超过 5% 连续 2 分钟（或高于基线 2 个百分点）、p95 超过 2 秒连续 2 分钟（或高于基线 50%）、readiness/依赖/安全/资金对账异常时立即停止扩容，按计划将流量切回 baseline digest。不得自动逆向数据库迁移；真实 canary、TLS/LB、告警送达和 RTO/RPO 仍需部署侧证据。

canary 实际切流完成后，操作人必须按固定 v1 字段生成脱敏 evidence（不得把上面的 dry-run plan 当 evidence），再执行机器晋级门禁：

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env canary-promote \
  --release-id 2026-09-15.1 \
  --evidence /secure-drills/2026-09-15/canary-evidence.txt \
  --service edge-bff \
  --canary-image 'registry.example/grassland/edge-bff@sha256:<64hex>' \
  --baseline-image 'registry.example/grassland/edge-bff@sha256:<64hex>'
~~~

校验器要求 warm-up、1%/10%/25%/50%/100% 每个 hold point 均通过且至少满足规定时长，readiness、依赖、Finance 对账、告警送达、smoke 和 rollback-ready 均为 `passed`；超过 5xx 或 p95 abort 阈值、证据过期、digest 错配或重复字段都会 fail-closed。`canary-promote` 只验证记录，不执行切流。

## 七、备份与恢复演练

[备份脚本](../../scripts/backup-restore-drill.sh)输出 PostgreSQL custom dump、指定 MinIO bucket 的当前对象镜像和 SHA-256 manifest。它不备份 Kafka、Temporal、KEK、对象存储 IAM/桶策略或历史对象版本；这些由各系统单独备份与演练。BGM 位于同一 bucket 的 `bgm/` 时随对象镜像一起备份。

### 备份与完整性检查

在受控环境注入源端 `DATABASE_URL`、`MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET`，确认目标是本次独立空目录：

~~~bash
umask 077
scripts/backup-restore-drill.sh backup --destination /secure-backups/2026-09-15
scripts/backup-restore-drill.sh verify --manifest /secure-backups/2026-09-15/manifest.txt
~~~

`backup` 会立即读取源数据并写本地备份，不需要 `--execute`；`verify` 只核对 manifest 版本、文件集合与 checksum。将备份目录加密保存并按策略复制到异地。数据库 dump 与对象 mirror 是分步执行，需记录各自时间并在业务静默窗口或经验证的一致性方案下执行。

### 恢复到隔离环境

脚本仅按数据库 host 名称及 bucket 前缀做基本保护：目标数据库与源 URL 不同，host 为 localhost/回环或名称含 restore/drill/staging，bucket 以 `grassland-restore-drill-` 开头。名称通过校验不代表网络、账号和外部通知已隔离，执行前仍需核对实际目标。

源端与目标端使用不同凭据，明确设置以下目标参数：

| 参数 | 要求 |
|---|---|
| `--target-database-url` | 使用不含密码的隔离库 URI，密码通过 0600 的 `PGPASSFILE` 等 PostgreSQL 凭据机制提供；脚本 dry-run 会打印该 URI |
| `TARGET_MINIO_ENDPOINT` | 明确指向隔离存储，未配置时脚本会沿用源端 |
| `TARGET_MINIO_ACCESS_KEY` / `TARGET_MINIO_SECRET_KEY` | 由受控环境注入隔离账号；未配置时会沿用源端凭据，不能忽略 |
| `--target-bucket` | 本次独立的演练 bucket |

确认目标端配置后先预演，再执行：

~~~bash
scripts/backup-restore-drill.sh restore \
  --manifest /secure-backups/2026-09-15/manifest.txt \
  --target-database-url postgresql://restore_user@restore-db.internal/grassland_drill \
  --target-bucket grassland-restore-drill-20260915

scripts/backup-restore-drill.sh restore \
  --manifest /secure-backups/2026-09-15/manifest.txt \
  --target-database-url postgresql://restore_user@restore-db.internal/grassland_drill \
  --target-bucket grassland-restore-drill-20260915 \
  --execute
~~~

实际恢复调用 `pg_restore --clean --if-exists --no-owner`，会清理并重建目标中的相应对象；MinIO 写入显式目标 bucket。脚本末尾只核对 `app_users` 和 `organization` 基本行数，完整验收还包括登录、任务、资金台账只读一致性、媒体/BGM 下载以及对象与数据库引用对应。恢复环境不得触发真实 PSP、邮件、短信或推送。

### 数据与密钥联合恢复

manifest 通过只证明文件完整。数据库与 SOPS/Secret Manager 的密钥版本必须分别恢复；按第二节的持久字段清单，对有存量数据的类别分别抽查解密，包括 BYOK、KYB、创作提示词和渠道凭据。没有对应数据时记录未覆盖范围，不能补写成功结果。只在页面看到掩码不是解密成功证明，证据记录结果与版本，不记录明文。

KEK 的保留期须覆盖所有依赖它的数据库备份。当前库完成重加密后也不能直接销毁旧 KEK，历史备份可能仍含旧版本密文。Kafka/Temporal 的持久层、history、留存与外部恢复结果另附工单，不计为此脚本自动完成。

~~~bash
  --output /secure-drills/2026-09-15/video-webhook-plan.txt
~~~

确认兼容环境的实际验签配置后，将匹配的 secret 与 owner 短时 access token 分别放入 0600 文件。脚本的 `--secret-file` 只用于签发演练请求，不会给服务端配置密钥。不要将二者写入命令行、仓库或证据；经维护工单批准后显式执行：

~~~bash
scripts/video-webhook-drill.sh run \
  --base-url https://api.example.com \
  --provider minimax \
  --provider-task-id PROVIDER_TASK_ID \
  --job-id JOB_UUID \
  --drill-id 2026-09-15-video-webhook-01 \
  --access-token-file /run/secrets/grassland/drill-owner-token \
  --secret-file /run/secrets/grassland/video-webhook-secret \
  --output /secure-drills/2026-09-15/video-webhook.txt \
  --confirm-live-webhook-drill
~~~

脚本依次验证有效 80% 回调、完全相同事件的重放、新事件携带迟到 20% 进度、owner-scoped Job 查询仍保持 `processing:80`，以及坏签名必须返回非 2xx。证据文件只记录状态码、事件 ID、最终状态/进度和时间戳，不记录 token、签名或 secret。工单还必须附 ingress 日志、inbox claim 数、Job/AI Run/补偿对账、告警送达和演练后 polling 恢复结果。旧协议的部署验证也须使用真实公网入口，不能用 mock 契约替代；证据范围仍限于旧 Job。

### 旧 Job 归档与 Finance operation 对账

受控兼容环境中的真实 provider 旧 Job 完成并归档后，先生成只读演练计划：

~~~bash
scripts/video-archive-reconciliation-drill.sh plan \
  --base-url https://api.example.com \
  --job-id JOB_UUID \
  --drill-id 2026-09-15-video-archive-01 \
  --output /secure-drills/2026-09-15/video-archive-plan.txt
~~~

将 Job owner 与 platform admin 的短时 access token 分别放入 0600 文件。审批后执行：

~~~bash
scripts/video-archive-reconciliation-drill.sh run \
  --base-url https://api.example.com \
  --job-id JOB_UUID \
  --drill-id 2026-09-15-video-archive-01 \
  --owner-token-file /run/secrets/grassland/video-owner-token \
  --admin-token-file /run/secrets/grassland/platform-admin-token \
  --output /secure-drills/2026-09-15/video-archive.txt \
  --confirm-live-archive-drill \
  --ack-monetary-policy-missing
~~~

演练要求管理员对账中的指定 Job 为 `consistent`、Finance 权威 `credits_consume_operation` 为 `consumed`，owner 下载端点签发 HTTPS URL，且实际对象下载非空、不超过 200 MiB；证据只保存对象大小和 SHA-256，不保存 token 或签名 URL。Finance 当前积分含 paid 与免费 quota 两种来源。只有所有版本化 policy 字段都通过校验时，报告才返回对应的 `monetaryConversionState=<policy-version>`；否则返回 `policy_missing`，脚本必须显式要求 `--ack-monetary-policy-missing` 并输出 `passed_with_monetary_policy_pending`。即使 policy 已配置，本演练也不自动执行金额换算，仍需 Finance 产品批准后才能标记金额层完成。这证明 operation ID、账号、feature、consume/compensation fence 与 Intelligence cents 计量可以联合审计，不代表积分金额已经按某个比例折算成功。

### 旧协议证据晋级

视频 Webhook 与归档演练会生成两份脱敏证据，但演练证据不等于晋级证据。正式晋级前必须由同一 Job、同一 provider 和同一维护窗口产生两份文件，并由校验器验证版本、字段完整性、时间新鲜度、Job 关联、单调进度、Finance authority、私有对象下载摘要和货币换算策略版本。`policy_missing` 或 `passed_with_monetary_policy_pending` 只能留作技术演练记录，不能进入正式晋级。

~~~bash
scripts/production-release.sh --env-file /run/secrets/grassland/production.env promote \
  --release-id 2026-09-15.1 \
  --webhook-evidence /secure-drills/2026-09-15/video-webhook.txt \
  --archive-evidence /secure-drills/2026-09-15/video-archive.txt \
  --job-id JOB_UUID \
  --provider minimax \
  --max-age-seconds 3600
~~~

未显式提供 `--policy-version` 时，脚本取 `--env-file` 中的 `FINANCE_CREDITS_CENTS_POLICY_VERSION`；运行前仍须通过完整 Finance policy 预检。该命令只校验旧协议证据并输出门禁结果，不切流量或修改容器，也不证明新成片管线已验收。校验失败时重新执行适用环境的真实演练，禁止手工编辑证据绕过门禁。证据目录由维护工单引用并至少保留一个发布周期，访问令牌、Webhook secret、签名 URL 和完整 provider payload 不得写入文件。
